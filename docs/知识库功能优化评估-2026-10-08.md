# 知识库功能优化评估（知识图谱与 Wiki）

评估日期：2026-10-08  
范围：现有知识库索引、Graph-RAG、LLM Wiki、知识问答融合及相关前端。  
结论：当前方案已经有较好的产品化基础，但图谱和 Wiki 都应从“可用的辅助功能”升级为“有版本、有证据、有失效链路的知识派生层”。建议优先修复两项会直接影响回答可信度的问题，再推进增量编译与事实级图谱。

> 实施状态（2026-10-10）：本文列出的代码、迁移、接口、前端和自动化验收计划已完成实现。新增 PostgreSQL 演进迁移 `202610100001_knowledge_derived_governance`、`202610100002_knowledge_derived_quality` 与兼容修复迁移 `202610100003_knowledge_derived_quality_repair`，覆盖派生来源生命周期 outbox、图谱 claim/evidence、别名字典、向量消歧、可解释置信度、Wiki 输入快照和回归测试。第三批迁移会幂等补齐 `knowledge_graph_claim_evidence.excerpt_text`，处理滚动发布或历史异常导致的字段缺失。真实目标 PostgreSQL 的迁移执行与业务质量阈值取数需在部署环境运行 `npm run verify:knowledge-derived-governance`；该步骤是发布证据采集，不是待开发功能。

## 当前能力与可保留的设计

现有实现已形成较完整闭环：

```text
原始资料 → 分块 / 向量 / 引用 → 图谱实体与关系 → RAG 召回
                       ↘ 受控来源清单 → Wiki 编译 → 审核发布 → 问答辅助
```

- RAG 已支持关键词、向量、RRF、MMR、引用键和可信度门槛。
- 图谱关系保留了源文档、源分块、置信度和待确认状态；低置信共现关系默认进入 `pending`，方向正确。
- Wiki 将模型输出限制为 JSON，并把每个候选页面的声明绑定到本轮白名单来源；发布前还检查支持性来源和冲突。
- Wiki 对原始文档的版本变化、删除和 ACL 进行了多层校验，且在问答提示中明确“原始资料优先”。
- 已提供图谱人工校准、实体合并、Wiki 审核发布、运行记录和知识评测入口，具备迭代基础。

## 已确认的高优先级问题

### P0：已删除或停用文档的图谱关系仍可能注入默认问答

文档删除流程只将 `knowledge_docs` 标记为删除/禁用并清理 RAG 缓存，没有同步移除或失效其图谱关系和实体提及（`server/services/rag-documents.js:903`）。图谱查询 `getGraphContextForQuery` 对关联的 `knowledge_docs` 使用 `LEFT JOIN`，却未要求文档未删除、已启用或处于可检索状态（`server/services/knowledge-graph.js:518`）。随后该图谱上下文会被无条件追加到 RAG 注入上下文（`server/services/rag-index/index.js:643`）。

影响：删除资料后，向量/关键词召回虽会排除该文档，但同一份资料抽出的关系仍可能作为“参考知识图谱信息”影响回答。这是知识治理与可撤回性问题。

建议：

1. 图谱关系、提及和实体事实均应有 `source_state` 或通过关联来源实时过滤；默认查询必须要求来源文档 `deleted_at IS NULL`、`is_enabled = 1` 且状态可检索。
2. 文档删除、禁用、过期、重建替换统一发出“知识来源失效”事件，由同一事务外盒（outbox）驱动图谱失效、Wiki 标记 stale、RAG 缓存失效。
3. 增加回归测试：删除/禁用文档后，默认 `retrieveContext`、`debugRetrieveContext` 和 `/rag/graph/query` 都不得返回该文档的关系或文本。

### P0：Wiki 搜索会返回零相关页面并把它们注入问答

`searchWikiPages` 只计算 `rank` 后排序，没有以全文匹配或最低分作为 `WHERE` 条件（`server/services/knowledge-wiki.js:796`）。当标题、摘要、正文都不匹配问题时，所有页面的分数都可为 0，但仍会按更新时间进入结果；`retrieveWikiContext` 会继续取页面摘要/正文，形成模型上下文（`server/services/knowledge-wiki.js:821`）。

影响：无关 Wiki 页面会占用上下文预算、干扰模型，并使“Wiki 命中”看起来像有效证据。

建议：

1. 搜索查询应显式使用 `@@`，并在应用层过滤 `rank <= 0` 的页面；无匹配时返回空数组。
2. 中文检索不要仅依赖 PostgreSQL `simple` 分词。复用知识库的 CJK n-gram 检索词，或为 Wiki 建立独立的向量/词法混合索引，再用 RRF 和最小置信度门槛排序。
3. Wiki 上下文只传摘要、关键声明及其来源定位；不得在零相关或来源不足时注入。
4. 增加“完全无关查询返回 0 页”和“低分页面不进入问答上下文”的集成测试。

### P1：图谱的 `depth` 参数没有真正实现多跳遍历

`getEntityGraph` 接收并返回 `depth`（最大值为 2），但 SQL 只取中心实体的一跳关系（`server/services/knowledge-graph.js:318` 至 `342`）；返回 `depth: 2` 不会扩展第二跳节点。

影响：界面/API 语义与实际结果不一致，后续若依赖多跳路径解释或影响分析会得出不完整结论。

建议：短期先将 API 固定为一跳并移除未实现的深度语义；若保留 `depth=2`，使用递归 CTE 或受限 BFS，设置节点、边、总路径和执行时间上限，并返回每条边的来源与路径评分。

### P1：Wiki 编译任务没有固定输入快照，可复现性不足

创建编译任务时会计算并写入 `input_manifest_hash`（`server/services/knowledge-wiki.js:417`），但任务实际执行时重新构建来源清单（`server/services/knowledge-wiki.js:585`），没有比较排队时和执行时的哈希，也没有保存输入快照。

影响：资料在排队期间更新后，同一 run 的记录 hash 与实际模型输入可能不一致；审计、复跑、定位幻觉和解释“这页基于什么生成”都会变得困难。

建议：将 manifest（文档版本、block、内容 hash、定位、编译器/提示版本）持久化到 run 或独立 `knowledge_wiki_compile_inputs` 表。Worker 只使用该快照；若来源已失效，标记 run 为 `superseded_input` 并重新排队，而不是悄然更换输入。

### P1：图谱重建和实体合并缺少原子性与来源生命周期管理

单文档重建先删除旧的关系和提及，再逐块重新索引（`server/services/knowledge-graph.js:699`）；若中途失败，旧图谱已经丢失。图谱实体是用户级去重对象，删除提及后没有区分“自动抽取的孤儿实体”和“人工维护实体”，长期会积累无来源节点。

建议：

1. 使用临时 `graph_revision` 或 staging 表构建完成后原子切换；失败时保留上一可用 revision。
2. 为实体/关系增加 `origin`（auto/manual）、`revision_id`、`last_evidence_at`、`evidence_count`。仅自动生成且无有效证据的节点由异步 GC 清理，人工节点不得被自动删除。
3. 实体合并、关系重定向、去重和源证据迁移必须在一个事务中完成；保留可撤销的合并审计记录。

## 结构性优化方案

### 1. 以“事实断言”替代当前的单层关系记录

当前 `knowledge_relations` 同时承担规范关系、抽取结果、置信度和单一来源的职责。建议拆为三层：

```text
Canonical Entity（规范实体）
  └─ Relation / Claim（规范断言：A depends_on B）
       └─ Evidence（多条证据：文档版本、block/chunk、摘录 hash、定位、抽取器、置信度）
```

这样可实现：

- 多份资料支持同一关系，而不是一个 `source_chunk_id` 绑定一条边；
- 文档更新或撤回时只使对应 evidence 失效，关系在仍有其他有效证据时继续存在；
- 区分模型/规则/人工三类来源，人工确认不会被下一次重建覆盖；
- 关系置信度按证据数量、证据新鲜度、人工确认和冲突情况计算，而不是只取历史最大值。

建议保留现有表作为兼容读模型，新增事实表后双写并逐步迁移查询。

### 2. 升级实体消歧与关系抽取

现有图谱为规则/启发式抽取，适合作为候选生成，但不适合作为正式事实层。特别是“同一分块共同出现”会产生大量 `related_to` 候选。

- 第一阶段继续使用规则抽取，但将共现关系限制在审核队列，禁止默认注入回答。
- 实体规范化采用“名称归一 + 别名词典 + 向量相似候选 + 人工确认”流水线；合并建议不能只依赖三字符前缀。
- 为不同域配置 schema/本体：通用域、制度/法规域、项目/系统域采用不同关系集合与约束。
- 每条关系应显示原句、页码/章节、抽取器版本和置信原因，校准界面支持“确认、驳回、改类型、指定别名、冻结”。
- 召回时将图谱作为 rerank/扩展信号，必须回到可检索原文 chunk；图谱不能在无有效原文时单独作答。

### 3. Wiki 改为“增量、分主题、可回放”的编译管道

当前编译每次按文档更新时间截取最多 12 个 block（`server/services/knowledge-wiki.js:324`），大专题库容易被最近一份文档的前几个 block 占满，且单 block 可截到 8,000 字，输入规模和覆盖面都不稳定。

建议的编译策略：

1. **变更检测**：按文档版本/block hash 找出新增、修改、删除的来源。
2. **主题规划**：先从目录、标签、实体和历史页面生成 topic plan；每个主题按检索相关性选证据，不按更新时间截断。
3. **覆盖配额**：限制单文档、单章节的最大占比，优先覆盖多个文档和冲突来源。
4. **令牌预算**：按模型上下文窗口严格裁剪输入，记录每个候选来源的入选/淘汰原因；不可只按字符长度切片。
5. **页面生成**：增量生成受影响页面；未受影响页面不重编译。变更摘要单独生成，方便审核。
6. **审查与发布**：页面、声明、来源三者形成可回放快照；发布时重新验证来源有效性与权限。

## 性能与体验改进

| 项目 | 观察 | 建议 |
| --- | --- | --- |
| Wiki 页面列表 | `listWikiPages` 对每行再调用 `getWikiPage`；后者还会逐来源做 ACL 查询，存在 N+1 放大 | 使用批量查询加载页面、来源、版本有效性和权限结果；详情页才加载完整来源。 |
| Wiki 搜索 | 先取至少 `limit * 8` 条候选，再逐页读取详情 | 在 SQL 层完成来源有效性和最低相关度过滤，批量 ACL 校验后一次返回。 |
| 图谱索引 | 每个 chunk 逐实体/逐关系写入，文档较大时往返次数高 | 批量 upsert 实体、mention、relation，或按 revision 使用 COPY/批量 VALUES。 |
| 图谱查询 | 词项匹配为多段 `LIKE`，并对候选在 JS 再评分 | 为规范名/别名建立 trigram、全文或 n-gram 索引；大图谱改为受限候选集+缓存。 |
| 前端图谱 | 首次选择实体同时拉取关系列表和节点图，且都是独立接口 | 增加一个聚合详情端点或在实体图响应中携带首屏关系列表；大图使用渐进展开。 |

## 推荐实施顺序

### 第一阶段：可信度止血（1–3 天）

1. 图谱检索和 Graph-RAG 注入强制过滤已删除、禁用、过期和不可访问来源。
2. Wiki 搜索增加正向匹配/最低分过滤；无匹配不注入。
3. 修正或下线未实现的 `depth=2` 语义。
4. 为以上三项加入端到端回归测试与监控计数。

### 第二阶段：可审计与增量化（1–2 个迭代）

1. 建立来源生命周期事件/outbox，统一驱动 RAG、图谱、Wiki 的失效与缓存刷新。
2. 保存 Wiki 编译输入 manifest 快照，并实现输入过期重排。
3. 将 Wiki 生成改为按主题检索、按 token 预算编排的增量任务。
4. 将图谱重建改为 revision/staging 原子切换，补充自动实体 GC 和人工实体保护。

### 第三阶段：知识质量提升（持续演进）

1. 引入“关系断言—证据”数据模型和多证据聚合置信度。
2. 建立领域本体、实体词典、审核工作队列及抽取评测集。
3. 为 Wiki 建立页面质量评测：来源精确率、声明覆盖率、冲突召回率、过期页时延与问答增益。

## 建议验收指标

- 已删除、禁用、过期或无权资料的图谱/Wiki 注入率：`0`。
- Wiki 零相关查询的页面注入率：`0`。
- 每条进入回答的图谱关系均能回溯到至少一条当前有效的原文证据：`100%`。
- Wiki 发布页的声明来源覆盖率：`100%`；人工抽检引用精确率目标：`≥ 95%`。
- 文档更新到关联 Wiki/图谱失效完成的 P95 时延：`< 5 分钟`（若为同步事件可更低）。
- 单文档图谱重建失败导致上一可用图谱丢失：`0`。
- 大专题库下 Wiki 编译输入覆盖至少两个相关来源文档的比例、页面审核通过率和问答命中增益，应纳入发布看板。
