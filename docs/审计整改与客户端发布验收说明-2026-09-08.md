# Pivot 审计整改与客户端发布验收说明

更新时间：2026-09-08

## 1. 文档目的与判定口径

本文把 `.tmp/审计结论.md`（v0.1.84、140 条审计线索）与当前工作区的整改、测试和发布约定合并为一份可执行说明。原审计结论是问题线索和历史证据，不应直接视为当前版本的最终状态；早期的“后续计划”文档同样只保留为历史背景。

本轮已对已确认且纳入范围的安全、可靠性、性能、交付和工程治理问题实施代码整改，并以自动化门禁验证。以下两项不在本轮的“彻底改造”范围内：

- 暗色主题未完整接线；
- `stealthSecret` 的业务分发模型和交互形态。

这里的“未纳入”不代表无风险：它表示必须由产品/运维策略另行决策，不能用代码审计结论替代生产环境验收。

## 2. 已完成的整改结果

### 安全与权限

- 数据库 MCP 的只读边界、共享连接表白名单、行数上限、IPv6/DNS SSRF 防护、数据分析导入统一治理和调用审计均已收口；PostgreSQL、MySQL 增加会话级只读保护。
- 登录、令牌和凭据增加访问令牌版本撤销、刷新令牌家族重放检测与设备绑定、API Key 作用域和过期时间、密码强度与 bcrypt 升级、IP/账号双维度限流。
- Agent 审批回调、非幂等恢复、终态副作用、步骤唯一性和重试路径已增加约束和回归测试。
- 桌面端渲染页面默认拒绝系统权限；敏感 JSON 使用原子写入；特权配置页面与普通页面隔离。

### 可靠性、RAG 与运行维护

- RAG 改为暂存索引后原子切换，嵌入失败不会伪造“就绪”；支持批量落库、查询向量并发去重、并行候选召回、字符偏移引用和保留引用尾部的上下文裁剪。
- Agent 队列支持持久化重试时间、指数退避和真实队列状态统计；DAG 节点同样采用受控退避，工具 checkpoint key 以运行、节点和规范输入摘要保持跨 attempt 稳定，运行元数据通过可重试 CAS 补丁保留并发审批、聊天回写等不同键的更新。
- 健康检查会真实探测数据库；SSE 增加连接上限、取消、有界背压，服务关闭时会先通知并释放 SSE 客户端、终止受跟踪的沙箱/能力工作进程、收口 HTTP 连接，再刷新写队列和关闭连接池；模型流的首响应截止、持续流无进展截止和用户取消使用同一控制器，返回可诊断错误码。
- 存储 GC 已包含上传目录孤儿文件对账；工作区清理命令默认仅预览，显式 `--yes` 才执行删除。

### 前端、交付与工程门禁

- 聊天页面脚本使用 `defer`；模块 CSS 构建为单一受校验 bundle，并清理了无引用的会话标签、旧提示词库、法规旧布局和数据分析旧面板选择器；应用、自动化、工作流、知识库、工具库和设置工作区改为同源按需模板，首屏 HTML 从约 365KB 降至约 100KB；个人、应用、Agent、工作流、知识库、工具库和设置导航统一经受控工作区模块 API；代码高亮限制语言集合并缓存；Markdown 只在安全 DOM 插入点消毒一次；ECharts 禁用字符串 formatter，并合并为单一节流 resize 监听。
- 远程桌面安装包不携带本地 Chromium；仅本地运行时档位临时注入经实际启动自检的裁剪 Chromium，移除安装、提权、PWA、WebGPU 辅助文件和未选语言。Docker 运行环境保留可实际启动的 Chromium，better-sqlite3、KaTeX 字体及桌面包内容已进行裁剪或完整性校验；Docker 与桌面标准包默认不携带未启用的 MySQL、SQL Server、MongoDB 驱动闭包。需要对应数据库 MCP 时，构建者可明确选择连接器配置。
- PostgreSQL 迁移、架构边界、异步数据库调用白名单、依赖 overrides、第三方许可证、死导出、生产直接 SQL 和 legacy 全局别名均已纳入阻断门禁；大文件基线缩小后会被强制收紧，文档渲染与技能域的摘要工具已解耦，工作流与知识库工作台入口已迁出 legacy 兼容命名空间，Agent Runtime 只导出具名领域 API。

## 3. 客户端 `config.json`、隐身模式和自动更新

### 谁需要 `config.json`

- 服务端生产环境**不需要**部署桌面客户端的 `config.json`。服务端配置来自 `.env`、数据库和全局参数。
- 桌面安装包会在 `resources/config.json` 内携带远程地址、更新源等启动配置；开发机根目录的 `config.json` 只用于本机联调，正式安装包从 `PIVOT_DISTRIBUTION_CONFIG` 提供的独立配置生成。新用户安装后无需自己创建 `config.json`。
- 外置 `config.json` 仍是可选的运维覆盖方式，可用于命令行、环境变量、安装目录旁或包内资源的配置优先级覆盖，不是普通用户的必备文件。

客户端查找顺序为：`--config` 指定路径、`PIVOT_DESKTOP_CONFIG`、`Pivot.exe` 同目录、安装包 `resources/config.json`。均不存在时才回退本地模式。

### `stealthSecret` 的当前操作约定

1. 服务端在全局参数中开启隐身模式后，服务端使用当前 `stealthSecret` 校验请求。
2. 正常发布时，桌面打包脚本从 `PIVOT_DISTRIBUTION_STEALTH_SECRET`、`PIVOT_STEALTH_SECRET` 或根目录 `.env` 读取密钥，并仅临时写入构建中的 `config.json`。打包结束后，源码工作区的 `config.json` 会恢复为不含真实密钥的状态。
3. 因此，新用户安装由**当前密钥**构建的安装包后可以直接连接，不需要手工填写密钥或另行准备配置文件。
4. 如管理员需要轮换密钥：先在全局参数页面更新服务端密钥，再把新密钥通过受控渠道发给现有客户端用户；用户在客户端“配置服务器”页面更新 `stealthSecret` 后即可继续访问。现有客户端不需要重新安装、重启系统或重新打包。

需要如实注意一个不可绕过的边界：旧安装包中预置的是旧密钥。若密钥轮换后仍让**新的**用户安装旧包，则该新用户必须在客户端输入新密钥一次；若要维持“新安装即无感连接”，发布给新用户的安装包必须采用新密钥构建。这是离线预置密钥的必然约束，不是客户端重启或服务端重装问题。

源代码配置中的 `stealthSecret` 为空本身不会影响打包后的连接；但构建发布包时必须由上述环境变量或 `.env` 提供非空密钥，脚本会在缺失时失败，避免生成无法连接隐身服务的安装包。

正式 Windows 发布还必须设置 `PIVOT_WINDOWS_UPDATE_PUBLISHER` 与 Electron Builder 代码签名凭据（`CSC_LINK`、`WIN_CSC_LINK`、`CSC_NAME` 或 `WIN_CSC_NAME`）。打包过程会把分发配置、签名发布者和密钥临时写入构建输入，结束时恢复开发机文件；若进程被强制中断，下次构建会自动恢复上次保存的 `package.json` 与 `config.json`。

### 自动更新

- 自动更新依赖客户端已有的更新源配置，不依赖用户在终端另行准备 `config.json`。
- 仅当业务 `remoteUrl` 本身为 HTTPS 时可同站推导 `/downloads/`；业务服务为 HTTP 时必须显式提供独立 HTTPS 更新 URL。发布目录需同时提供安装器、`.blockmap`、`latest.yml` 和 `SHA256SUMS.txt`。
- 正式发布和客户端配置都会拒绝 `allowInsecureHttp=true` 及任何 HTTP 更新 URL。开发机可通过 HTTP 访问本机业务服务，但默认关闭自动更新。业务 HTTP 访问本身不等于允许 HTTP 更新。
- Windows 正式更新包还必须提供 Authenticode 签名发布者和签名凭据；客户端会校验 `app-update.yml` 中的发布者、拒绝 web installer 与版本降级。

## 4. 生产发布前必须完成的外部验收

以下项目无法仅靠本工作区测试证明，必须由拥有生产环境权限的人员执行：

1. 在生产 PostgreSQL 核验迁移记录、表结构和关键索引；确认 `DATABASE_URL` 可连接且格式正确。数据库密码可继续使用现有值，密码轮换按运维策略执行并同步更新 `.env`；程序不会替运维直接修改数据库账户。
2. 检查 `JWT_SECRET` 与 `DATA_ENCRYPTION_KEY` 分离且均为高强度值；生产启动会拒绝二者复用并校验 `DATABASE_URL` 格式，但不会因现有 PostgreSQL 密码复杂度不足阻断启动。
3. 使用普通账户和管理员账户验证权限矩阵、数据库共享连接、审批回调和审计日志。
4. 在实际内网验证远程地址、隐身模式密钥、首次安装、客户端登录、SSE、文件上传和知识库索引。
5. 在实际 HTTPS 更新源验证 `latest.yml`、安装器、blockmap、来源白名单、Authenticode 发布者和升级后的版本号；确认新版本号高于已安装版本。
6. 在发布前保留数据库与上传文件备份，并执行完整测试与安装包运行时校验。

## 6. 发布决策摘要

- 新用户：安装由受控 `PIVOT_DISTRIBUTION_CONFIG` 构建的客户端即可正常远程连接、登录和自动检查更新，无需手工创建 `config.json`。
- 日常密钥轮换：全局参数更新服务端密钥，向现有用户分发新值并由其在客户端更新；无需重装客户端或重启系统。
- 后续新用户：应获得含当前密钥的安装包；如果继续分发旧包，则需首次手工输入新密钥。
- 服务端：只需维护服务端 `.env`、数据库、全局参数和下载发布目录；无需放置桌面端 `config.json`。
- 未纳入项：暗色主题与隐身密钥分发模型的根本变更，均需单独立项后再改变现有行为。
