# Pivot Windows App 远程模式部署说明

正式远程安装包会内嵌由受控分发配置生成的 `resources/config.json`。仓库根目录 `config.json` 仅供开发机联调，默认指向本机服务，正式构建绝不会复用它。普通用户下载安装后即可连接、登录和自动检查更新，**不需要自行创建或在终端准备 `config.json`**。外置配置仍保留为 IT 的可选覆盖手段，用于 UAT、故障切换或受控运维，不是日常分发前置条件。

签名证书和私钥由发布端（受控 Windows 构建机）统一保管，构建时完成签名并将公开的证书指纹内嵌到安装包；内网服务器只分发验收通过的更新文件。普通用户不需要导入证书、填写指纹或管理签名，只需首次安装和在更新提示中确认重启。私钥不得进入客户端安装包或公开下载目录。

## 分发文件

- `Pivot Setup <version>.exe`：由 `npm run dist:win` 生成的 Windows 安装器。
- 安装器内的 `resources/config.json`：由 `PIVOT_DISTRIBUTION_CONFIG` 在构建时注入的真实启动配置；普通用户无需另行处理。
- 外置 `config.json`（可选）：IT 可放到 `Pivot.exe` 同目录，或通过 `--config <path>` 指定，以覆盖内置配置。
- `config.example.json`：配置模板，随包放入 `resources`，仅供受控运维复制修改，不会自动作为真实配置加载。

桌面构建会排除 `pdf-parse`、`pdfjs-dist` 和 `pdf-lib` 的源码映射文件，保留 PDF 运行代码、资源及本地模式所需文件；远程连接、本机授权和分发配置加载规则不受影响。包内涉及这些依赖的错误堆栈可能无法还原到原始源码位置；排障时可使用对应版本的开发依赖和源码映射。

## 配置加载优先级

桌面端按下面顺序查找配置，找到第一份存在的 `config.json` 后停止。前 3 项都是可选的运维覆盖；常规安装会使用第 4 项内置配置：

1. 命令行：`Pivot.exe --config C:\Pivot\config.json`
2. 环境变量：`PIVOT_DESKTOP_CONFIG=C:\Pivot\config.json`
3. `Pivot.exe` 同目录下的 `config.json`
4. 安装包 `resources/config.json`

仅当以上位置都没有配置文件时，应用才回退本地模式默认配置。

## 内网 HTTP 配置示例

适用于无互联网、无公网 IPv4/IPv6、无域名、无 HTTPS 证书、只能通过局域网 HTTP 访问 Pivot 的生产环境。复制为 `config.json` 后，把 `remoteUrl` 改成客户端实际能够访问的局域网地址。

Pivot 不要求公网 IP、DNS 域名或证书，但远程模式必须存在一种可达地址：私有 IPv4（如 `http://192.168.10.20:3000/`）、IPv6 字面量（如 `http://[fd00::20]:3000/`）或局域网可解析的操作系统主机名（如 `http://PIVOT-SERVER:3000/`）。如果网络中确实既没有任何 IP 地址，也没有可解析的主机名，客户端与服务器之间无法建立 HTTP 连接，应使用桌面本地模式或先建立局域网寻址。

```json
{
  "mode": "remote",
  "environmentName": "Production LAN",
  "remoteUrl": "http://192.168.10.20:3000/",
  "partition": "persist:pivot-production",
  "windowTitle": "智枢 Pivot",
  "allowExternalOpen": false,
  "lockServerConfig": true,
  "allowedExternalOrigins": [],
  "autoUpdate": {
    "enabled": false,
    "path": "/downloads/",
    "url": "",
    "checkOnStart": true,
    "checkIntervalMinutes": 30,
    "autoDownload": true,
    "allowPrerelease": false,
    "allowedOrigins": [],
    "installOnQuit": false
  }
}
```

## 字段说明

- `mode`：`remote` 连接已有 Pivot 服务；`local` 启动安装包内置的本地服务。
- `environmentName`：显示在窗口标题中，建议填写 `Production LAN`、`UAT`、`Test` 等环境名。
- `remoteUrl`：远程模式必填，只允许 `http` 或 `https` URL。
- `lockServerConfig`：企业统一下发推荐设为 `true`。开启后锁定客户端连接参数，隐藏普通用户界面的服务器连接修改入口，杜绝内网端点与凭据泄露及误改。
- `partition`：Electron 会话分区。建议每个环境使用不同值，隔离 Cookie 和缓存。
- `windowTitle`：窗口标题前缀。
- `allowExternalOpen`：默认 `false`。只有同时配置 `allowedExternalOrigins` 时才允许在系统浏览器打开外链。
- `allowedExternalOrigins`：受信任外部站点的完整 Origin 列表，例如 `["https://docs.example.com"]`。不得填写路径、查询参数、账号信息或通配符。

## 自动升级配置

无互联网、无公网 CA 证书的局域网可使用当前默认内网通道 `npm run dist:win`（等同 `npm run dist:win:intranet`），由发布端使用固定自签名证书签名并内嵌 SHA-256 指纹。客户端通过内网 HTTP 或 HTTPS 下载更新后自动核对签名发布者和指纹，无需用户在 Windows 证书库中手工建立信任。内网 HTTP 更新须显式启用 `autoUpdate.allowInsecureHttp=true` 并配置更新源白名单。若只通过离线介质分发、不启用自动更新，可使用 `npm run dist:win:offline`。

`autoUpdate` 控制 App 自动升级。默认情况下升级目录可与业务服务器同站复用 `/downloads/`；如填写 `autoUpdate.url`，则升级服务器地址可以与业务服务器地址相互独立。

更新器使用独立网络会话，现与业务会话共用动态隐身签名策略；每个同源更新请求按当前连接重新生成 v1/v2 头。跨源更新地址不会自动复用业务隐身密钥，独立更新源应按其自身访问规则部署。切换本地模式且没有显式独立更新 URL 时，有效配置停用更新检查，避免空地址导致配置加载失败；切回远程后恢复原始策略。此次修复保留现有远程配置、退出安装和安装向导行为，不替换生产更新文件。

- `enabled`：是否启用自动升级。正式启用时改成 `true`。
- `path`：同站更新目录，默认 `/downloads/`。当 `url` 为空且自动升级启用时，会基于 `remoteUrl` 推导更新源。
- `url`：独立更新文件目录。为空时使用 `path`；填写时会覆盖同站推导结果，程序会自动补齐目录末尾的 `/`。
- `allowedOrigins`：允许的更新源 origin，例如 `["https://updates.example.com"]` 或 `["http://192.168.10.20:3000"]`。更新源必须与其中一项完全同源；HTTP 还须启用 `allowInsecureHttp`。
- `checkOnStart`：启动后自动检查更新。
- `checkIntervalMinutes`：运行期间隔自动轮询检查更新（分钟），默认 30 分钟。设为 0 时关闭定时轮询。
- `autoDownload`：发现新版本后自动下载。
- `allowPrerelease`：是否允许预发布版本。
- `certificateSha256`：由发布端计算并内嵌的签名证书 SHA-256 指纹；自签名或 `Pivot Local Dev` 更新必须配置，普通用户无需填写或导入证书。构建环境变量 `PIVOT_UPDATE_CERT_SHA256` 可提供该指纹；使用证书库 SHA-1 选择器时构建脚本可自动读取。内网通道允许现有校验策略中的 Authenticode 状态 1/6 继续进入发布者、文件路径和指纹核验，其他无效签名状态仍会拒绝。
- `allowUntrustedRoot`：内网通道由构建脚本连同证书指纹注入，允许客户端按固定指纹校验自签名更新；该字段不会修改 Windows 证书库或企业应用控制策略。
- `allowInsecureHttp`：默认为 `false`，更新源应使用 HTTPS；确需内网 HTTP 时须在受控分发配置中显式设为 `true`。
- `installOnQuit`：是否在用户退出 App 时自动安装。生产环境建议设为 `false`，由用户在“更新已下载”提示中点击“重启并安装”后再覆盖安装。

下载完成后，App 会提示用户选择“重启并安装”或“稍后”。本版本默认不会因用户退出客户端而自动安装；签名和指纹校验由客户端自动执行。后续版本必须继续使用已安装客户端认可的证书和发布者；同名新证书的指纹也不同，不能替代原证书。构建机迁移、证书备份和换证迁移由发布维护者统一处理，不能仅替换服务端安装器和新包内的指纹来更新旧客户端的信任。

首次安装能否运行仍受 Windows 企业应用控制策略约束。若目标环境拦截自签名程序，应由管理员集中部署信任或应用放行策略，普通用户无需处理证书；应用内的指纹校验不会绕过系统执行策略。

隐身模式的新客户端同时发送与目标 Host 绑定的 v2 签名和旧版兼容签名；新服务优先验证 v2。反向代理必须保留客户端访问的 Host（含非默认端口）。确认旧客户端已升级后，可在服务端设置 `PIVOT_STEALTH_ALLOW_LEGACY=false` 禁止旧客户端签名；若需回滚旧客户端，应恢复该开关。时间窗口和 Host 绑定不替代 HTTPS，也不提供一次性防重放保证。

## 自动升级发布流程

每次发布新版本时：

1. 准备未纳入 Git 的生产客户端配置，例如 `C:\secure\pivot-production-client.json`。其中写入生产 `remoteUrl`、更新地址/来源白名单等非密钥配置；不要在文件中写入 `stealthSecret`。推荐使用受信任 HTTPS；确需同站 HTTP 更新时还须显式设置 `autoUpdate.allowInsecureHttp=true`。
2. 更新 `CHANGELOG.md` 顶部版本号，并执行 `node scripts/sync_version.js` 同步 `package.json` 和锁文件。
3. 发布维护者在受控 Windows 构建机设置 `PIVOT_DISTRIBUTION_CONFIG`、`PIVOT_DISTRIBUTION_STEALTH_SECRET` 和签名资料。当前默认内网通道可在首次发布时自动创建 `Pivot Local Dev` 自签名证书，并将发布者和 SHA-256 指纹注入安装包；后续发布须复用原证书及私钥。也可通过 `WIN_CSC_LINK`/`CSC_LINK` 指定固定 PFX，或通过 `PIVOT_WINDOWS_CERTIFICATE_SHA1`/`PIVOT_WINDOWS_CERTIFICATE_SUBJECT` 选择既有证书，并提供对应的 `PIVOT_WINDOWS_UPDATE_PUBLISHER`；内网通道使用 PFX 或 Subject 选择器时还须由发布端配置 `PIVOT_UPDATE_CERT_SHA256`。先执行 `npm run preflight:win-update`，再执行 `npm run dist:win`。构建完成后会验证安装器和 `Pivot.exe` 的 Authenticode 签名、发布者及配置的指纹，任一失败都不会复制到 `downloads/`。普通用户不参与这些步骤。
4. 打包脚本将内嵌配置和构建覆盖写入系统临时 staging 目录，不改写工作区的 `config.json` 与 `package.json`；正常结束时清理 staging。
5. 打包脚本会自动把下面文件复制到 `downloads/`：
   - `Pivot Setup <version>.exe`
   - `Pivot Setup <version>.exe.blockmap`
   - `latest.yml`
   - `Pivot-Setup.exe`（网页登录页下载入口）
   - `SHA256SUMS.txt`（上述发布文件的 SHA-256 完整性清单）
6. 如果生产环境通过 Docker volume 挂载 `downloads/`，同步或替换该目录文件即可发布新客户端。
7. 已安装客户端启动后会检查 `latest.yml`，发现新版本后自动下载并提示安装。

### 固定构建通道

不要再直接调用 `node scripts/package_desktop.js`，也不要把开发构建产物手工复制到生产 `downloads/`。只使用下列通道：

| 目的 | 命令 | 自动更新 | 是否写入 `downloads/` |
| --- | --- | --- | --- |
| 正式自动更新发布 | `npm run preflight:win-update` 后执行 `npm run dist:win` | 启用 | 是；安装器/blockmap 先发布，`latest.yml` 最后原子替换 |
| 正式离线分发 | `npm run dist:win:offline` | 强制关闭 | 否 |
| 本机开发或冒烟 | `npm run dist:win:dev` | 强制关闭 | 否 |

`npm run dist:win` 与 `npm run dist:win:intranet` 当前均使用内网自动更新发布通道，要求分发配置中 `autoUpdate.enabled=true`、更新源 Origin 进入 `allowedOrigins`、更新地址不是 `localhost`/回环地址，并使用固定签名身份与内嵌证书指纹。打包后会核验 `latest.yml` 指向的安装器大小/SHA-512、blockmap、客户端内嵌 `config.json` 和 `app-update.yml` 的 feed 与发布者绑定。任何一项失败都会阻止更新元数据发布。

## 安装包运行时档位

- **远程档位（默认）**：分发配置为 `mode: "remote"` 时默认使用。安装包不再携带本地 Agent Chromium 运行时，减少约数百 MB 的安装和更新传输；远程用户的 Agent 浏览器能力由服务端提供，本机浏览器连接器仍使用用户显式授权的浏览器，不依赖内置 Chromium。
- **本地档位**：分发配置为 `mode: "local"` 时自动启用，构建会携带并启动自检裁剪后的 Chromium 运行时。若远程配置的安装包仍需保留用户切换到本地服务的完整能力，构建前设置 `PIVOT_DESKTOP_RUNTIME_PROFILE=local`。
- 不能为 `mode: "local"` 的配置强制指定 `PIVOT_DESKTOP_RUNTIME_PROFILE=remote`；构建会失败，避免生成缺少本地浏览器运行时的错误安装包。

## 换环境方式

从 UAT 切换到生产时，只需要把用户机器上的 `config.json` 替换为生产配置。安装包和应用本体不用重新分发。

## 异常页与重试

远程服务不可达、VPN 未连接或证书/网络异常时，应用会显示内置错误页，页面包含环境名、目标地址和“重试”按钮。用户恢复网络后可直接重试，不会看到原始 Chromium 错误页。

### 0.7.74 客户端下载更新后没有安装提示

升级前的验签由正在运行的旧客户端执行，新安装包内的更新器尚未运行；回退新包中的验签逻辑不会改变这一次升级。0.7.74 已支持内网自签名状态 1/6，需结合旧客户端的真实状态判断阻断环节。

左上角 Pivot 菜单如果显示“重启并安装更新／已就绪”，表示安装包已下载并通过旧客户端的校验，保存工作后可直接点击该项安装，无需处理证书。服务端页面会分别提示发现更新和下载完成；刷新页面时也会提示旧客户端中已就绪的更新，避免原生提示未显示时找不到安装入口。

若菜单仍停在下载中或显示错误，则需要读取旧客户端返回的更新错误，不能把下载进度达到 100% 当作已通过校验。仅当点击安装后出现安装器错误，才继续检查安装目录进程、权限或系统应用控制。

如果直接运行 0.7.148 安装器也提示“无法核对安装目录的运行状态，已停止安装”，故障来自该安装器依赖的 CIM/WMI 进程查询，而非旧客户端的更新签名。修复后的安装器直接使用 Windows 原生进程快照和完整映像路径查询，不依赖 PowerShell 模块；检测到目标目录进程时仍会阻止覆盖，不会终止其它目录中的同名客户端。自动更新以 `--updated` 启动时，最多等待十秒让旧客户端自然退出。

此类修复必须重新生成安装器并同步对应 blockmap、`latest.yml` 和校验清单，单独更新服务端页面或回退新客户端的验签代码不能修复已经生成的旧安装器。若使用同版本修复安装器，发布维护者须保证服务器上的文件与新元数据一致，并让旧客户端重新启动更新检查，以免继续运行之前缓存的故障安装器。

## IT 注意事项

生产旧版为 0.7.76 且直接安装 0.7.155 卡住时，下载进度 100% 不代表验签完成。修复源码会将该阶段显示为“正在校验更新”；旧版已经固化的严格验签不能通过服务端页面变更解除。安装器显示阶段详情，并将进程检查、旧版本处理和安装完成等阶段写入 `%TEMP%\PivotInstaller-<进程号>.log`。维护者可运行 `scripts/bat/收集客户端安装诊断.bat` 采集只读报告；它不会终止进程、修改证书或读取完整配置中的凭据。具体结论见[0.7.76 后续排查记录](reports/windows-client-076-followup-20261113.md)。

- 自动更新支持 HTTPS 与局域网/专网 HTTP；内网自签名包使用发布端统一维护的固定证书和客户端内嵌指纹，证书私钥不得随更新文件分发。目标 Windows 的企业应用控制由管理员集中配置，不能要求普通用户逐台处理证书。
- 在纯 HTTP 环境中通过防火墙只向受控网段开放服务端口，并保持 `COOKIE_SECURE=false`；不要把该监听端口直接暴露到公网。
- `allowedOrigins` 建议与更新源的协议、主机和端口一致；若未显式配置 `autoUpdate.url`，客户端会在连接服务器时自动将当前业务服务 Origin 纳入同源更新允许范围，自适应服务器 IP/端口变更。
- 同一环境保持 `partition` 稳定，便于保留登录状态。
- 测试和生产使用不同 `partition`，避免 Cookie 或缓存串环境。
