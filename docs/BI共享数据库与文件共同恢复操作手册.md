# BI 共享数据库与文件共同恢复操作手册

本文对应建设方案第 23 节和 BI-13。工具按整个 PostgreSQL 集群、项目共享 `data`、`uploads`、Artifact/CAS、文档处理、分析版本、Agent 大对象/运行包/技能目录建立恢复单位。独立安全日志不随旧业务备份回退，按[安全恢复授权核对手册](BI安全日志与恢复授权核对.md)重放和签认。

本地演练属于工程验证；目标环境的独立故障域、100 GiB、存储加密、Linux 持久性和实际生产 RPO/RTO 仍需单独认证，不能由 Windows 临时目录结果代替。

## 身份、目录与部署准备

使用独立数据库运维身份运行 `scripts/bi_physical_backup.js`。该身份需要物理复制、查看集群控制信息、创建有名恢复点、切换 WAL、核对/登记恢复点、保护对象引用以及超时终止自身备份会话的权限。在线应用身份必须与之分离：不能是超级用户，不能创建角色/数据库、修改共享 Schema/表或删除备份。迁移由独立迁移身份在维护窗口执行，随后再用受限身份运行应用。

恢复单位要求专属应用集群：拒绝其他业务数据库、含持久业务表的 `postgres` 管理库、外部表空间、外部或无日志关系。物理 PITR 不能选择性恢复部分数据库/表。机制依据 [PostgreSQL 连续归档与 PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)及 [pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html)；逻辑 `pg_dump` 继续作为既有离线维护工具，不能替代这条连续恢复链。

独立运维 JSON 配置必须使用绝对路径、私有权限、真实目录，禁止符号链接；不要放入应用共享数据、备份对象、明文暂存或源代码仓库。配置包含：

| 字段 | 合同 |
| --- | --- |
| `clusterId` | `pg_control_system()` 的数据库系统标识，不能从另一集群复制 |
| `operatorConnection`、`applicationRole`、`schema`、`bin` | 独立运维连接、在线应用角色、应用 Schema、对应主版本 PostgreSQL 工具目录；连接凭据只保存在私有配置/运维环境，不进入子命令参数 |
| `primaryDataDirectory`、`projectRoot` | 实际 PGDATA、部署项目逻辑根路径；所有路径恢复时保持合同一致 |
| `environment` | 本部署的 `DATA_DIR`、上传/CAS/文档/分析/Agent 外部目录，以及独立安全日志目录、密钥和签认公钥路径 |
| `backupRoot` | 独立备份对象、完整基础备份、WAL 与共同恢复点目录 |
| `escrowRoot` | 与主数据、备份及暂存分离的配置托管目录 |
| `keyFile` | 独立三十二字节随机密钥，十六进制编码；禁止位于主数据、备份、配置托管或暂存目录 |
| `stagingRoot`、`plaintextStagingPolicy` | 私有明文物理备份暂存目录及组织批准的磁盘加密/访问策略；文字声明不构成磁盘加密认证 |
| `configurationFiles` | 必须包含项目 `.env`、`config.json`，并明确列出部署另行引用的必要配置、TLS/应用密钥等文件；不得包含备份加密密钥本身 |

Linux 独立目录要求 `0700`、密钥和运维配置 `0600`。备份与托管对象使用流式 AES-256-GCM，并绑定集群、用途和对象摘要；先 fsync 完整临时文件，再原子链接且不覆盖已有对象。Windows 仅记录文件 fsync 功能验证，不能声称支持 Linux 目录持久认证。

生产应限制备份存储的独立身份与删除权限，密钥另行离线托管；同一磁盘的不同目录不构成独立故障域。传输使用组织批准的 TLS/加密通道。主机和明文暂存所在卷仍须落实组织静态加密策略，加密备份文件不能替代主存储加密。

## 连续归档和日常执行

数据库启用 `wal_level=replica` 或更高、`archive_mode=on`、`full_page_writes=on`、`fsync=on` 与持久提交。`archive_command` 使用固定 Node/脚本/私有配置路径，只接收 PostgreSQL 展开的 `%p`、`%f`：

```text
"/usr/local/bin/node" "/opt/pivot/scripts/bi_physical_backup.js" --config "/etc/pivot/physical-operator.json" --archive "%p" --name "%f"
```

先由数据库运维身份安装并验证归档命令，再建立完整基础备份。归档限制为登记 PGDATA 的 `pg_wal` 中合法段/历史/备份文件；重复归档必须验证既有密文和明文摘要相同，不能覆盖。失败非零退出，PostgreSQL 按原归档机制重试。监测 `pg_stat_archiver`、WAL 容量和备份存储健康，不能只依赖业务 HTTP 探针。

```text
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json --base
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json --point --base-id base_<UUID>
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json --tick
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json --tick --prune
```

将 `--tick` 接入独立运维调度器，每分钟执行一次；工具串行化调度会话，每日建立完整物理备份，每五分钟尝试共同恢复点。`--prune` 每日执行一次。调度身份和失败告警不得依赖被备份主机的唯一磁盘。未接线的调度器/值班人员不计为运营验收通过。

完整备份使用 `pg_basebackup` 的物理全集群备份和流式 WAL，执行 `pg_verifybackup`，再逐文件加密、fsync 和独立校验；不使用 `--no-sync`。明文暂存只清理本次生成、已核对边界的随机目录。磁盘不足、文件变化、校验失败或工具超时均失败，不能留下已完成标记。

## 共同恢复点合同

1. 在屏障之外确认安全日志，先建立进行中的恢复记录并固定就绪对象，防止复制期间被回收。固定外键等待发生在排他屏障之外。完整预复制共享文件和配置，记录摘要、长度和文件身份。数据根目录与七类既有备份目录合并去重，不遗漏嵌套目录。只排除分析/文档处理的 `tmp` 以及两个 CAS 字节层的 `.tmp-write` 暂存目录，具体绝对路径写入清单；恢复后按任务租约重建未完成输出。就绪数据库引用如果指向这些临时目录仍会被拒绝，不能借排除目录忽略必须对象。文件复制与校验使用固定四路并发并在失败时等待正在处理的文件结束。
2. 对全部共享应用表安装语句级写入保护，直接 SQL、批量更新和截断也先取得统一共享锁。运维尝试短期排他锁，等待已开始的引用写入提交；遗漏新表或保护失效时拒绝恢复点。
3. 在最长五秒预算中复核文件/配置签名和数据库必须引用，登记恢复点与 BI 对象保留引用，提交后由独立运维身份创建有名恢复点并取得 WAL 位置。此期间不复制文件、不运行另一个连接的日志泵，不持有资源行锁后再反向等待屏障。独立看护会话在超时后终止备份会话，释放写入保护；超时结果不可使用。
4. 释放屏障后切换并等待必需 WAL 全链、逐一核对备份对象、配置托管及独立安全高水位。完成后才发布不可覆盖的加密恢复点清单，并确认主库目录状态。进程若在独立清单完成和主库确认之间中断，返回“主库目录确认待重试”，保留进行中的目录与对象引用，下次调度或 `--confirm-point` 按同一清单重新核对确认；不能改成失败后删除保留引用。

数据库引用核对覆盖 BI 就绪对象/来源、CAS、有效附件、文档文件/页面/输出、知识来源/版本、法规来源、分析产物/物化及旧查询结果。就绪元数据指向缺失文件，或已登记摘要/长度不符时，不允许建立可恢复点。新增模块/文件引用必须扩展该合同和实际还原测试。

恢复点超过十五分钟或缺失时既有 BI 运营监测告警。未完成点保留失败状态；复制中的文件、只有 SQL 成功的行、缺 WAL 的目录都不能计入可恢复年龄。

## 保留和清理

至少保留七天连续 WAL 与全部五分钟完成点；三十天内每天保留一个完成共同点、完整日备份及各点所依赖的所有基础备份/对象/WAL/配置。始终保留最后一个完成点，即使备份长时间失败，也不因超过年龄删除唯一恢复基线。

清理前验证所有仍保留的恢复链、对象和安全锚点，缺项时停止清理。连续归档七天内的段即使尚未被五分钟目录引用也保留；孤立对象保留至少一天宽限，避免删除预复制中的数据。清理仅处理独立目录中登记格式的常规文件，边界、真实路径和符号链接均复核，不递归删除任意业务目录。

## 主机和本地存储丢失后的还原

1. 隔离旧主机/旧 Worker，保持外部访问关闭。保留独立备份、配置托管、密钥、当前身份授权源与安全日志；确认旧执行器不再运行。
2. 选择最后一个完整点并验证。目标必须是新 PGDATA、独立端口及明确为空的共享逻辑挂载，禁止覆盖现存集群或任意重定位其他模块记录的路径。
3. 使用下列命令准备物理还原，工具先完整核对基础备份、WAL、对象、配置和安全锚点，然后写入新目录并再次运行 `pg_verifybackup`。

```text
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json --verify-point point_<UUID>
node scripts/bi_physical_backup.js --config /etc/pivot/physical-operator.json --restore point_<UUID> --destination /srv/pivot-recovery/pgdata
```

4. 新集群使用工具生成的本机隔离配置启动，回放到登记的有名恢复点并提升，不加载原配置中的外部 include、复制连接、归档命令或预加载副作用。确认实际达到目标、数据库退出恢复态且时间线已提升；完整部署配置由运维核对后启用，不能直接把隔离配置公开给生产用户。
5. 数据库系统标识或时间线与原已接受值不同会强制关闭 BI 读取，关闭功能开关或更换客户端也不能绕过。已启用独立安全日志的旧库首次增加谱系记录时，也要求一次当前授权核对，不能假定它必然是未回退的原库。按安全手册重放当前日志、删除墓碑、旧凭据/任务代次失效，并核对当前身份/授权签认。活跃账号仍按当前密码验证器指纹核对，包括禁用交互登录的专用账号；缺失密钥或当前授权证明时保持关闭。
6. 核对所有清单和文件、固定来源/指标、历史报告、重算查询、视图/仪表盘、共享撤权、删除账号，以及其他应用的会话/附件/输出。处理未完成导入/输出和可重排任务；通知、刷新和其他外部效果不盲目重放。
7. 完成当前签认及固定查询核对后，用新的运维连接/PGDATA 配置执行 `--confirm-point point_<UUID>`，确认恢复库内的共同点目录；工具仍完整复验独立清单和安全状态。新时间线上的首次调度会强制新建完整基础备份，不能继续套用原时间线的当日备份。
8. 记录故障时刻、共同点、源/目标构建、对象数量/字节、实际数据损失、RPO/RTO、失败步骤和未恢复项。每月随机点完整还原/查询，每季度及数据库/存储/执行架构重大变化后重做主机与本地存储全失演练；只验证密文可解密不能替代这些演练。

## 本地验证命令与证据边界

```text
node --test tests/bi-modeling-backup-files.test.js
node --test tests/bi-modeling-physical-restore.test.js
```

物理专项创建持久化随机 PostgreSQL 集群和独立临时目录，不控制已有业务集群。它实际建立基础备份、连续加密 WAL、短屏障和共享点，删除本次演练的 PGDATA 与所有共享源，再在新 PGDATA/新端口还原，重放独立当前撤权并核对固定结果/重算。缺 WAL、密钥、对象和当前授权的检查均须失败；任何一步失败时，整项不记为通过。
