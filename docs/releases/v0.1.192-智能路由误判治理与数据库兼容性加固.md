# v0.1.192 智能路由误判治理与数据库兼容性加固

发布日期：2026-09-29

发布范围：智能语义路由算法、MCP 工具意图识别边界、大模型工具上下文注入控制、长期记忆任务状态管理、PostgreSQL 数据库类型兼容性。

---

## 1. 背景与核心问题

在智能路由系统投产与内网环境使用过程中，暴露出两项影响对话体验与稳定性的核心痛点：

1. **日常公文写作与代码提问频繁误弹工具授权**：
   - 当用户提出普通的自然语言任务（例如“帮我写一篇述职报告”、“写一份本周工作周报”、“请用表格对比两者的优缺点”、“请写一个查询用户表的SQL”）时，系统频繁下发 `candidate_only` 状态，前端界面提示：*“可以使用工具处理这条请求。授权后会自动继续，无需重新发送”*，强制用户在“允许并继续”与“直接回答”之间做出选择。
   - 用户选择授权并继续处理后，大模型又因为缺乏真正的数据库连接或本地文件参数而显示不需要调用工具，带来严重的交互干扰。

2. **消息回退与删除时触发 PostgreSQL 42804 错误**：
   - 用户在撤销消息、授权回退或删除对话时，服务端接口 `DELETE /api/messages/:id` 报错：
     `{"errorId":"...","code":"42804","message":"COALESCE types text and jsonb cannot be matched","url":"/api/messages/7135","method":"DELETE"}`
   - 导致前端状态未能正确清理，消息处理流程受阻。

针对上述现象，本版本深入底层代码、算法逻辑与数据库执行计划，进行了全面、彻底的排查、算法重构与数据兼容性加固。

---

## 2. 深入排查与根因分析

经过系统级代码审计，定位到以下关键根因：

1. **词法匹配算法存在短词膨胀缺陷 (`server/services/semantic-router.js`)**：
   - 原 `lexicalSimilarity` 算法采用 `shared / Math.min(leftTokens.size, rightTokens.size)`；
   - 当用户提问较短时（例如仅包含“报告”两个字），分词后其特征集合极小，与报表工具描述中的“报告”二字重叠，直接导致除数等于重叠数，计算结果虚高为 `1.0`（满分），强行击穿了工具匹配门槛。

2. **工具规则基础权重赋予过宽**：
   - 在 `toolRuleScore` 中，此前对带有潜在意图的提问通用赋予 `0.35` 分数，导致许多边界语义在没有精准工具需求时也被抬升到了候选筛选线。

3. **意图识别正则缺乏负向排查分支 (`server/services/chat-mcp-intent.js`)**：
   - 报表工具关键词匹配直接包含了“报告”、“文件”，未将“工作周报”、“述职报告”、“调研报告框架”等纯文本创作与真正的“本地报表文件目录扫描”区分开；
   - 数据库工具匹配包含了“表”字，未将 Markdown 文本表格对比、填表等自然语义与数据库真实数据表区分开；
   - 数据操作关键词包含了 `sql`、`select` 等，未将“请帮我写一段SQL代码”这种由 LLM 生成代码的自然提问，与真正向数据库执行 SQL 查询区分开。

4. **MCP 引导上下文过度注入 (`server/services/chat-mcp-context.js`)**：
   - 当意图未完全命中但规划器未完全清空时，曾存在注入 `PIVOT_MCP_CONTEXT_BEGIN` 提示词的现象，导致大模型在接收到系统提示词后误以为存在外部工具而试图发起调用。

5. **PostgreSQL JSONB 类型不匹配 (`server/services/long-term-memory/memory-jobs.js`)**：
   - 在 `cancelMemoryExtractionJobs` 中，使用了 `COALESCE(message_ids, '[]'::jsonb)`；
   - PostgreSQL 严格遵循强类型约束，当 `message_ids` 列在历史迁移中为 `text` 类型或数据为字符串字面量时，PostgreSQL 无法隐式将 `text` 与 `jsonb` 进行 `COALESCE` 统一，从而抛出 SQLCODE `42804`。

## 3. 详细解决方案与架构优化

### 3.1 词法相似度算法重构
在 [semantic-router.js](file:///e:/pivot/server/services/semantic-router.js) 中重写了 `lexicalSimilarity` 算法：
```javascript
function lexicalSimilarity(left = '', right = '') {
    const leftTokens = lexicalTokens(left);
    const rightTokens = lexicalTokens(right);
    if (!leftTokens.size || !rightTokens.size) return 0;
    let shared = 0;
    for (const token of leftTokens) {
        if (rightTokens.has(token)) shared += 1;
    }
    const promptCoverage = shared / leftTokens.size;
    const dice = (2 * shared) / (leftTokens.size + rightTokens.size);
    return Math.min(promptCoverage, dice * 4);
}
```
通过综合提示词覆盖率（`promptCoverage`）与 Dice 距离，引入对双方文本长度差异的惩罚，从数学层面彻底消除了短词命中引发的计算失真。

### 3.2 意图识别建立负向过滤机制
在 [chat-mcp-intent.js](file:///e:/pivot/server/services/chat-mcp-intent.js) 中强化意图识别准则：
- **公文与报告写作过滤**：显式排除以“写/撰写/起草/润色/修改/翻译/总结”开头的周报、月报、述职报告、方案提纲等自然公文创作需求；
- **代码生成过滤**：显式排除“请帮我写/编写/生成一段SQL/代码/语句/demo”等编程咨询需求，只有真正指明要“查询数据库/数据表”时才进入工具候选；
- **表格语义分离**：排除普通文本对比表格（如“用表格对比”、“填表”），仅识别明确指向数据库表名、表字段或统计聚合的物理表查询需求；
- **报表文件目录收敛**：`detectReportFileInventoryIntent` 严格要求提示词明确指向本地文件路径、文件扩展名（`.xlsx/.csv/.pdf`）或报表目录查看，普通文字报告一律放行给模型直接回答。

### 3.3 工具规则加分收口与上下文净化
- 在 `toolRuleScore` 中，仅在提问中显式出现“工具库/能力库/mcp/工具调用”时才赋予基线权重；
- 在 [chat-mcp-context.js](file:///e:/pivot/server/services/chat-mcp-context.js) 中，当用户未开启工具且规划器为 `none` 时，直接返回空字符串，绝不向对话提示词追加 `PIVOT_MCP_CONTEXT_BEGIN`。

### 3.4 数据库强类型兼容性加固
在 [memory-jobs.js](file:///e:/pivot/server/services/long-term-memory/memory-jobs.js) 中彻底重构相关查询逻辑：
```sql
EXISTS (
    SELECT 1
    FROM jsonb_array_elements_text(
        CASE
            WHEN message_ids IS NULL THEN '[]'::jsonb
            WHEN message_ids::text = '' THEN '[]'::jsonb
            ELSE message_ids::jsonb
        END
    ) AS source_message(message_id)
    WHERE source_message.message_id IN (...)
)
```
同时新增增量数据库迁移脚本 `server/db/migrations/memory-jobs-message-ids-jsonb-compatibility.js`，无论底层历史数据是以 `text` 还是 `jsonb` 存储，均能无缝执行，彻底杜绝 `42804` 错误。
