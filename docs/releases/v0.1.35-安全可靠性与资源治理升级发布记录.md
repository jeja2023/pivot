- 日期：2026-08-24

## 发布范围

本版本针对上一轮全项目审阅中发现的 11 类风险进行集中修复，重点覆盖认证轮换、文档任务恢复、文件解析内存、出站网络、浏览器下载、限流和安全配置。

## 安全修复

### 认证与初始化凭据

- 刷新令牌轮换改为事务内锁定、删除和新令牌写入。
- 并发请求中只有一个请求可以消费同一个刷新令牌。
- 配置校验拒绝弱 `DEFAULT_ADMIN_PASSWORD` 和常见占位 JWT/加密密钥。
- 工作区 `.env` 删除弱默认管理员密码和未使用的默认导入密码。
- `README` 与 `.env.example` 不再提供可直接运行的密钥占位值。

### 出站网络与浏览器

- OCR 服务、运行时资源包同步复用安全主机校验和 DNS Pinning。
- OCR 响应体和运行时资源包下载均有硬字节上限。
- Browser Worker 通过 Chromium `Network.dataReceived` 事件统计实际响应字节，chunked 响应不能绕过下载上限。
- 运行时资源包继续执行 SHA256 和声明大小校验，并采用流式写入临时文件。

## 任务可靠性

### 数据分析全量语义任务

- 全量语义分析由逐批串行执行改为同一任务有界并发执行，默认同时处理 2 批，最高 4 批。
- 实际并发数不会超过模型端点的 `max_concurrent`；端点并发为 1 时继续串行。
- 批次仍通过数据库状态条件认领，不会因多个执行协程而重复处理同一批。
- 取消、失败重试、进度统计、服务重启恢复和最终汇总报告保持原有行为。
- 配置每日 Token 额度的模型自动使用单批串行，避免多个批次同时通过额度预检后造成超额使用。

### 文档处理队列

- `document_jobs` 使用 `locked_at` 作为处理租约。
- 服务启动时恢复排队任务和过期处理租约。
- 后台定时扫描重新排队过期任务，超过最大尝试次数的任务标记失败。
- 任务领取使用状态条件更新，多个进程不会重复执行同一个排队任务。
- 任务处理进度会刷新租约，避免长 OCR/PDF 任务被误判为失联。

### 取消、删除和失败清理

- 终态写入不会覆盖已经取消的任务。
- 删除运行中任务时，后台 worker 无法重新写回成功或失败状态。
- 创建任务记录失败时，会清理已经登记的源文件。
- PDF 多文件任务在部分登记成功后失败，会清理已登记文件。

## 资源边界

- 纯文本附件使用流式前缀读取，避免把完整文件加载到 Node 堆内存。
- PDF、DOCX、XLSX、OLE 和 PDF 工具增加解析缓冲区上限。
- 文档文件 SHA256 使用流式计算。
- Agent JSON 数据源限制文件大小、行数和列数。
- 管理员 CSV 用户导入使用流式解析，支持 RFC 风格引号字段和跨行内容，并限制最大行数。
- PDF 输出归档限制所有输出文件的总大小。
- 归档、OCR、运行时资源包和浏览器下载在超限时返回可诊断错误或主动中止。

## 数据库与运维

- PostgreSQL/SQLite 权威 schema 新增 `rate_limit_counters` 表及过期索引。
- 所有主要 HTTP 限流器切换为 PostgreSQL 共享存储；数据库暂时不可用时回退到有界本地计数，避免无限增长。
- 维护任务清理过期限流计数。
- 技能包 ZIP 解析器 `unzipper` 纳入正式生产依赖；Docker 在 `npm ci --omit=dev` 后显式加载 DuckDB 与 `unzipper`，避免缺少运行依赖的镜像进入启动阶段。
- 新增以下运维参数：
  - `DOCUMENT_PROCESSING_JOB_LEASE_MS`
  - `DOCUMENT_PROCESSING_RECOVERY_BATCH`
  - `DOCUMENT_PROCESSING_RECOVERY_INTERVAL_MS`
  - `DOCUMENT_MAX_BUFFER_BYTES`
  - `OCR_SERVICE_MAX_RESPONSE_BYTES`
  - `AGENT_DATA_MAX_JSON_BYTES`
  - `ADMIN_USER_IMPORT_MAX_ROWS`
  - `DATA_ANALYSIS_SEMANTIC_BATCH_CONCURRENCY`

## 升级注意事项

1. 启动时会自动创建 `rate_limit_counters` 表和索引，无需手工迁移脚本。
2. 生产环境应删除 `DEFAULT_ADMIN_PASSWORD`，使用首次启动生成的一次性凭据文件或管理员界面轮换密码。
3. 本版本没有自动替换现有 `JWT_SECRET` 和 `DATA_ENCRYPTION_KEY`，避免在未完成会话失效和密文重加密准备时造成数据不可用。若这些密钥曾经暴露或多人共用，应在维护窗口内完成密钥轮换和相关会话/密文迁移。
4. 多实例部署应确认所有实例连接同一个 PostgreSQL 数据库；限流和文档任务恢复依赖共享数据库。
5. 全量语义分析建议先保持 `DATA_ANALYSIS_SEMANTIC_BATCH_CONCURRENCY=2`；只有在模型端点可稳定承载更多并发且全局 AI 并发仍有余量时，再逐步调至 3 或 4。
