# v0.3.1 - 工作流契约与法规检索生产加固

> **发布日期**：2026-10-15  
> **升级类型**：兼容性补丁发布  
> **兼容性**：向后兼容 v0.3.0；无需数据库结构迁移

---

## 版本概述

v0.3.1 聚焦两条生产链路：工作流编排的工具输入契约，以及法规查询的治理一致性和高并发检索韧性。

本版本解决了历史可视化 SQL 工作流把编辑器状态一并传入工具、从而被严格策略拒绝的问题；同时让法规元数据审核、质量概览、引用治理、分类权限和混合检索在同一套数据范围与权限边界下运行。对于法规库从当前约 1,641 份记录继续增长的场景，语义召回不再可拖垮整次检索请求，而是按受控预算降级为可用的词法结果。

## 一、工作流编排：工具契约与编辑状态彻底分离

### 1.1 修复 `db.run_readonly_query` 的 `queryBuilder` 策略拦截

此前，可视化 SQL 构建器将 `queryBuilder` 作为 `db.run_readonly_query.input` 的一部分保存。该字段仅服务于编辑器回显，并不是工具 Schema 允许的执行参数；严格 PEP 校验因此会拒绝请求并返回 `TOOL_POLICY_DENIED`。

本版本将职责拆分为：

- 工具输入仅保留生成后的 `sql`、`limit` 等已声明字段；
- 构建器列、条件、排序等展示/编辑状态保存到 `node.ui.queryBuilder`；
- 读取、保存及格式化历史工作流时，自动将旧字段迁移到 `ui`，用户无需手动重建工作流；
- DAG、Agent、流式执行和直接策略入口均在工具边界剔除遗留 `queryBuilder`，作为历史数据的最后一道兼容保护。

### 1.2 保存前即发现契约问题

- 工具目录向编排器提供与 PEP 一致的规范化输入 Schema；
- 编排器就绪检查会标出工具契约未声明的已保存字段；
- 后端保存工作流时验证节点 Schema 与真实工具 Schema，API 调用无法绕过该检查；
- 契约报告区分输入和输出阻断项，使错误可定位至具体节点、字段和契约方向。

结果是：工作流在编辑、保存、发布和执行阶段使用同一份工具输入规则，避免“界面认为可用、执行时才被拦截”。

## 二、法规质量治理：状态、统计和队列使用同一口径

### 2.1 元数据审核完成后即时收敛

- 法规表“管理/效力”列改用法规级 `metadata_review_status`，不再从旧版本或其他状态字段推断；
- 质量概览的“待审核元数据”由未归档法规当前版本的缺失字段和未通过审核状态共同计算；
- 审核通过后，列表状态、待审核总数和元数据治理队列一起减少，不再出现“已审核但仍显示待审核”的割裂；
- 质量概览只向管理员角色显示；普通用户不会看到没有处理权限的入口。

### 2.2 引用治理的功能边界

| 队列 | 含义 | 处理方式 |
| --- | --- | --- |
| 未解析引用 | 从条文提取到引用，但尚未连接到库内目标条文 | 重建关联；如果目标不在库内，可标记为外部引用 |
| 引用待审核 | 已连接到库内条文、仍需人工确认的引用 | 单条确认/驳回/标记外部；高置信记录可批量确认 |

引用识别和回连可自动产生候选，但“审核”是治理确认动作，不会在没有审核依据时自动替代人工结论。统计和操作范围均限定为未归档法规的当前版本，防止历史版本反复计数。

### 2.3 法规分类目录权限一致化

法规分类目录会影响后续导入的归档口径，因此与导入权限对齐为系统 `admin` 专属：

- 非 `admin` 管理员不显示“新建分类”按钮；
- 同时不显示删除自定义分类和“导入此分类法规”入口；
- 即使直接构造请求，创建/删除 `/category-folders` 仍会被服务端以 403 拒绝；
- 前端操作函数也会拦截，避免旧页面或脚本触发无效请求。

## 三、法规混合检索：超时隔离、候选限流与降级结果

### 3.1 503 问题的原因与修复

生产日志中的 `canceling statement due to statement timeout` 说明可选的语义召回超出数据库语句时限。旧流程中，这类慢查询可能占满请求窗口，最终使 `/search/hybrid` 返回 503，即使词法检索本应可用。

v0.3.1 增加事务局部的只读查询时限：查询使用专属连接、`BEGIN` 和 `SET LOCAL statement_timeout`，提交或回滚后立即归还连接，不会把较短时限泄漏到连接池的其他请求。连接获取也受独立预算限制，避免在连接池饱和时无谓等待。

### 3.2 新的检索行为

1. 先在受控预算内执行词法召回；
2. 语义召回单独使用更短预算，并最多取固定数量候选；
3. 语义结果正常时与词法结果融合排序；
4. 语义召回超时、Embedding 不可用或 pgvector 出错时，仅记录结构化告警，继续返回词法命中；
5. 词法排序特性不可用时仍会尝试基础词法检索。

因此，日志中“语义召回不可用，保留词法检索结果”属于已预期的安全降级信号；若词法查询本身也超过时限，则应继续通过慢 SQL、索引与数据库资源监控排查，而不是盲目提高全局超时。

### 3.3 新增运行参数

| 环境变量 | 默认值 | 作用 |
| --- | ---: | --- |
| `REGULATION_LEXICAL_QUERY_TIMEOUT_MS` | `3000` | 词法召回单次数据库时限 |
| `REGULATION_SEMANTIC_QUERY_TIMEOUT_MS` | `2000` | 语义召回单次数据库时限；到期后回退词法结果 |
| `REGULATION_SEMANTIC_CANDIDATE_LIMIT` | `100` | 向量召回候选上限，控制排序成本 |

参数已登记在 `.env.example` 和[类型化配置注册表](../configuration-registry.md)。生产环境可先保留默认值；仅在监控证实索引、连接池和资源余量充足时再逐步调整。

## 四、法规检索交互：关闭清理与防重复提交

- 关闭检索弹窗会中止仍在执行的浏览器请求、使旧响应令牌失效、清空检索输入框和结果；
- 点击检索后，按钮立即禁用并显示“检索中…”，同时呈现加载状态；
- 请求完成、失败或取消后才恢复按钮；
- 晚到的响应无法覆盖已关闭或后续重新打开的检索窗口。

这既避免用户连续点击造成并发检索，也避免关闭弹窗后残留关键词影响下一次法规查询。

## 五、升级与验收

### 5.1 升级步骤

1. 部署 v0.3.1 应用文件并重启服务；应用会从 `CHANGELOG.md` 读取版本，静态资源 URL 自动切换到 `v0.3.1` 缓存标识。
2. 保留或按需设置上述三个 `REGULATION_*` 参数；未设置时采用安全默认值。
3. 以系统 `admin`、普通管理员和普通用户分别登录，验证分类入口和质量概览可见性。
4. 使用一个曾出现慢语义召回的检索词验证：在语义服务迟缓或不可用时，界面仍能收到词法结果，而非 503。
5. 打开一条历史可视化 SQL 工作流并保存、执行，确认不再出现 `input.queryBuilder` 契约拒绝。

### 5.2 自动化验证覆盖

- 工作流 DAG 布局、编排增强、输入契约、工具策略和工作流控制面回归；
- PostgreSQL 事务级限时查询与法规混合检索降级回归；
- 法规质量概览、元数据审核统计、分类权限和检索弹窗浏览器回归；
- `npm run build:chat-css`、`npm run check:text` 与差异空白检查。

## 六、兼容性与回退

- 不新增数据库迁移，也不改变法规数据表结构；
- 旧工作流中的 `input.queryBuilder` 在第一次读取/保存时会被兼容迁移到 `ui.queryBuilder`，执行期仍保留防御性剔除；
- 新检索参数均有默认值，未配置不会阻断启动；
- 回退应用版本前，应保留已保存 DAG 中的 `ui.queryBuilder`，旧客户端对未知 `ui` 字段会忽略，SQL 与 `limit` 仍可正常执行。
