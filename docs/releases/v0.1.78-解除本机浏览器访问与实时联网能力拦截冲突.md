# v0.1.78 发布记录：解除本机浏览器访问与实时联网能力拦截冲突

发布日期：2026-09-04

## 一、问题背景

在已连接桌面端并授权本机浏览器工具（如 `mcp.0.browser.*`）的会话中，当用户发出包含具体 URL 以及常见时效性词汇的指令时（例如：“`使用工具库中的浏览器打开 https://www.baidu.com，查询最新的新闻`”），系统未调用已授权的本机浏览器工具，而是直接拒绝执行并返回通用提示：
> 当前系统还没有接入“实时联网检索”执行能力，所以我不能直接完成这类操作。你刚才的请求属于：联网搜索、查询今天新闻、获取实时价格……

而在工具库控制台中针对 `mcp.0.browser.open` 等工具进行单步测试时均可正常执行。

## 二、根因分析

1. **粗粒度静态意图前置拦截**：
   - 服务端在 [`server/routes/chat/index.js`](../../server/routes/chat/index.js) 最前置阶段执行了 `detectUnsupportedCapability(modelContent)`。
   - 用户提问中若同时包含“`最新`”与“`新闻`”，会无条件命中 `realtime_web`（实时联网检索）正则表达式。
   - 该拦截发生在普通对话的 MCP 工具库意图分析与 Agent 调度之前，导致凡是提及“最新新闻”、“实时价格”等词汇的请求，均被提前抢占拦截，无法进入工具库调度流程。
2. **两类能力的本质差异**：
   - “实时联网检索”是指大模型自身具备内置实时搜索引擎连接（系统尚未接入）；
   - “本机浏览器访问”则是用户在本地受控授权环境下，委托本地浏览器打开指定的特定 URL。当用户明确给出了 `http/https` 网址并要求浏览器访问时，应由工具库与本地 MCP 连接器接管执行，而非被粗粒度拦截。

## 三、优化与改造方案

1. **能力拦截让渡判定（`shouldDeferRealtimeCapabilityGuard`）**：
   - 在 [`server/services/chat-mcp-context.js`](../../server/services/chat-mcp-context.js) 中新增 `shouldDeferRealtimeCapabilityGuard(capability, { mcpEnabled, userPrompt })`：
     - 当且仅当会话已启用工具库（`mcpEnabled === true`）、触发的能力为 `realtime_web`、且用户指令明确包含合法 URL 及浏览器访问意图（`detectBrowserVisitIntent(userPrompt) === true`）时，让渡拦截检查。
2. **对话路由放行流转**：
   - 在 [`server/routes/chat/index.js`](../../server/routes/chat/index.js) 中，当识别到上述情况时跳过能力拦截，记录日志 `已将明确本机浏览器访问请求交由工具库处理`，平滑进入上下文装配与 MCP 工具规划器流程，正确调用本地浏览器连接器执行打开任务。
3. **单元测试与回归防护**：
   - 在 [`tests/local-browser-connector-tools.test.js`](../../tests/local-browser-connector-tools.test.js) 中补充用例：
     - `已开启工具库的明确本机浏览器访问不会被实时联网能力拦截抢先拒绝`，验证在各种提示词分支下让渡机制的准确性。
