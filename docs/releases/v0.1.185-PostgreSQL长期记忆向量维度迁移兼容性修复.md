# v0.1.185 PostgreSQL 长期记忆向量维度迁移兼容性修复

发布日期：2026-09-27

发布范围：PostgreSQL 版本化迁移 `202609260003_long_term_memory_embedding_recovery` 的历史向量字段兼容性。

## 问题与影响

部分早期生产数据库中的 `memories.embedding` 列仍为 `TEXT`，当前 Schema 快照则使用 pgvector 的 `vector` 类型。长期记忆向量恢复迁移在回填 `embedding_dimensions` 时直接调用：

```sql
vector_dims(embedding)
```

当历史列是 `TEXT` 时，PostgreSQL 无法匹配 `vector_dims(text)`，服务启动会在该版本化迁移处中止。

```text
function vector_dims(text) does not exist
```

迁移运行器会将单条迁移包裹在事务中。失败时不会记录该迁移 ID，也不会留下部分回填结果；部署修复版本并重启即可自动重试。

## 修复内容

- 不再直接依赖 `vector_dims(embedding)` 的列类型。
- 所有历史向量均通过 `embedding::text` 读取：这兼容 pgvector 的标准数组文本表示和旧版文本向量。
- 迁移会安全解析纯数值 JSON 数组并将数组长度写入 `embedding_dimensions`。
- 空值、空白文本、非法 JSON、JSON 对象/标量、空数组或包含非数值元素的数组统一保留为维度 `0`。
- 维度为 `0` 的活动记忆会由既有长期记忆向量恢复任务按当前模型配置重新生成，不会被错误用于向量检索或 HNSW 索引。
- 解析函数仅存在于当前迁移事务中，回填后立即删除；`memories.embedding` 的实际列类型和历史向量正文不被强制转换或改写。

## 升级步骤

1. 部署 `v0.1.185` 的服务端代码及对应版本元数据。
2. 重启 Pivot 服务。
3. 启动时会自动重试尚未完成的 `202609260003_long_term_memory_embedding_recovery`，随后继续后续长期记忆迁移。
4. 在启动日志确认 PostgreSQL 迁移完成记录，服务健康检查恢复正常。

不需要手工删除迁移记录。此前出现 `vector_dims(text)` 错误时，运行器已经回滚事务，因此该迁移通常不会被记录为已完成。已经成功完成该迁移的数据库不会重复执行。

## 验收证据

- 新增 `tests/long-term-memory-embedding-recovery-migration.test.js`，验证迁移不再调用 `vector_dims(TEXT)`，且包含安全数组解析与临时函数清理契约。
- 真实 PostgreSQL 回归：在事务内把 `memories.embedding` 改为 `TEXT`，插入合法数组、非法文本和非数组 JSON；验证合法数组回填维度 `3`，其余记录均安全保留为 `0`，最后回滚测试事务。
- `node scripts/run_node_tests.js tests/long-term-memory-embedding-recovery-migration.test.js` 通过。
- 定向 ESLint、`npm run check:pg-migrations`、`npm run check:text`、全量 JavaScript 语法检查、`npm run check:standards:changed` 与 `git diff --check` 通过。

## 发布边界

- 本版本不新增迁移 ID、数据库字段或环境变量，只修复既有未完成迁移的兼容执行路径。
- 修复不会把旧 `TEXT` 列在线转换为 pgvector。向量检索层已有失败降级和恢复逻辑；生产环境如需完全恢复数据库侧向量索引，应在业务低峰按既有 PostgreSQL/pgvector 升级流程评估列类型迁移。
