# v0.1.161 发布记录：生产知识库权限与向量索引修复

发布日期：2026-09-22  
版本号：v0.1.161

## 发布结论

v0.1.161 修复了普通管理员仍可读取全体用户知识库文档的权限遗漏，并消除了 pgvector HNSW 部分索引创建时的 `WITH` 语法错误。同步补充 llama.cpp Embedding 容器的物理批次容量运维指引，避免单条分块超过默认 512-token 上限后不断降级为关键词索引。

## 权限边界

- 超级管理员定义不变：同时满足 `role=admin` 且用户名为 `admin` 的账户。
- 只有超级管理员可跨用户读取常规知识库集合、上传文档、标签、检索结果、图谱、数据源、索引任务和引用汇总。
- 普通管理员（角色为 `admin` 但用户名不是 `admin`）与普通用户均按 `user_id` 严格过滤；即使猜测其他用户的文档 ID，也不会通过列表、检索或图谱接口取得其资料。
- 产品化文档保留明确、可审计的协作路径：所有者、指定内容负责人/审核人和 `knowledge_permissions` 显式授权主体只能访问获授权的具体文档。该路径不会将普通管理员提升为全库读权限。

## HNSW 索引修复

知识库会为相同 `embedding_profile` 和 `embedding_dimensions` 的向量建立部分 HNSW 索引。旧实现将部分索引的 `WHERE` 条件置于 HNSW 参数 `WITH` 前，PostgreSQL 会返回：

```text
syntax error at or near "WITH"
```

现已改为 PostgreSQL/pgvector 要求的顺序：

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS ...
ON knowledge_chunks USING hnsw ((embedding::vector(1024)) vector_cosine_ops)
WITH (m = 16, ef_construction = 64)
WHERE embedding IS NOT NULL
  AND embedding_dimensions = 1024
  AND embedding_profile = '...';
```

失败的旧索引语句不会创建半成品索引。升级镜像后，对任一受影响文档执行“重新索引”，或等待后台向量补齐任务重试，即可自动重新创建索引；数据和已成功创建的索引无需删除。

## llama.cpp Embedding 服务

当 llama.cpp 返回下列错误时，Pivot 的批次自适应拆分已经执行，但单条输入仍大于服务的物理 batch：

```text
input (...) is too large to process. increase the physical batch size (current batch size: 512)
```

在 Embedding 容器的 Compose 启动参数中同时设置 `--batch-size` 与 `--ubatch-size`。推荐从 `2048` 开始；若显存不足，再一起降为 `1024`。两者并不等同于 Pivot 的 `RAG_EMBEDDING_BATCH_MAX_INPUTS`：后者只控制一次 HTTP 请求包含多少条输入，无法分割一个已经超过 `--ubatch-size` 的单条文本。

```yaml
command:
  - --batch-size
  - "2048"
  - --ubatch-size
  - "2048"
```

`--ubatch-size` 的含义及默认值见 [llama.cpp server 参数文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)。

## 桌面客户端自动更新与分发配置修复

排查并修复了打包生成的 Windows 客户端安装包无法触发自动更新的系列问题：

1. **自动纠正开发环境回环地址残留**：`scripts/desktop_auto_sign_profile.js` 在生成分发配置时，增加对 `baseConfig.remoteUrl` 及既有 `.tmp/dist-config.json` 的回环地址（`localhost`、`127.0.0.1`）检测；若检测到开发残留，自动纠正为生产分发源 `http://50.64.150.51:9006/`，并将对应 Origin 注入 `allowedOrigins` 白名单，防止客户端更新源指向本机的不可达端口。
2. **构建元数据动态注入真实 generic feed**：`scripts/desktop_build_staging.js` 在 staging 临时构建元数据中，自动将 `bundledConfig.autoUpdate` 衍生的更新 feed URL（如 `http://50.64.150.51:9006/downloads/`）注入 `manifest.build.publish`，解决 `package.json` 中的占位地址被直接写进打包后 `app-update.yml` 的问题。
3. **支持修改服务器连接时热重载更新控制器**：在 `desktop/main.js` 中，当用户通过界面保存新的服务器连接配置时，主进程主动销毁并以新配置重建 `updaterController`，使得切换服务器后能立即使用新服务器的更新发布源。
4. **代码签名信任要求**：Windows 生产环境自动更新由 `electron-updater` 基于系统 Authenticode 链验证；自签名证书在开发测试阶段用于跑通安装包构建，生产分发更新时需配置受信任的代码签名证书（`WIN_CSC_LINK` / `CSC_LINK`）以通过系统校验。

1. 备份 PostgreSQL 与同一恢复点的 `uploads/`。
2. 构建、导入并部署 v0.1.161 Pivot 镜像；无新增数据库迁移或 Pivot 环境变量。
3. 使用普通管理员账号验证：`/api/rag/docs`、专题库、标签、图谱、数据源和索引任务均不展示其他用户数据；使用超级管理员 `admin` 验证可执行跨用户运维。
4. 若部署 llama.cpp Embedding 容器，按服务显存更新其物理批次参数并重建该容器。
5. 在知识库中重新索引一份 1024 维文档，并确认日志不再出现 HNSW 的 `WITH` 语法错误；按需通过 `pg_indexes` 查询确认索引存在。
