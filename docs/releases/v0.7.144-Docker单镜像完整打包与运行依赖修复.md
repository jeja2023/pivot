# v0.7.144 Docker 单镜像完整打包与运行依赖修复

日期：2026-11-09。本次启用源码版本 v0.7.144，补齐本轮依赖与镜像修复的更新日志、部署和使用说明。功能验证阶段构建的镜像仍为 v0.7.143；文档和版本同步没有重新构建或替换已有镜像、tar、桌面安装包，也未部署生产环境。

## 默认一个主镜像完整交付

从仓库根目录执行：

```sh
docker build -t pivot:latest .
docker save -o pivot.tar pivot:latest
```

第一条是完整构建命令，不需要为 Git、ripgrep 增加参数或单独构建终端镜像；第二条按原流程导出镜像。最终主镜像默认包含：

- 主应用、生产 Node 依赖、项目 Python、Vosk 运行环境和离线模型，以及已有文档、字体和浏览器工具。
- Git、ripgrep 和 `/runner/runner.js` 终端协议入口；构建以非 root 身份检查 Node、Python、Git、rg 和协议脚本。
- veraPDF CLI/JRE 及本次探测修复。

Git/ripgrep 的安装独立成层，以复用已有 Chromium、JRE 和数据库客户端层缓存。运行底座继续使用 `node:22.23.4-bookworm-slim`，没有为了工具遗漏恢复整套编译工具链。主镜像的默认命令仍启动 Web 服务；终端使用同一镜像时由控制面显式执行 `node,/runner/runner.js`。

独立 `terminal-runner` Dockerfile 保留为需要单独标签或默认终端入口时的兼容包装，直接复用主镜像中的工具。终端容器继续按既有签名、Execution Grant、不可变镜像身份、用户/运行/工作区授权和隔离规则执行。已有部署若仍指向旧 Runner 摘要，加载新主镜像后须按原信任流程登记并更新终端镜像身份；本次没有自动修改部署凭据或开启高风险能力。

## SQLite 安装来源修复

原依赖将 `better-sqlite3` 写成 GitHub `v12.11.2` 源码归档 URL，锁文件也保存同一地址。该 URL 不受 `NPM_REGISTRY` 替换，GitHub TLS 连接重置时，增加 npm 重试仍不能消除下载路径依赖。

本次改用 npm 已发布的精确版本 `12.11.1`，同步 `package.json`、锁文件版本、发布包 URL 和 SHA-512 完整性摘要，安装可沿用现有 npm 源配置。不跨大版本升级，也不通过跳过校验掩盖下载失败。

Docker 继续先禁止安装脚本，再使用镜像内 Node 头文件从源码编译 SQLite 绑定，并执行内存查询自检。桌面 Electron 43 不包含在本轮镜像验证中；`12.11.1` 没有对应预编译包时，既有桌面打包链会回退源码编译，需要目标平台编译工具链，桌面安装包应另行验收。

## veraPDF 探测与恢复

- JVM 启动探测上限从5秒调整为30秒，并发请求共用同一次探测；超时强制终止探测进程。
- 成功结果缓存60秒，失败只缓存5秒，避免一次瞬时负载让验证能力持续一分钟不可用。
- 探测超时使用 `VERAPDF_HEALTH_TIMEOUT` 和504状态，提示稍后重试或检查负载；缺少 CLI/Java 环境和其他配置失败继续以503返回清晰提示，且不暴露内部路径。
- PDF 工具页的能力查询保留35秒等待，覆盖服务端预算。响应直接解析 JSON，操作表改用原生键值映射，去掉不必要的复制。

PDF/A 仍只验证并生成报告。普通 PDF 不会被自动转换，也不会因引擎可运行或探测成功而被标为合规。
