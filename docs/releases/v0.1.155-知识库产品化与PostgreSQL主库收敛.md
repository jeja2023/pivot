# Pivot v0.1.155 发布记录：知识库产品化与 PostgreSQL 主库收敛

发布日期：2026-09-20  
版本来源：[CHANGELOG.md](../../CHANGELOG.md) 顶部版本标题；已同步至 `package.json`、`package-lock.json` 与 README。

## 发布结论

v0.1.155 将 Pivot 知识库从“文件上传后可被 RAG 检索”的功能模块，升级为可维护、可验证、可运营的局域网知识产品；同时完成主业务数据库的 PostgreSQL-only 收敛。

本版本的边界必须明确：**Pivot 主业务库不再支持 SQLite 启动、Schema 初始化、迁移或兼容回退。** SQLite 仍保留在桌面端受控本机能力中，绝不影响桌面授权和本机数据文件使用。

## 知识库产品化交付

### 内容资产与生命周期

- 新增稳定的知识文档、版本与内容块模型，保留与历史 `knowledge_docs`、`knowledge_chunks` 的投影关联，避免升级时丢失已上传资料和可用检索内容。
- 文档支持草稿、审核、发布、归档生命周期；可记录责任人、验证人、验证状态、复核时间、有效期策略、版本差异与变更摘要。
- 支持评论、纠错与处理状态，引用由稳定 `citation_key` 标识，可返回原文片段、位置定位和受 ACL 约束的原件下载。

### 可恢复索引与检索

- 索引任务改为 PostgreSQL 持久化队列，支持幂等键、优先级、租约抢占、心跳续租、退避重试、重启恢复和多实例 `SKIP LOCKED` 并发消费。
- Embedding 或向量服务不可用时，文档保留 `lexical_ready` 的关键词可检索状态；向量恢复巡检会在服务恢复后补齐向量，而不是把资料静默下线。
- 检索固定采用 PostgreSQL `tsvector + GIN`、`pg_trgm` 回退、pgvector 向量检索与 RRF/MMR 融合。向量按 `embedding_profile` 与 `embedding_dimensions` 隔离，并使用部分 HNSW 索引避免不同模型空间混检。
- 聊天、知识库工作台、引用预览、下载和 Agent 项目资料包统一通过集合/文档 ACL 判定，不再各自维护可见范围。

### 局域网来源与治理

- 支持受控上传、目录/NAS/SMB 映射路径、内网 HTTP/API manifest、以及局域网数据库内容投影。
- 目录与 HTTP/API 来源支持 hash/ETag 增量识别、同步运行记录、失败状态和删除归档；目录访问严格限制在管理员白名单内，并拒绝符号链接逃逸。
- 数据库来源不接受自由 SQL；只能引用管理员审核通过的单条只读查询模板，并固定标题、内容和水位字段映射。
- 引用行为、来源同步、文档审核和质量评测均保留可审计的持久化记录。

### 质量评估与运营

- 新增黄金问题集与评测运行，覆盖 Recall@K、MRR、nDCG、引用精确率/召回率/F1、答案关键点覆盖和无答案场景的拒答准确率。
- 支持评测运行间比较、来源与集合维度的质量摘要，以及用于治理的知识缺口报告。

## PostgreSQL 主库收敛

### 已移除的主库兼容层

- 移除 SQLite 主 schema、SQLite FTS、主库 SQLite 迁移、SQLite→PostgreSQL 转换脚本、差异/基线校验脚本和 SQLite 主库测试契约。
- `server/db/schema/pg-schema.snapshot.json` 成为审查后的原生 PostgreSQL DDL 唯一来源；启动按快照补齐表、遗留列、外键、索引和注释。
- 所有主库版本迁移只暴露 `upPg`。当前注册 68 条 PostgreSQL 迁移；历史建表由 schema 快照承担，迁移仅处理 PG 专属数据回填、约束和控制面演进。
- 测试中的同步 statement facade 改为共享内存 PostgreSQL Worker，不再模拟 SQLite 主库行为。

## SQLite 保留范围

以下能力继续保留 SQLite，且不使用 Pivot 主业务数据库连接：

| 场景 | 保留原因与约束 |
| --- | --- |
| 桌面本机授权 | 保存用户在桌面端明确授权的本机目录/数据库访问范围；授权仍由桌面端控制。 |
| 桌面 Agent 状态库 | 仅保存桌面运行时局部状态，不参与服务端业务数据、用户、会话或知识资产持久化。 |
| 本机只读数据库工具 | 可在用户授权后读取 SQLite 文件；仍受路径白名单、只读执行器和工具治理约束。 |
| 数据分析导入 | 允许把 SQLite 文件作为待分析数据集导入；导入后的业务元数据仍保存于 PostgreSQL 主库。 |

因此 `better-sqlite3` 继续随桌面运行时和相关受控本机工具交付；其存在不表示主业务数据库仍有 SQLite 兼容路径。

## 升级步骤

1. 备份 PostgreSQL 数据库，并将 `uploads/` 纳入同一变更窗口的文件备份；不要只备份桌面或容器的 `data/` 目录。
2. 确认 `.env` 中 `DATABASE_URL` 指向目标 PostgreSQL，并验证应用数据库账号具备建表、补列、建索引权限；知识向量检索还需要可用的 `vector` 与 `pg_trgm` 扩展。
3. 部署 v0.1.155 服务。首次启动会执行原生 PostgreSQL schema 初始化，再按 `schema_migrations` 应用未登记的 PG 迁移。
4. 部署后执行只读对账：

   ```powershell
   npm run verify:knowledge-migration -- --strict
   ```

5. 使用普通用户与管理员各抽查一次：上传或同步资料、查看引用、按权限访问集合、处理索引失败重试、运行质量评测，以及聊天/Agent 内的受控知识检索。
6. 保留桌面端 SQLite 授权和本机数据文件；无需也不应把这些文件导入 PostgreSQL。

## 不支持的升级路径与回滚

- 本版本不提供从仍在使用的 SQLite **主业务库**自动在线迁移的脚本。已完成历史数据迁移的 PostgreSQL 环境可以直接升级；未完成迁移的旧环境必须先在隔离环境完成一次性数据迁移、抽样核验和切换演练。
- 不要执行已经删除的 `scripts/migrate_sqlite_to_pg.js`、`scripts/verify_pg_migration.js`、`scripts/diff_schema_sqlite_pg.js` 或任何依赖主库 SQLite DDL 的旧流程。
- 版本化数据库迁移不提供自动 down migration。若需要回退，请停止写入、恢复升级前的 PostgreSQL 备份与对应文件备份，再恢复匹配的软件版本；先在 staging 验证，不能以删除表或手工回退列替代恢复流程。

历史 SQLite→PostgreSQL 一次性迁移方案仅作为归档资料保留，当前生产运行与升级规则以 [PostgreSQL 主库运行与升级说明](../生产环境PostgreSQL主库运行与升级说明.md) 为准。

## 验证记录

- `npm run check`：通过，包含 68 条 PostgreSQL 迁移覆盖、104 张表/184 个外键/172 个索引的 schema 与索引基线、配置注册表、治理、语法、资产与 E2E 合同检查。
- `npm run lint`：通过。
- `npm test`：通过 1,179 项测试，两个隔离 PostgreSQL schema 分组分别为 513 与 666，零失败。
- 回归显式覆盖：知识产品化迁移与权限、引用/来源同步、PostgreSQL FTS 与向量恢复、聊天 Agent 终态幂等、桌面本机授权、SQLite 文件数据分析导入和桌面本机只读 SQLite 执行器。
