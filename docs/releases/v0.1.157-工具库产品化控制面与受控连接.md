# Pivot v0.1.157 发布记录：工具库产品化控制面与受控连接

发布日期：2026-09-20  
版本来源：[CHANGELOG.md](../../CHANGELOG.md) 顶部版本标题；已同步至 `package.json`、`package-lock.json` 与 README。

## 发布目标

本版本将 Pivot 的工具库从“管理 MCP 服务和工具缓存”的配置页，升级为可安全发现、连接、执行、观测、评测和持续发布工具的企业控制面。既有 MCP 服务、内置工具、数据库工具及既有工作流继续可用；`mcp_tool_cache` 保留为 active Catalog Release 的兼容投影。

## 核心能力

### 1. 工具契约与目录 Release

- 每次 MCP `tools/list` 刷新都建立不可变 Catalog Release，冻结工具名称、中文/旧名别名、输入/输出 Schema、annotations、示例、标签、Scope、风险、幂等与定义摘要。
- 系统比较新旧目录：删除工具、增加必填输入、收窄输入类型或改变输出契约均标记为破坏性变更；兼容变更可自动激活，破坏性变更进入审核。
- 刷新失败或候选目录不合规时，旧 active release 继续提供服务。管理员可查看 release、差异并显式激活审核版本。
- 已发布工作流会固定 MCP 工具的 `release_id + definition_digest`；工具定义变化后依赖项变为 stale，须重新确认后发布。

### 2. 统一工具策略与可靠执行

- 聊天、Agent、DAG、MCP RPC、OpenAI 兼容工具调用、数据分析导入与手动测试均经统一 Tool Policy Enforcement Point。
- 策略依次验证工具/release、访问范围、能力包、连接账户与 Scope、输入契约、审批、网络/数据边界；返回可解释 reason code，并在输出侧再校验 Schema 与脱敏规则。
- 工具任务支持高熵任务 ID、查询、取消与补充输入。工具/连接维度增加并发舱壁、速率限制、熔断、半开探测和仅对安全失败的退避重试。
- 调用事件关联 actor、来源、连接账户、release、策略决定、Trace、耗时和安全摘要；凭据和业务原文不会作为日志预览或模型上下文保存。

### 3. 连接中心与 OAuth

- 连接器定义、连接账户和工具绑定成为独立对象，支持个人、单位共享和服务账号归属。
- OAuth 2.0 使用授权码 + PKCE，校验 state、账户归属、回调地址和 HTTPS 端点；支持刷新、撤销、过期/失败状态与重新授权。
- 工具库“连接与凭据”页展示账户状态、Scope、到期时间与诊断摘要，OAuth 账户可跳转到服务提供方完成授权；“测试连接”只执行授权校验及 MCP `tools/list` 握手，不触发业务工具。
- API Key 和遗留数据库/MCP 服务以兼容账户形式登记；访问令牌只在服务端加密保存，不返回浏览器、工具 Schema、工作流版本、调用日志或模型。

### 4. 渐进式发现、运营与供应链

- 新增 `tools.search`、`tools.describe`、`tools.execute`：先返回少量已授权工具摘要，再按需加载冻结契约并受策略执行。词法、中文别名、标签、示例和向量索引均按 release 持久化。
- 工具库页面增加“工具目录、数据连接、连接与凭据、运行与治理”四个入口；运行面板聚合成功率、延迟、失败原因和待审批调用。
- 新增工具评测集、用例、运行和 Top-1/Top-3 指标。`pivot.toolkit.json` Schema、RSA 签名密钥、Manifest/签名/目录契约/评测门禁和审核发布构成受控工具包供应链。
- MCP HTTP 保持既有会话模式兼容，同时支持 2026 无状态 `Mcp-Method`、`Mcp-Name` 路由头和 W3C Trace Context。

## 升级与运维

1. 在维护窗口前备份 PostgreSQL 与同一恢复点的 `uploads/`。
2. 部署 `v0.1.157` 后启动服务。系统会执行 `202609200004_tool_library_product_control_plane`；不要手工删除旧 MCP 缓存或新建表，也不要修改 `schema_migrations`。
3. 管理员刷新已有外部 MCP 服务，确认生成 Catalog Release；若差异为破坏性，先评估并重新确认受影响工作流。
4. 对 OAuth 连接器登记受 HTTPS 保护且精确匹配的授权端点、令牌端点和回调地址。生产环境必须保持 `PIVOT_ALLOW_INSECURE_OAUTH_HTTP=false`。
5. 在“连接与凭据”完成账户授权或点击“测试连接”；在“运行与治理”确认策略决定、Trace 和错误摘要符合预期。

PostgreSQL 迁移没有自动 down migration。需要回退时，应在 staging 验证后恢复升级前数据库与文件备份，而不是删除新表、列或迁移登记。
