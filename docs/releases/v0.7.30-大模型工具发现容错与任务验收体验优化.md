# v0.7.30 大模型工具发现容错与任务验收体验优化

**发布版本**：v0.7.30  
**发布日期**：2026-10-22  
**发布类型**：功能修复与体验加固版本（深度优化智能体任务执行链路与核验交互）

---

## 1. 版本概述

在日常使用大型语言模型（尤其是 Qwen3.5-35B 思考模型、DeepSeek-R1、o1 等具备深度推理思考能力的大模型）进行自主智能体对话与任务执行时，部分用户遇到了工具调用执行失败、连续错误超过预算导致任务中止、以及任务验收面板提示晦涩英文硬性条件未通过等连环问题。

v0.7.30 针对上述核心痛点进行了全链路代码审查与彻底修复，涵盖：
1. **渐进式工具发现容错**：支持模型以简化的 toolName 或缺少 digest 的 toolRef 调用 `tools.describe` 与 `tools.execute`，并支持已授权工具的自动检索回退；
2. **长推理周期适配**：将发现缓存有效时间由 30 秒延长至 10 分钟，消除长达 60s~120s+ 深度思考后缓存超期的异常；
3. **流式通信空帧安全**：修复了 `server/streaming.js` 在接收第三方推理引擎空 choices 帧时触发的 delta 报错与通道自适应切换误报；
4. **验收核验结果全面中文化**：将前端验收面板的技术字段与未通过原因转换为清晰直观的业务中文说明。

## 2. 核心改进与问题定位

### 2.1 解决 tools.describe 工具契约读取失败与预算熔断

- **现象定位**：大模型调用 `tools.describe` 时，报错：`请先使用 tools.search 获取当前已授权工具的 toolRef，再读取其契约。`。模型连续重试多次均报错，触发了任务预算中的 `max_consecutive_errors: 3` 熔断（`连续错误次数超过预算。已完成 5 项执行观察，但未能生成完整总结。`）。
- **根本原因**：
  1. `tools.search` 阶段返回的候选工具带有 64 位 SHA-256 定义摘要（`definitionDigest`），而大模型后续生成 `tools.describe` 时通常仅传入 `{ toolRef: { toolName: "..." } }`、`{ toolName: "..." }` 或字符串名称，忽略了长摘要字段，造成键比对失败；
  2. 缓存超时过短：旧逻辑 `DISCOVERY_CACHE_TTL_MS` 仅为 30 秒，而思考模型仅单轮思考便耗时 69.0 秒，导致检索状态在模型开始调用 describe 前已过期。
- **解决方案**：
  - 在 `server/services/agent-tool-progressive-discovery.js` 中新增 `candidatesByName` 索引，并通过 `resolveReferenceKey` 自动补全正规的 releaseId 与 definitionDigest；
  - 在 `server/services/agent-tools-discovery.js` 中实现**自动搜索回退机制**：如果模型已知工具名称并直接发起 describe，系统在确认该工具属于用户已授权目录后自动为其登记搜索记录，顺利返回工具契约；
  - 将 `DISCOVERY_CACHE_TTL_MS` 提升至 10 分钟（支持上限 30 分钟），从容适配所有长思考深度推理模型。

### 2.2 修复流式推理空帧引发的通道切换误报

- **现象定位**：执行记录中出现 `5. 通道自适应平滑切换：检测到底层通信波动，已自动平滑切换至可靠通道继续执行。`。
- **根本原因**：在 `server/streaming.js` 的 `extractStreamPayload` 中，针对 `json.choices[0].delta` 的检查在面对某些厂商发送的 `{ choices: [] }` usage 帧时，因未做数组长度校验而抛出 `TypeError: Cannot read properties of undefined (reading 'delta')`，触发流式降级。
- **解决方案**：严格使用 `Array.isArray(json.choices) && json.choices[0]?.delta` 进行安全访问，彻底消除该偶发报错。

### 2.3 任务验收与硬性条件全面本地化中文展示

- **现象定位**：任务验收结果中显示：
  - `需要补充 3 项硬性条件未通过`
  - `• artifact_required: 未通过`
  - `• deliverables_verified: artifact_not_materialized`
  - `• evidence: evidence`
- **根本原因**：
  1. 前端 `client/chat/agent-run-status-views.js` 直接使用 `rule.key: rule.actual` 输出，未做中文映射；
  2. 后端 `server/services/agent-verification.js` 中 `evidence` 规则的实际值被字面硬编码为 `'evidence'`。
- **解决方案**：
  - 修正后端的 `rule.actual` 输出，真实反映来源证据的充足性；
  - 前端建立 `AGENT_VERIFICATION_RULE_NAMES` 与 `AGENT_VERIFICATION_REASON_NAMES` 中文对照表，规范显示为：
    - `• 成果交付文件：尚未生成要求的文件`
    - `• 交付内容核验：尚未生成要求的文件`
    - `• 资料来源与佐证：缺少引用来源或佐证记录`
