# v0.1.162 发布记录：Windows 客户端自动更新发布通道固化

发布日期：2026-09-22  
版本号：v0.1.162

## 发布结论

本版本将 Windows 客户端“可构建安装包”与“可安全发布自动更新”拆成不可混用的通道。此前开发机自签名包、离线安装包和生产更新包容易落到同一个 `downloads/` 目录，导致更新能力时而可用、时而在下载后被签名校验拒绝。现在只有明确的正式更新通道可以写入更新元数据。

## 固化后的构建通道

| 通道 | 命令 | 用途 | 自动更新 | `downloads/` 发布 |
| --- | --- | --- | --- | --- |
| 正式更新 | `npm run preflight:win-update` → `npm run dist:win` | 已安装 Windows 客户端升级 | 开启 | 是 |
| 正式离线 | `npm run dist:win:offline` | 共享目录、U 盘或企业软件分发 | 强制关闭 | 否 |
| 开发联调 | `npm run dist:win:dev` | 本机功能验证 | 强制关闭 | 否 |

正式更新通道必须同时拥有：

- 独立 `PIVOT_DISTRIBUTION_CONFIG`，且其中 `autoUpdate.enabled=true`；
- 非回环的更新 URL，并在 `autoUpdate.allowedOrigins` 中显式允许其 Origin；
- `PIVOT_DISTRIBUTION_STEALTH_SECRET` 或 `PIVOT_STEALTH_SECRET`；
- 非 `Pivot Local Dev` 的 `PIVOT_WINDOWS_UPDATE_PUBLISHER`；
- `WIN_CSC_LINK`、`CSC_LINK`、`PIVOT_WINDOWS_CERTIFICATE_SHA1` 或 `PIVOT_WINDOWS_CERTIFICATE_SUBJECT` 中的一种有效 Windows 签名凭据。

缺少任一项即失败，不会使用自签名开发证书兜底，也不会覆盖生产更新源。

## 发布一致性校验

正式构建完成后会验证：

1. 安装器与 `Pivot.exe` 的 Authenticode 签名有效，且证书 Subject 与发布者一致；
2. `latest.yml` 的版本、安装器名称、大小和 SHA-512 与实际文件一致；
3. 对应 `.blockmap` 存在；
4. 打包后的 `resources/config.json` 已启用更新且允许目标 Origin；
5. `resources/app-update.yml` 指向相同 generic feed，并绑定相同签名发布者。

发布顺序为安装器和 blockmap 原子替换、`latest.yml` 最后替换，避免客户端读到指向未完成文件的版本描述。

## 签名校验稳定性

Windows 更新器不再直接 `JSON.parse` 整个 `Get-AuthenticodeSignature` 证书对象。部分企业镜像会将 `ConvertTo-Json` 深度告警或模块进度混入 stdout，造成 `Unexpected non-whitespace character after JSON`。新版仅将签名状态、文件路径与证书 Subject 写入临时 JSON 文件再读取，随后仍严格要求签名状态为有效和发布者匹配。

## 现有客户端迁移

`CN=Pivot Local Dev` 的自签名安装器不能作为生产自动更新基线：Windows 不信任该根证书，且更新器会拒绝发布者改变后的安装包。现有这类客户端需先通过企业软件分发或受控人工安装升级到企业签名基线；之后的企业签名版本才可使用自动更新。

客户端行为保持为“自动检查并下载，用户确认后重启安装”，不会在用户没有确认时静默覆盖正在运行的客户端。

## 验证

- 构建通道、发布预检、分发配置、签名发布者、`latest.yml`/SHA-512/blockmap/feed 绑定均有自动化测试。
- Windows 签名读取已改为受控标量 JSON，规避 PowerShell 证书对象序列化污染 stdout。
- 仍需在一台干净 Windows 机器上完成实机验收：安装企业签名旧版、发布更高企业签名版本、检查下载、确认安装、核对版本与服务连接。
