# Pivot v0.1.159 发布记录：工作台交互中文化治理与对话侧栏滚轮隔离

发布日期：2026-09-22  
版本来源：[CHANGELOG.md](../../CHANGELOG.md) 顶部版本标题；已同步至 `package.json`、`package-lock.json` 与 README。

## 发布目标

本版本聚焦系统交互细节的精致打磨与高频操作稳定性：
1. **解决滚轮误拦截**：彻底根治桌面端（Electron）中在右侧对话主区域滚动时因指针状态误判导致主区域不滚、反而左侧会话记录列表滚动的故障；
2. **工作台交互与目录全面中文化**：将 Agent 控制台与工具库中的能力目录、内置工具及权限范围（global/admin/user）全面本地化为中文，支持弹窗式快捷目录浏览，优化搜索框基准对齐与焦点自动隐退；
3. **知识库治理层级与交互修复**：规范模态框层级梯度（主弹窗 5600、版本 6200、新建数据源 6300、Alert 7200），解决版本弹窗被遮挡在下层的问题，并补齐全局 `showAlert` 与局域网数据源管理弹窗。

## 核心变更

### 1. 桌面端会话滚轮桥接精准隔离

- **指针状态实时与双重判定**：
  在 `desktop/preload.js` 中新增 `isPointerInsideSidebar` 函数，结合 DOM 包含关系、视口边界坐标（`clientX/Y`）、侧栏折叠状态（`sidebar.classList.contains('collapsed')`）以及是否有模态弹窗进行严谨判定。
- **消除状态卡死与即时同步**：
  在 `document.addEventListener('pointermove')` 与 `pointerdown` 中补充移出侧栏时的置 `false` 逻辑，在 `wheel` 判定不命中会话列表时即时复位；移除 `setSessionListPointerInside` 中的 `requestAnimationFrame` 异步延迟，状态发生变化时立即调用 IPC 发送至主进程，保证主进程 `before-mouse-event` 零延迟获取最新状态，不再错误调用 `event.preventDefault()`。
- **侧栏折叠防护与滚动链隔离**：
  侧栏折叠状态主动向主进程上报 `active: false`；在 `client/chat/sidebar.js` 中拦截折叠侧栏的滚轮事件；在 `client/chat/styles/layout-refresh.css` 为 `.message-container` 添加 `overscroll-behavior-y: contain;`，防止滚动边界穿透。

### 2. 能力与工具目录全面中文化与体验升级

- **目录弹窗化展示**：
  Agent 控制台“可用技能与能力目录”支持通过按钮以专属模态弹窗形式弹出，提升首屏核心面板空间利用率。
- **卡片与范围标签全面汉化**：
  - 能力与工具卡片上的范围标识（`global`、`admin`、`user`）全面显示为“全局”、“管理员”、“个人”；
  - 运行状态统一本地化为“已启用”、“未启用”；
  - 工具库可用工具目录弹窗卡片全面中文化，内置能力（浏览器检查、资料库检索、渐进式发现工具等）均配备符合中文习惯的友好名称与参数说明。
- **搜索与输入交互优化**：
  - 搜索框内的提示语（Placeholder）与前面的放大镜图标垂直居中严格对齐，搜索框与操作按钮保持在同一水平线；
  - 输入框支持光标聚焦后提示语自动隐退，提供纯净专注的输入体验。

### 3. 知识库使用与治理模态框梯度治理

- **模态框层级梯队规范**：
  - 知识库治理主工作台：`z-index: 5600`
  - 文档历史版本弹窗：`z-index: 6200`
  - 新建数据源弹窗：`z-index: 6300`
  - 全局通用 Alert 详情弹窗：`z-index: 7200`
  彻底解决文档版本弹窗渲染在主弹窗下层导致无法交互的问题。
- **补齐全局统一提示弹窗 `showAlert`**：
  在 `client/chat/app/dialogs.js` 实现 `window.Pivot.legacy.showAlert(title, message)`，为“同步记录”、“版本差异对比”、“评测详情”等功能提供标准的轻量对话框展示。
- **局域网数据源管理增强**：
  后端接口增加 `GET /knowledge/sources?kind=lan` 过滤，精准展示局域网受控来源；新增独立的新建数据源模态框，内置类型引导与标准参数模板。

### 4. 大型历史知识库升级不再阻塞启动

- **根因分析**：
  旧版本库中的 `knowledge_chunks` 可能存有大量历史分块，且 `embedding` 列在更早版本中可能是保存向量文本的 `text`。产品化迁移曾试图在启动事务中转换列类型或回填全部 `embedding_dimensions`、`embedding_profile`。即使不再重写列，整表 `UPDATE` 仍可能超过 `PG_STATEMENT_TIMEOUT_MS`；事务回滚后容器每次重启都会重复这一过程。
- **迁移策略**：
  - `202609200004_knowledge_product_foundation` 仅补齐结构并创建新增产品化表，不再扫描、转换或回填既有 `knowledge_chunks`；
  - 存量 `TEXT` 与 `vector` embedding 原样保留。检索层对形如 pgvector 文本的历史值执行受限、安全的显式转换；异常历史值不会中断整次检索；
  - 新生成的分块始终写入正确的 `embedding_profile` 与 `embedding_dimensions`，可继续使用相应的部分 HNSW 索引；未回填的历史分块通过有限兼容候选参与检索，后续可在受控窗口按业务需要重建索引；
  - `knowledge_chunks_block_fk` 与 `knowledge_docs_source_fk` 以 `NOT VALID` 挂载：不会在升级启动时扫描历史表，但继续约束迁移后的新增或更新数据。
- **运维结果**：
  - 若旧镜像已因 `57014`（`statement timeout`）失败，迁移事务已回滚且不会登记在 `schema_migrations`；部署含本修复的新镜像后可直接重试；
  - 不需要、也不得通过删除表/列、修改 `schema_migrations`、清空 `knowledge_chunks` 或手工 `ALTER ... TYPE vector` 来“解锁”升级；
  - 不能仅靠提高 `PG_STATEMENT_TIMEOUT_MS` 解决该问题；这会让启动继续等待全表工作，而不是消除根因。完整生产检查步骤见 [PostgreSQL 主库运行与升级说明](../生产环境PostgreSQL主库运行与升级说明.md)。
