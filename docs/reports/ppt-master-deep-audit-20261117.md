# PPT Master 用量、轮询与制作链路深入检查

日期：2026-11-17。审查源码基线：v0.7.167 / `d1afc6a5`；本机固定 PPT Master 包为6.8.0、修订 `769547394107870a0c7b5ad8d1c0c75035123aef`。

本轮只检查并形成报告，没有修改 PPT 业务代码。保留前一轮技能修复的未提交改动。用户已说明截图来自生产环境；本机数据库只读查询未找到 PPT Master 任务，尚无生产任务ID、逐轮记录及提供方账单，因此不能断言截图中的691,255 Token被重复扣费。

## 主要结论

1. “查看每轮模型用量”自动关闭已经真实浏览器复现：每1.5秒任务轮询重建状态区，原有 details 节点及展开状态被删除。
2. 正常返回有效非零 usage 的路径，未发现同一响应被任务累计两次。模拟3次响应，每次111输入+22输出，累计399，记录3条。任务累计与全局模型统计是两个统计范围，不应把两者再相加。
3. 发现独立的估算口径错误：上游缺少 usage 时，全局模型统计把图片Base64当作文本估算；明确返回0也被当作缺失值。任务统计采用另一套规则，导致严重不一致。
4. 高输入开销确实存在：固定流程全文、历史读取结果、输入图片持续进入后续请求。以下量化是项目估算器结果，不是生产实测分词、供应方计费或节省承诺。

## 用量实测与口径

使用真实驱动的启动逻辑、本机完整固定指引和确定性模型替身，未调用真实收费模型：

| 基础输入 | 项目估算 Token |
| --- | ---: |
| SKILL.md | 5,397 |
| workflows/routing.md | 7,450 |
| workflows/generate-pptx.md | 23,749 |
| 三份常驻文件合计 | 36,596 |
| 加宿主协议与一个简单任务后的首轮输入 | 39,142 |
| 以上基础输入重复15次 | 587,130 |

这还不含后续模板、策略、设计规范、素材、历史工具结果及输出。该结构足以解释为何“页面尚未开始生成”就可能累计大量输入，但不能据此还原该生产任务的真实账单。步骤数也不严格等于调用数：响应已返回并记账后，若发生截断或格式错误，步骤计数可能尚未增加。

另以一张173,878字节的有效JPEG和同一模型响应复现两种统计口径，使用无效账号/模型标识保证只计算返回值、不写入实际用量账本：

| 提供方 usage | 任务累计 | 全局统计入口累计 |
| --- | ---: | ---: |
| 缺失 usage | 1,055 | 116,008 |
| 输入明确为0、输出为10 | 10 | 116,003 |
| 输入100、输出20 | 120 | 120 |

这证明平台额度统计可能高估，尤其是图片输入且提供方未返回有效用量时；它不证明提供方重复收费，也不能直接解释截图中任务侧的691,255。缓存命中数、总输入Token和实际收费金额应分别展示。

## 确认问题

### F01 · P2：轮询重建折叠控件，展开后立即失效

- 位置：[apps-workbench-presentation-master.js:260–287](../../client/chat/apps-workbench-presentation-master.js)。
- 触发：任务状态为working，用户展开每轮用量。
- 实际：`poll` 每1500ms调用 `renderTask`，后者先 `panel.replaceChildren()` 再新建 details。浏览器复现结果为展开前后 `true → false`，不是点击事件冲突或任务本身结束。
- 影响：无法持续查看长明细，阅读位置和键盘焦点也可能随节点重建丢失。
- 最小修复：以任务ID保存并恢复展开状态、滚动位置；优先保留固定节点，只更新变化的数值和新增用量行。切换任务或账号时再清理状态。
- 补测：working任务连续至少三次轮询，保持展开和阅读位置；主动收起后不被自动展开。

### F02 · P1：图片回退估算与零用量处理导致全局统计虚高

- 位置：[agent-model.js:404–412](../../server/services/agent-model.js)、[provider-usage-calibration.js:37–42](../../server/services/provider-usage-calibration.js)；对照[任务记账 context.js:66–79](../../server/services/presentations/master/context.js)。
- 触发：上游不返回输入用量，或明确返回0；请求包含图片Data URL时放大最明显。
- 实际：任务侧以消息结构估算图片，全局侧对整个 `JSON.stringify(providerMessages)` 估算，图片编码被当成正文；全局 `usageInput > 0` 又把有效0替换为估算。复现数字见上表。
- 影响：同一次调用在任务预算和用户模型额度中计入不同数量，可能过早触发模型日额度，无法可靠对账。
- 最小修复：统一有效用量解析和多模态估算规则，保留有效0；明确区分缺失、估算、提供方实际返回及缓存用量。不要从Base64字符数直接推断视觉Token。
- 补测：有效非零、有效0、缺失字段、部分usage和真实图片输入；任务、运行预算、全局额度与展示使用一致口径。

### F03 · P2：普通文件读取忽略 length，无法真正缩小范围

- 位置：[docker/ppt-master/runner.py:174–180](../../docker/ppt-master/runner.py)。
- 触发：模型使用允许的 `read` 动作指定较小length读取长材料；读取反馈提示缩小范围时尤其容易发生。
- 实际：真实运行器接受请求 `offset=10,length=1000`，却返回60,000字符，nextOffset为60,010。相邻 `read_runtime` 正确使用length，两个入口语义不一致。
- 影响：本可只读短片段的请求带入大段材料，增加后续每轮输入，也更容易触发批量结果截断。
- 最小修复：普通read与read_runtime复用有界分页参数及响应字段，按实际返回长度推进游标。
- 补测：小length、默认值、越界offset、负数、超上限、Unicode材料及完整分页重组。

### F04 · P2：批量结果按字符串截断，破坏结构并使上下文压缩失效

- 位置：[driver.js:113–125](../../server/services/presentations/master/driver.js)、[context.js:17](../../server/services/presentations/master/context.js)。
- 触发：一个合法动作批次的观察结果超过90,000字符，例如写入一页后读取两份长材料。
- 实际：程序将序列化后的整个数组直接slice，再追加说明，得到不可解析的JSON。驱动复现中，第三次请求仍携带已经成功写入的第一轮长正文，`compactedWrites=0`；结果缺项也没有结构化游标。
- 影响：模型无法可靠获知后续动作结果，容易重读和重做；压缩器解析失败后整条跳过，额外放大重复输入。
- 最小修复：在序列化前按结构控制返回量，保留每个动作状态、路径、摘要和分页引用；完整结果保存在受控存储。不得截断JSON外壳或丢掉写入成功回执。
- 补测：混合write/read批次超限、后续动作失败、分页续读；保证JSON有效、回执可核对、已落盘正文仍可安全压缩。

### F05 · P1：当前完整工作流要求的必要工具未接入宿主

- 位置：[工具白名单 tool_catalog.py:6](../../docker/ppt-master/tool_catalog.py)、[驱动宿主协议 driver.js:21](../../server/services/presentations/master/driver.js)。固定包 `workflows/generate-pptx.md:251` 要求在首张SVG前使用 `scripts/text_measure.py calibrate ... --outline` 生成文字度量校准；该文件真实存在。
- 触发：按当前默认Generate工作流进入页面绘制前的强制文字校准步骤，包括模板制作。
- 实际：运行器没有登记text_measure；直接使用受控命令解析器请求该工具被拒绝，已有project子命令也没有对应校准入口。不能通过宿主提供的动作完成该规定步骤。
- 影响：完整工作流与实际可执行能力不一致，模型可能停下、查阅更多指引或尝试替代动作；无法据此声称完整落实上游制作规范。尚无该生产任务动作日志，不能断言截图任务已在此处反复失败。
- 最小修复：对固定发行包的强制步骤做能力契约检查，补齐所需的受限工具及参数校验，或明确提供等价的受控适配。保留工作区、超时、输出和网络限制，不能以开放任意Shell或跳过质量门禁解决。
- 补测：使用真实固定包走完模板规划、校准、SVG、检查和导出，不仅用“工具返回成功”的替身判断整条流程可用。

### F06 · P2：一次轮询失败后永久停止刷新并移除停止按钮

- 位置：[apps-workbench-presentation-master.js:153、260–264](../../client/chat/apps-workbench-presentation-master.js)。
- 触发：制作过程中一次任务状态请求遇到短暂网络或服务故障。
- 实际：异常进入showError并清空状态区；下一次定时轮询没有被安排。浏览器夹具第二次请求失败后，继续等待超过两个轮询周期，仍只发出2次请求，停止按钮数量为0。
- 影响：后台制作可能继续消耗模型额度，但用户在当前窗口无法观察进度或直接停止。
- 最小修复：保留最后成功的任务状态与停止入口，增加有界重试和手动刷新；任务、账号和弹窗生命周期变化时使旧响应失效。可参考已有原稿编辑轮询恢复实现。
- 补测：一次失败后恢复、连续失败、关闭窗口、切换任务、取消期间迟到响应。

## 恢复和结果回看缺口

### F07 · P2：选择新模型后“继续”仍使用旧模型

- 位置：[前端 master.js:330–333](../../client/chat/apps-workbench-presentation-master.js)、[后端 tasks.js:164–174](../../server/services/presentations/master/tasks.js)。
- 触发：旧模型输出截断/不可用，界面提示可切换模型后继续；用户改选模型并点击“从检查点继续”。
- 实际：浏览器复现选中模型2，但续跑请求仅携带预算和步骤；后端同样仅更新这两项，保留模型1。
- 影响：用户认为已经换模型，实际继续遇到原模型限制并可能再次消耗额度。
- 修复选择：若支持换模型续跑，显式传入并重新检查授权、视觉能力、上下文和输出限制；否则锁定选择器并明确说明需重新创建任务，不能给出无效的换模恢复指引。

### F08 · P2：关闭后重新进入制作，已完成任务的下载入口消失

- 位置：[master.js:212–218](../../client/chat/apps-workbench-presentation-master.js)；关联[交付 delivery.js](../../server/services/presentations/master/delivery.js)及[文稿列表 presentation-service.js:201](../../server/services/presentations/presentation-service.js)。
- 触发：任务已经完成，关闭制作窗口后重新打开或重载页面。
- 实际：latest返回completed也被忽略，界面显示“服务就绪”；浏览器复现不再出现下载按钮。完整制作交付登记为独立产物，普通文稿列表读取presentation_documents，不会因此自动成为同一个列表项。
- 影响：制作应用缺少稳定的完成任务回看与再次下载路径。此处不是文件已被删除，也不否认其它产物管理接口仍可能访问到已登记文件。
- 最小改进：增加按账号分页的制作任务历史，或提供“查看最近完成结果”；新建表单清空与结果历史应分开处理，下载继续复核当前权限。

## 上下文优化方向

1. **分阶段加载权威指引。** 当前三份基础全文约36,596估算Token常驻后续所有请求。应把固定版本、阶段、确认门禁和已确认设计约束显式持久化，保留当前阶段必需规则；参考资料按需加载。不能简单裁剪必需约束或把未经验证的摘要当成完整事实。
2. **对只读结果去重、按引用重读。** 目前只压缩摘要匹配的旧write正文，重复read/read_runtime结果完全不压缩。夹具中重复读取后输入估算60,178，压缩后仍为60,178。可按运行包版本、路径、页范围和内容摘要复用相同读取；变化的项目文件必须重新验证，原始证据保留在检查点或受控文件中。
3. **区分图片使用阶段并补齐视觉反馈。** `model-input.js` 每轮重读、解码并附加输入图片；没有按阶段或动作选择。可以在确需视觉分析时发送图片，按摘要复用规范化文件；同时补齐生成页面的受控预览读取。当前通用Master驱动只有输入图片回传，交付报告本身也标记officeVisual未检查，不能把文件结构校验等同于页面视觉验收。
4. **让逐轮账目可对账。** 保存任务ID、调用ID、模型身份、提供方返回用量、估算方法、缓存观测和失败原因。明确步骤数与调用数的区别，说明历史列表保留范围；避免只显示一个无法追溯的累计数。性能优化应以同一任务材料、模型和质量门禁做前后对照。

建议顺序：先修折叠与轮询恢复、统一用量口径；随后修分页读取和结构化观察；再补齐工作流强制工具并建设阶段上下文；最后完善换模恢复、任务历史和视觉反馈。
