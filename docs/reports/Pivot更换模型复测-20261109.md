## 已确认的问题

### 风险筛选字段与工具目录不兼容

触发条件：模型在 tools.search 填写 Schema 明确接受的 `riskLevel=low`（或 medium/high/critical），工具已通过目录规范化。

- [agent-tools-discovery.js](../../server/services/agent-tools-discovery.js#L116) 向模型暴露的风险枚举是文字等级。
- [agent-contracts.js](../../server/services/agent-contracts.js#L75) 通过 normalizeRisk 把工具风险转换为 0—5 的数字，并写入 risk_level。
- [tool-discovery.js](../../server/services/tool-discovery.js#L38) 却把风险筛选和 tool.risk_level 直接转字符串比较。例如 low 与 1 不相等，因此相应候选被全部排除。

独立本地源码复现：同一个已规范化的 mcp.1.workspace_read 目录项，仅按 source=mcp 搜索可命中；增加 Schema 合法的 riskLevel=low 后返回空；内部数字筛选 1 可命中，但 1 不在对模型暴露的风险枚举中。该复现没有修改产品，也没有执行业务工具。

最小修复方向：统一搜索入口和目录的风险等级表示，复用已有 normalizeRisk，并明确筛选是精确等级还是风险上限；同步候选摘要，补上真实 normalizeToolContract → rankTools 的集成回归。不能用扩大工具授权或删除治理检查代替修复。

### 能力筛选和错误恢复加重了问题

本轮搜索还多次把自然语言能力描述（例如“读取订单与退款数据”“文件”）填入 capability；[matchesFilters](../../server/services/tool-discovery.js#L44) 对该字段按能力标识精确匹配，因而返回空。其 Schema 只是无说明的字符串，没有给出当前目录的合法能力标识或说明可省略。部分调用把 source 限为 builtin/api_operation，进一步排除了本轮 MCP 工具；也有 source=mcp 的调用，仍因风险/能力筛选返回空，不能只归因为选错来源。

独立复现中，对同一工具使用自然语言 capability 返回空，使用已登记的 network.request 可命中。这里的问题是输入含义和反馈不足，不能把自然语言直接当成授权能力标识，也不能默默放宽用户明确的安全限制。

搜索结果同时报告 totalAuthorizedTools=9，说明并非本轮没有登记业务工具。但 [agent-discovery-progress.js](../../server/services/agent-discovery-progress.js#L9) 只累计空结果，达到上限即终止；没有在当前授权边界内反馈“过滤条件不匹配”的原因或帮助模型重新选择。EX01 最后把故障解释为“请启用读取和交付工具”，与实际已有 9 个授权工具不一致。

建议提供有类型约束和说明的可选能力筛选、有效条件/空结果原因，并在原授权和剩余预算内引导修正模型自选过滤条件。最终提示应区分“目录确实缺能力”和“有授权工具但检索条件未匹配”。
