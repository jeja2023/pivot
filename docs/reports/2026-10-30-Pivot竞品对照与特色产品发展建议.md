# Pivot 项目与前沿产品对照及特色产品发展建议

日期：2026-10-30；项目基线：`v0.7.69`，Git `495f2db9`。

> 方向更新：当前优先把基础能力做实，不以“可信闭环”或特定行业场景作为第一阶段目标。实施顺序和验收以 [基础能力做实与分阶段执行方案](2026-10-30-Pivot基础能力做实执行方案.md) 为准；本文保留竞品对照及中长期参考。

## 一、结论与检查范围

建议定位为**面向组织内网的可信工作智能体平台**：用户交办任务后，系统在授权范围内查找资料、调用工具、形成可审阅的结果，并在必要时等待人工批准，留下可追溯证据。

优先做深一个完整业务场景：**制度依据驱动的材料审查与报告交付**。用户上传制度、表格和文档，系统核验适用范围、定位证据、列出冲突和缺漏，生成审查报告与待确认操作。差异化组合来自内网部署、中文办公资料、权限一致性、任务恢复和证据交付。该定位是建议，须通过真实用户试点验证市场需求。

本次检查覆盖项目目录与配置、README、设计与验收文档、关键权限/任务/知识库/部署实现，以及自动治理报告；对九类产品的比较基于截至 2026-10-30 可访问的官方资料。检查并非逐行审计所有文件，没有进行真实企业用户访谈、生产压测、渗透测试或对竞品相同任务的实测。代码与测试存在代表能力基础，不等于现场部署已完成验收；不把产品描述、规划、自动化测试和生产证据混为一谈。

项目当前有 2532 个 Git 跟踪文件，其中服务端 908、客户端 439、桌面端 54、测试目录 488；治理脚本统计 1190 个生产 JavaScript 文件、9 个超过 1000 行的存量文件和 87 个按脚本口径计数的 E2E 测试。数字仅反映规模和治理脚本口径，不代表业务正确率。

## 四、建议的产品结构

### 4.1 普通用户：统一工作入口

一个交办输入框支持引用已授权的文件、知识库和数据源。任务进度只显示用户需要的信息：正在做什么、已得到什么、需要用户提供什么、批准将影响哪里；完成时展示摘要、来源、文件和未完成事项。

建议沿用现有会话、任务、自动化、知识库和工具库导航。任务卡片不自动宣称完成：每一结论和产物应能回到具体版本、页码或数据查询，证据不足时标注缺失并允许用户补资料。

### 4.2 业务管理员：流程与知识治理

把自然语言生成的流程保存为草稿，节点展示输入、输出、失败处理、成本及副作用。管理员以真实样例测试、比较不同版本、确认数据与工具授权，再发布或回滚。知识库应展示采集状态、质量、权限继承、更新时间和检索测试；更新或撤销后，缓存和衍生产物的可访问范围要同步变化。

### 4.3 系统管理员：控制与运维

集中展示模型与连接状态、权限来源、队列和 Worker、任务成本、失败和待确认事件、备份及恢复证据。组织/租户能力按照实际接线状态显示，缺失时给出明确限制；不能让规划项表现为已经部署。安全策略至少覆盖身份、权限、凭据、网络、执行位置、用户授权和结果交付。

## 五、优先级与实现建议

以下顺序按风险与用户价值排列；工期取决于团队人力和业务样例，未经过估算。

### P0：可信基础与一个可验收的任务闭环

1. **确定场景与金标**：选一个有真实资料、业务负责人和处理量的场景；先由负责人确认 30–50 条脱敏案例、各类困难案例及不应执行的反例。建议从制度审查入手，也可根据实际需求换成材料汇总。交付物：输入/输出规范、禁止事项、验收集、基准记录。
2. **统一任务结果页**：复用现有 chat feed、事件、产物、审批与任务控制；展示状态、时间线、引用、交付文件、遗漏和用户下一步。验收：刷新、断线、切换设备不丢状态；取消/恢复行为真实可追溯；没有核验不显示已核验。
3. **证据链和权限闭环**：每条重要结论绑定来源版本、位置、引用范围、读取权限与可用状态；原资料失效或授权撤销时不再展示受限正文。验收：跨用户、跨单位、撤权后读取/缓存/导出回归；事实、推断、缺依据分别展示。
4. **副作用与恢复**：沿用任务事务、授权和工作树能力，先显示拟修改目标与差异，再由授权者决定提交；外部写入超时标记结果未知并人工核实，不自动重复。验收：重启、重复请求、审批过期、网络断开和并发争抢演练。
5. **消除功能误认**：保留历史接口门禁，核对外部调用方；修复入口说明及迁移文档，只有真实数据访问、权限和恢复回归通过后才开放。
6. **建立最低交付与观测线**：记录成功、部分完成、失败、取消、未知、人工接管、耗时、模型与工具版本、预算及审批延迟；定义样本量和统计口径。将异常回放、恢复演练与发布准入绑定，低样本显示“证据不足”。

### P1：业务资产复用与管理效率

7. **流程资产**：允许将已完成任务转成流程草稿，复用现有版本、依赖、发布、灰度与回滚；至少给出参数、权限、外部影响和一次试运行结果。不要把自由聊天历史直接发布为工作流。
8. **知识质量工作台**：导入前后显示类型、页数、识别覆盖、缺页、来源、引用定位和失败原因；支持差异重建和标注集回放。以实际数据量测量检索质量和时延，再决定是否引入外部解析器。
9. **记忆与技能治理**：记忆分个人偏好、工作上下文和待复核候选；技能分草稿、验证、发布、停用。每条都有来源、有效期、作用范围、撤销和版本差异；组织级内容由授权管理员确认。
10. **连接器产品化**：先把文件/共享目录、只读数据库和 HTTP/MCP 做稳定，再按目标客户验证需求选择一两个 OA/邮件/消息系统；提供健康、权限、限流、凭据轮换、版本契约和真实系统测试。外部消息发送仍须明确授权。
11. **模型路由质量**：在现有上下文、视觉、成本、负载及升级策略上，用可追溯实际样例比较成功率、成本、P95 和失败恢复；固定模型做对照。决策 v2 人工标签未完成前不宣称有有效金标或扩大主动灰度。

### P2：企业规模化与生态

12. **统一组织身份与隔离**：先定义单组织、部门共享和多租户的目标客户与边界；按数据、凭据、索引、缓存、事件、日志、备份逐层验证。SSO、目录同步、策略继承和跨租户迁移应以已接线能力及现场验收为准。
13. **执行面和多节点**：为文件处理、浏览器及代码执行划分资源池和并发上限，保护主服务；基于 PostgreSQL/共享文件系统先做故障和容量验证。S3、Redis、其他队列仅在明确业务收益及适配完成后引入。
14. **可控生态**：技能/连接器提供版本、来源、签名、依赖清单、权限、样例和撤销；离线包按目标架构验证摘要并留回滚方案。先完善内部资产目录，再考虑外部市场。
15. **多模态与桌面能力**：优先提高中文扫描件、表格和页面定位质量；桌面控制选择有限业务场景，提供预览、显式授权和人工接管。避免把支持接口或模型描述直接当作全自动可靠性承诺。

## 六、首个场景示例：制度依据与材料审查

**输入**：制度文件、需要审查的申请材料、所选部门及明确的任务目标。

1. 用户授权知识库和材料；系统列出文件版本、识别覆盖及适用单位，缺页或识别质量不足时提示补充。
2. 检索并列出适用制度条款及原文页码；对冲突或未找到依据的要求标记待人工核查。
3. 抽取申请材料中的关键字段，展示对应原文位置；结构化检查金额、日期及必需附件，复杂判断给出依据与不确定性。
4. 生成“符合/不符合/待核实”检查表及可编辑报告，用户能点击核对来源并纠正。
5. 如需写入业务系统、发送通知或提交审批，先展示目标、接收人、具体内容及影响，经用户授权后执行；执行结果未知时人工核查。
6. 经用户确认的结果可保存为个人或组织范围的草稿资产；组织发布需要授权和验证，不自动将私有数据转为共享资产。

**非目标**：自动替代业务签批、法律判断或绕过原系统权限。若真实需求是公文审校、报表分析或法规查询，可用同一骨架替换检查规则和结果模板。

## 七、试点评测与验收

建议先设一条小规模试点基线，再由业务负责人确定阈值，而不是直接承诺竞品水平。每条评测保留样本数、输入版本、模型与工具版本、人工标签和失败类型。

| 指标 | 计算或观察方式 | 主要分层 |
| --- | --- | --- |
| 任务有效完成率 | 人工确认目标完成的任务 / 已评审任务；部分完成单独统计 | 场景、模型、资料质量、用户角色 |
| 证据支持率 | 抽检结论中原文实际支持的比例；同时统计无引用和引用失效 | 文档类型、中文表格/扫描件、来源时效 |
| 权限安全 | 越权读取、撤权缓存泄露、错误身份交付等场景的通过数与失败数 | 个人/单位、共享接收者、跨端 |
| 副作用正确性 | 未授权执行和重复执行次数；超时后未知状态是否保留及人工核验 | HTTP、通知、桌面及数据库 |
| 可恢复性 | 人工确认恢复后完成且无重复副作用的比例 | 进程崩溃、数据库/网络断连、审批过期 |
| 性能与成本 | 按成功、部分和失败分别统计 P50/P95/P99、内存、排队、模型 Token 与成本 | 用户数、文件规模、部署机器、模型 |
| 用户价值 | 完成人工处理时间、修改量、接受率与误报；用同一批案例与现行人工流程对照 | 部门、文种、复杂度 |

任何阈值应由业务、安全和运维共同确定；测试通过仍需生产网络、安全和恢复验证。建议利用现有 `docs/agent-experience/metrics-dictionary.md` 与五项证据手册，不重复发明指标平台。

## 八、工程落地与不建议优先做的事

- **入口收敛**：复用现有服务、路由和权限，统一数据契约与界面术语；优先删除失效入口和重复流程。不要为对照每个竞品引入另一套 Agent/RAG/工作流引擎。
- **可维护性**：9 个存量大文件按真实职责逐步拆解，先补行为测试；276 个 legacy 全局别名按调用迁移而非一次性替换。不要以行数推断性能或代码质量。
- **验证分层**：静态检查、真实 PostgreSQL、浏览器、独立 Worker、网络隔离、真实业务系统和生产灰度分别记录；不要把 CI、模拟模型或本机基准写成生产成功率。
- **安全治理**：坚持最小权限、确认可审阅的具体外部影响、撤权即时生效、禁止自动重试结果未知的非幂等动作。模型判断、网页内容和生成技能都不能覆盖确定性安全边界。
- **资源与成本**：用户此前展示的服务器为 Linux x64、40 个逻辑核心、约 251.53 GB 内存，适合规划单机或分进程试点，但截图不能证明 GPU、磁盘性能、模型吞吐、并发容量或生产资源配额。按现场实测决定 CPU 密集解析和 Worker 并发。
- **授权与依赖**：借鉴公开设计应核对各项目许可证及版本；商用代码、标识、协议和第三方服务成本须单独评估，不应假定所有功能都可免费离线使用。
- **不优先**：完整通用 Agent 市场、无限制自治/自修改、多模型自动互换结果、宣称全覆盖办公自动化、在没有用户与样例前大规模重写架构。这些都容易放大验证、权限和运维成本。

## 九、推进建议

1. 选定一个试点部门和场景，确认负责人、授权数据和验收样例。
2. 审阅现有任务、知识、权限和交付路径，建立真实基线；输出待办、风险和不应自动执行清单。
3. 做通一个任务闭环并完成故障、越权、撤权及真实文件格式验证。
4. 小范围试用，记录实际修改量、完成时间、证据质量和失败类型；按结果决定是否扩大到其他部门。
5. 再决定组织级身份、多节点和行业连接器的投入，不把架构预留当成已验收能力。
