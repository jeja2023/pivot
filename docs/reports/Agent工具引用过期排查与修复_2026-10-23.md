# Agent 工具引用过期排查与修复记录

日期：2026-10-23。状态：本地修复与针对性验证完成，尚未部署生产。

## 第二轮检查：搜索、契约与任务要求提示

用户后续提供的截图为 `tools.describe` 失败，原文是“请先使用 tools.search 获取当前已授权工具的 toolRef，再读取其契约。”，并反馈还经常出现要求读取工具契约和补充任务要求。它属于 `TOOL_DISCOVERY_SEARCH_REQUIRED`，与发布版本过期是不同的发现状态错误。

前一轮修复已覆盖 describe 缺失搜索状态和过期引用；继续检查又确认以下问题，本次一并处理：

1. **控制步骤被业务范围拦截。** 目录层保留了发现元工具，但策略层仍要求这些元工具出现在业务工具白名单、Skill 工具声明和业务能力集合中。只读任务还会因 `tools.execute` 这个路由工具自身不是幂等业务读取而拒绝它，导致模型无法完成必要的内部步骤。现仅把可信内置发现元工具作为控制步骤处理；搜索与 describe 的业务候选按原任务、会话和 Skill 范围过滤，嵌套的真实业务调用仍接受所有原限制。
2. **JSON 白名单解析不一致。** 目录支持 `["rag.search"]` 这类持久化 JSON 数组，原策略层却按逗号切分为包含方括号和引号的字符串，实际工具名无法匹配。现两种格式一致处理；未知目标仍拒绝。
3. **缺少契约时只抛错误。** 普通及流式预检查会在进入元工具之前抛出“先读契约”，即使契约可以由服务端安全读取。现先返回 `type: tool_contract_required`、`executed: false` 和当前完整契约，由智能体下一次显式调用确认；首次请求和批处理恢复期间不会执行任何业务动作。执行前契约校验的旧引用可以采用相同方式恢复，业务工具执行之后的错误不进入此恢复流程。
4. **等待处理状态文案误导。** `needs_input` 也用于空答案、文件未生成、来源不足、格式不合要求和验收服务不可用等情况。原界面一律提示“请补充要求后继续”。现优先展示实际核验原因，并改用“待处理事项”；不会把内部步骤问题直接描述为用户未给清楚任务。确实缺少资料、目标、业务条件或授权时仍保留对应阻断。

另外，执行预检查读取当前授权目录中的工具对象作为审批对象，避免使用运行开始时旧目录中的风险和审批属性。

内置工具的后备定义摘要还补入副作用、幂等、审批、网络、超时、认证范围及数据连接信息，并采用稳定键顺序。副作用或审批要求变化后，旧摘要必须失效；单纯 JSON 对象键顺序变化不会造成误报。

第二轮先完成 113 项相关回归，随后追加流式“先返回契约、下一轮才执行”及后备摘要用例。最终相关 71 项全部通过。本地没有生产原始运行记录，因此本报告不声称已还原每一次生产失败。

## 已确认的问题

### 1. 旧引用在读取契约时无法恢复

`tool-discovery.js` 的 `describeToolForUser` 会比较请求中的 `releaseId`、`definitionDigest` 与当前授权目录。发布版本或定义摘要不符时返回 `TOOL_REFERENCE_STALE`；截图文案对应发布版本比较。

这一严格检查应当保留，尤其用于执行边界。问题在上层 `agent-tools-discovery.js`：此前只处理“尚未搜索”，补全缺失字段；模型显式传入的旧版本或错误版本会一直保留。即便重新查询了最新目录，再次 describe 仍可能带着旧值失败。发现状态过期也没有进入恢复分支。

可触发的情况包括：目录在搜索与读取之间切换、续跑上下文仍携带旧引用、模型写错版本号。一个 MCP 服务的发布号覆盖整个目录，因此另一工具变化也可能使目标工具的发布号更新，而目标定义摘要保持不变。

### 2. 旧执行引用可能残留

原发现状态在收到完整 `catalogVersion` 变化时会整体失效，但内部补查只记候选引用，没有目录版本。同名工具更新后，旧精确键仍可能留在 searched/described 集合，且精确键优先命中。

实际执行仍会再次读取当前授权目录并拒绝旧版本，因此这不是放行旧契约的问题；残留状态会导致反复进入失败路径，妨碍恢复。

### 3. 返回引用与输入 Schema 不一致

内置工具和没有目录发布记录的本机工具通过 `toolRef()` 返回 `releaseId: null`。但原 `tools.describe`、`tools.execute`、`tools.batch_read` 的对应输入字段只声明整数，模型原样复制服务器返回值会在统一策略层被拒绝，尚未进入引用恢复代码。

### 4. 需要区分两种错误保护

普通执行与流式执行都会把未恢复的工具失败计入任务连续错误预算，默认上限为 3；重复同一调用也有停止保护。这说明反复 describe 失败可能阻断任务。

工具服务的独立熔断器只累计临时故障，例如 429、5xx 和网络异常。`TOOL_REFERENCE_STALE` 是 409，不属于其临时故障分类。因此不能把截图中的后续“自适应熔断切换”直接解释成该服务熔断器被引用错误触发。当前源码也没有该标题的固定文案；需要生产运行记录确认它是控制步骤、模型输出，还是其他版本实现。

## 本次修复

- `tools.describe` 先重建用户当前授权目录，并固定一次快照。旧引用只允许在读取契约时刷新，最多进行一次按名重读，不循环拉取变动目录。
- 返回最新完整输入输出契约、风险、幂等性与审批要求；通过 `referenceRefresh` 返回刷新原因、先前引用和后续使用要求。
- 更新发现目录摘要，清除旧授权目录状态；同名候选替换时同步移除旧搜索、描述和过期时间记录。
- 对过期发现状态重新查询当前目录并读取契约。不存在、停用或无权访问的工具仍拒绝返回契约。
- 三个引用输入 Schema 接受整数或 null，与服务器产出的引用一致；错误的字符串版本仍被拒绝。
- `tools.execute` 和只读批处理继续严格核验。契约变化不会自动重放业务动作，写入与审批要求不会被自动刷新绕过。

普通和流式 Agent 共用上述元工具实现。流式测试额外检查刷新结果确实进入下一轮模型消息，且不产生工具错误记录或原生工具降级。

生产复测应新建同类对话任务。存在写入、发送或删除步骤的旧任务，先核对其执行记录，避免把已完成动作从头执行。

现场应保留失败运行的版本号、运行 ID 和相邻步骤，以区分目录切换、模型错误引用与模型端点故障。以下 PostgreSQL 查询仅展示核验所需字段；在只读会话中运行，将 psql 变量替换为实际运行 ID：

```sql
\set run_id '替换为实际运行ID'
BEGIN READ ONLY;
SELECT id, status, model_id, chosen_model_id, error_message,
       started_at, completed_at
FROM agent_runs WHERE id = :'run_id';

SELECT step_index, type, title, tool_name, status, created_at,
       pivot_json_extract(input, '{toolRef,toolName}') AS requested_tool,
       pivot_json_extract(input, '{toolRef,releaseId}') AS requested_release,
       pivot_json_extract(input, '{toolRef,definitionDigest}') AS requested_digest,
       pivot_json_extract(output, '{toolRef,releaseId}') AS returned_release,
       error_message
FROM agent_steps WHERE run_id = :'run_id'
ORDER BY step_index, id;
COMMIT;
```

再根据工具名中的 MCP 服务 ID，核对 `tool_catalog_releases` 的发布号、状态和发布时间是否落在任务搜索与 describe 之间。若后续控制步骤指向模型切换，还需结合对应时段的模型请求事件与 HTTP/网络错误判断；不能用工具引用报错替代模型故障证据。
