# 开源工具离线移植与深度集成指南审查报告

## 1. 审查结论与范围

**总体方向基本合理，但当前指南存在可复现的执行错误、能力现状偏差和交付步骤缺漏，不能认定为“正确完善”，也不适合直接作为生产实施 SOP。**

可以保留的方向包括：复用 Pivot 已有 Agent 运行时；优先集成单点引擎；在联网准备端构建离线镜像；通过受控 MCP/HTTP 接口接入；将权限、审批、审计和产物管理作为集成要求。

本次通读指南，核对相关服务端、前端、Docker 配置、技能治理和部署文档，并对指南示例执行针对性验证。审查以当前代码为准；项目内其他说明文档也存在语音部署模式等描述漂移，不能仅靠文档互相引用确认实现。

验证没有启动或变更生产服务，没有安装第三方依赖，没有修改原指南、业务代码或生产配置。本报告是审查结果，不表示第三方引擎已完成真实离线部署与验收。

## 2. 必须修正的问题

### F01 [P1] 转换后的 Skill 示例无法通过 Pivot 自身校验

原指南：第 410—437 行、第 590 行。

对原文示例直接调用 `previewSkillSource()`，得到 `valid: false`，错误为：

```text
技能声明了未登记的能力：code_analysis
技能声明了未登记的能力：workspace_read
技能声明的工具未在平台登记：filesystem.read_workspace
技能声明的能力未覆盖工具 mcp.hermes_tools.run_ast_audit 所需能力（network.request）。
```

此外，运行期 `executeMcpTool()` 只接受 `mcp.<数字服务ID>.<工具名>`，`mcp.hermes_tools.run_ast_audit` 即使通过宽松的前缀登记判断，仍不能被实际执行。

修正要求：

- 从同步后的工具目录复制实际全名，例如实际服务 ID 为 42 时使用 `mcp.42.run_ast_audit`，不能把服务展示名当 ID。
- 使用已经登记的能力。当前普通外部 MCP 工具通常解析为 `network.request`；工作区读取能力是 `filesystem.read_workspace`，对应已登记工具可为 `workspace.read`。能力名与工具名不能互换。
- 明确远端服务内部的代码分析权限、文件权限仍需独立限制；声明网络调用能力不会自动赋予远端读取任意文件的权限。
- 推荐稳定标识放入 `name`，中文展示名放入 `title`；原示例中文 `name` 不是本次预览失败的原因。

代码依据：[技能预览](../../server/services/agent-skill-authoring.js)、[能力注册表](../../server/services/agent-capability-registry.js)、[工具能力映射](../../server/services/agent-tool-capabilities.js)、[MCP 执行器](../../server/services/mcp-client.js) 第 822 行起。

### F02 [P1] FastMCP 启动代码混用了不同接口的参数位置

原指南：第 459—474 行。

示例导入的是 `mcp.server.fastmcp.FastMCP`。所核对的官方 Python SDK v1.x 中，`host`、`port` 是构造参数，`run()` 接受 `transport`、`mount_path`；原文的 `mcp.run(transport="sse", host=..., port=...)` 不符合该接口。

应先锁定 SDK 版本，再按该版本编写和验证。以所核对的 v1.x 接口为例，启动结构应为：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("hermes-tools-service", host="0.0.0.0", port=8501)

# 在此登记真实实现的工具。
if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

这只是启动接口修正，不包含工具实现、鉴权和生产交付。不能将该 SDK 与独立 `fastmcp` 包或其他主版本的接口混用。依据：[官方 SDK v1.x 源码](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v1.x/src/mcp/server/fastmcp/server.py)。

### F03 [P1] 旧式 `/sse` 接入方式与当前 Pivot 客户端流程不匹配

原指南：第 290—296 行、第 491—495 行。

当前 `mcp-client.js` 默认 `protocolMode` 为 `legacy`，不会按标准模式自动初始化。标准模式首先向配置 URL 发送 POST，并可消费同一端点返回的 SSE 响应；这与旧式“先 GET `/sse`、再向服务端下发的 messages 地址 POST”不同。

本次使用遵循旧式入口行为的本机 HTTP 夹具验证，观察到 Pivot 向 `/sse` 发送 POST，随后因无法获得对应 JSON-RPC 结果而失败。已有 Streamable HTTP 测试通过，不能据此推导任意旧 SSE Server 都兼容。

修正要求：优先采用锁定版本的 Streamable HTTP 服务，填写实际 `/mcp` 端点，显式选择 `protocolMode: standard`，并配置双方验证兼容的协议版本。项目现有测试覆盖 `2025-11-25` 会话式路径及 `2026-07-28` 无状态路径；这些覆盖不等同于本次已验收第三方 SDK 服务。

依据：[Pivot MCP 客户端](../../server/services/mcp-client.js) 第 514—640 行、[MCP 传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

### F04 [P1] 所谓 Hermes“安全审计”示例实际只返回固定的成功文字

原指南：第 463—471 行、第 511—523 行。

两个 Python 函数没有读取源码、解析 AST、读取 Git 历史或调用 Hermes 模块。提取函数体并传入不存在的路径，仍分别返回“未发现高危代码注入特征”和“合规良好”。

这会制造虚假的安全结论，不能作为深度实战或端到端验收证据。

修正要求：若保留为协议演示，应明确标为占位示例，返回“尚未执行扫描”，不能返回合规结论。若作为实战，必须列明真实上游仓库、提交、模块路径、依赖及调用函数，并加入“含已知问题样本、正常样本、不存在路径、扫描失败”的验收用例。

还应对抽取模块的运行时依赖作清单；Hermes 部分工具依赖自身注册、后端和生命周期模块，不能默认视为可直接拷走的纯函数。可参照其[实际 terminal 工具源码](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/tools/terminal_tool.py)。

### F05 [P1] Kroki 默认 Mermaid 示例缺少后端组件，适配器也未正确处理响应

原指南：第 303—326 行。

第一，只有 `yuzutech/kroki` 网关不足以支持示例默认的 Mermaid。官方部署要求另外启动 `yuzutech/kroki-mermaid` 并配置 `KROKI_MERMAID_HOST`。网关单容器可用于其自带的其他绘图库。依据：[官方安装说明](https://docs.kroki.io/kroki/setup/install/)、[官方多容器配置](https://docs.kroki.io/kroki/setup/use-docker-or-podman/)。

第二，项目 `safeJsonPost()` 返回完整 Axios 响应，原文 `return { svgContent: response }` 会把响应对象当作 SVG。针对本机 SVG 返回夹具的调用已确认 SVG 文本在 `response.data`。

第三，原适配器未传入调用身份或经过设计的服务端出站授权上下文，默认按空用户检查，无法直接访问私网地址；原示例也缺少响应类型、超时、类型白名单以及对错误状态和响应 MIME 的处理。

修正要求：完整打包网关与所需绘图后端；在 Pivot 的权限及网络策略内调用；读取 `response.data`，显式处理文本响应、状态、超时和大小上限；SVG 入库与展示复用既有清洗流程。不能靠伪造管理员身份或全局关闭 SSRF 来让适配器工作。

代码依据：[安全 HTTP 客户端](../../server/services/safe-http-client.js)、[出站安全策略](../../server/security.js)、[SVG 展示与清洗](../../client/chat/artifact-renderer.js) 第 218 行起。

### F06 [P1] 远端工具缺少文件传递与隔离设计，端口映射还可能绕过 Pivot 治理

原指南：第 477—488 行、第 511—518 行。

示例将 `uploads/demo.py` 作为字符串发往独立容器，但该容器没有任何文件挂载或文件获取接口。Pivot 容器内的路径不会随 JSON-RPC 自动成为工具容器中的文件。即使换成真实扫描器，也无法按此闭环执行。

同时，示例发布 `8501:8501`，没有展示服务端鉴权。部署者修好启动代码并接入真实工具后，能访问该端口的主体可能直接调用工具，绕过 Pivot 的用户可见性、审批和审计链路。

修正要求：定义按用户和任务授权的文件引用协议，由 Pivot 验证归属并暂存最小输入；或者使用受限、只读、按任务隔离的挂载。结果也需经过授权校验回收，不能把整个 `uploads` 或 CAS 目录直接开放给工具。仅容器间通信时移除宿主机端口发布，并配置服务鉴权及允许的调用来源。

代码依据：[附件上传与安全](../../server/upload.js)、[产物渲染权限检查](../../server/services/agent-artifact-renditions.js)、[MCP 传输安全要求](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

### F07 [P2] 三个 Compose 片段没有说明独立使用与叠加使用的区别

原指南：第 303—314 行、第 478—489 行、第 556—577 行。

三个片段均引用 `ai-bridge`，但缺少顶层网络定义。逐一提交给 `docker compose ... -f - config --quiet`，三个均返回退出码 1，错误为 `refers to undefined network ai-bridge`。

如果明确与主 `docker-compose.yml` 叠加，主文件可补齐该声明，此时不能把它判为合并配置必然失败。问题是原文没有提供对应完整命令，也把最后一个片段称为第三方工具的生产配置。

修正要求：独立文件补充以下声明，并说明先创建外部网络；叠加文件则给出完整的 `-f` 参数与启动命令。

```yaml
networks:
  ai-bridge:
    external: true
```

网络互通不需要发布工具宿主机端口。`pull_policy: never` 不等于禁止容器联网；普通 bridge 默认提供外部访问。是否使用专用内部网络或出口防火墙，应按模型、数据库、OCR 和工具的真实通信矩阵设计，避免直接改坏已有共享网络。依据：[项目主 Compose](../../docker-compose.yml)、[Docker bridge 行为](https://docs.docker.com/engine/network/drivers/bridge/)。

### F09 [P2] MCP 接入被夸大为自动完成 UI、CAS 和下载集成

原指南：第 269—278 行、第 499—523 行。

自动发现输入 Schema 只解决工具可发现和可调用的一部分。`agent-artifact-renditions.js` 是基于 Document IR 的渲染与交付服务，不是“任意 JSON 自动变成交互卡片”的通用适配器。

`createRendition()` 需要已有产物 ID、真实用户/租户、工具调用标识和有效 IR。图表使用 `pivot_chart` 等显式结构，表格与文件也有各自的契约；外部 MCP 返回一段字符串或任意路径，不会自动成为指定格式的 CAS 制品或“安全审计卡片”。普通文本产物记录与二进制 CAS/Rendition 应分开说明。

修正要求：将四重嵌入改写为四项待完成的集成工作，并补充“工具返回 → 规范化结果 → 创建/更新 Artifact → 必要时写入 CAS/生成 Rendition → 授权预览/下载”的明确调用与错误处理。第三方容器应通过受控适配层回收产物，不应在架构图中暗示直接写 Pivot 的 CAS 就已完成治理。

代码依据：[Rendition 创建](../../server/services/agent-artifact-renditions.js)、[普通产物记录](../../server/services/agent-artifacts.js)、[渲染格式注册表](../../server/services/document-rendering/index.js)、[图表结构](../../server/services/builtin-mcp-visualization.js)、[前端图表解析](../../client/chat/render-charts.js)。

### F10 [P2] 技能标准、ZIP 包结构和发布流程描述不完整

原指南：第 375—389 行、第 440—447 行。

Agent Skills 标准描述的是包含 `SKILL.md` 的目录，可有 `scripts`、`references`、`assets`；`allowed-tools` 是可选、实验性的空格分隔字符串，版本可放在 `metadata` 中。原表格把顶层 `version` 和数组形式 `allowed-tools` 当作标准固定字段，且承诺正文完全无需适配，并不准确。脚本、相对引用、命令、路径和离线依赖均需逐项检查。依据：[Agent Skills 官方规范](https://agentskills.io/specification)。

当前 Pivot ZIP 解析要求根目录存在 `SKILL.yaml/yml/json/md` 之一，不支持把多个技能目录随意压成一个包就批量注册；包内脚本目录等可执行内容还会受到供应链扫描限制。

`previewSkillSource()` 通过也不等于完整发布门禁通过。发布要核对最近完整验证结果；个人发布与团队/组织共享有不同权限和签名要求，并受发布范围与灰度控制，不是点击发布就“全员生效”。ZIP 安装服务本身也不等于完成发布注册。

修正要求：分别给出单技能 ZIP 目录、签名及信任公钥要求、实际上传接口 `POST /api/agents/skills/package`、创建版本、完整验证、个人发布/组织共享及回滚步骤。

代码依据：[ZIP 解析](../../server/services/agent-skill-packages.js)、[供应链扫描](../../server/services/agent-skill-supply-chain.js)、[上传路由](../../server/routes/agents.js)、[发布门禁](../../server/services/agent-releases.js)、[禁止直接注册](../../server/services/agent-skills.js) 第 99 行起。

### F11 [P2] 离线 SOP 缺少可复现交付与故障验收闭环

原指南：第 530—591 行。

现有步骤可作为离线打包概览，但作为生产 SOP 至少还应包含：

1. 固定源码提交、依赖锁、所有镜像 ID/版本与平台架构，避免使用 `latest` 作为唯一交付标识。
2. 交付完整物料清单及 SHA-256 校验文件，明确模型、配置、浏览器运行时、中文字体和多组件镜像是否齐备。
3. 明确宿主机 Docker/Compose 基线、CPU 指令集/系统架构、可选 GPU/CUDA 兼容条件；Windows wheels 不能直接当 Linux wheels 使用。
4. 给出网络创建、目录预建、UID/GID 权限、运行用户可写路径、`tmpfs` 和配置注入步骤。`user: 1000:1000` 需要按第三方镜像实际支持情况适配。
5. 使用 `docker compose config --quiet` 和离线启动参数，尤其主 Compose 带有 `build` 时应按既有部署要求使用 `up -d --no-build --pull never`。
6. 区分禁止拉镜像与运行期禁止公网出站，给出出口控制和断网冷启动验证，确认没有运行时模型下载、遥测或远端 fallback。
7. 验证普通用户可见性、越权拒绝、审批拒绝及批准、服务鉴权、超时/取消/大响应处理、故障重启和审计可追溯性。
8. 验证真实结果、产物归属、预览/下载及摘要；为 TTS、Diff、图形和抓取分别给出样本与验收指标。
9. 明确停机窗口、数据库及文件同恢复点备份、镜像与配置回退、回滚后核查和更新责任人。

对 OpenAPI 接入，应补充项目现有受控操作导入服务和 UI，说明支持的规范与限制，而不仅提通用 `agent.http`。依据：[OpenAPI 操作服务](../../server/services/workflow-api-operations.js)、[操作导入界面](../../client/chat/mcp-workbench-api-operations.js)。

可复用 [生产环境离线部署](../生产环境离线部署.md) 中仍与代码一致的步骤；语音资料与 Docker 快速指南的模式描述应另行按当前 Dockerfile/Compose 复核，不能直接当权威基线照搬。
