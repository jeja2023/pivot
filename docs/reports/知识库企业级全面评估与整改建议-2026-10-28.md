# 知识库企业级全面评估与整改建议

评估日期：2026-10-28  
范围：当前工作区 v0.7.48 代码及未提交修改，覆盖接入、索引、检索、对话、权限、引用、治理、Wiki、图谱、评测和运维；结合公开产品文档对照。本文是代码审查与有限的本地函数复现，不代表对生产环境的性能、安全或业务质量认证。

## 结论

系统已具备混合检索、受控来源、文档版本和审核、引用、Wiki、图谱、评测与后台索引等较完整的基础，但当前尚不能认定为企业生产级知识可信系统。建议优先处理正文覆盖率、拒答与引用核验、索引重建、来源同步安全，再用真实业务数据建立评测和容量基线。能力强弱应按部署范围、权限和业务目标评估，不以是否复制国外产品的全部功能为标准。

## 已确认问题

### P0：长 PDF 在前 10 页后未建立知识索引

`server/services/rag-documents.js:355` 固定传入 `maxOcrPages: 10`；`server/services/document-processing/text-extraction.js:69` 对所有 PDF 页面先截断，不只限制扫描页 OCR；后续页面即使原本可提取文字也不会入索引。省略信息被拼接到文本，而索引状态按向量覆盖判定，可能仍显示就绪。应分离全部原生文字提取和 OCR 预算，保存总页数、成功页、失败页及字符截断等结构化覆盖信息；不完整时显示部分就绪、支持续处理，避免把系统提示作为正文证据。验收需覆盖原生、多页扫描、混合 PDF、页级失败和超限重试。

### P0：拒答关键词可以绕过事实核验

`server/services/knowledge-grounding.js:237` 只要全文包含“知识库中未找到足够依据”等字样便跳过逐句校验。本地以“知识库中未找到足够依据，但公司批准所有人年假30天。”调用严格核验，结果 `accepted=true`。另外 `server/services/chat-context-assembler.js:645` 在无结果时不启用输出核验，主要依赖模型遵循拒答提示。应将纯拒答与部分回答分开处理，缺证据时由服务端输出受控拒答，带事实的句子始终验证；不能仅凭关键词放行。建立含拒答与未引用事实混写、无源、检索失败及流式输出的回归。

### P0：不完整数据源扫描可能误归档

`server/services/knowledge-sources.js:148` 在达到 `maxFiles` 时停止目录遍历，但 `:374` 仍可按 `syncDeletes` 将未见到的已同步文档归档。外部 Wiki 在 `:375` 对缺失页执行归档时也未使用同一删除开关。数据库同步在 `:515` 限制 1000 条后，`:543` 仍可能据此归档；具体截断与执行器返回行为需进一步验证。应引入完整扫描证明、分页/水位、失败及截断标识，在扫描不完整时禁止任何缺失删除；批量删除预览、比例阈值、隔离和恢复，Wiki 与正文统一遵循同一删除策略。对失败项不应把整体无条件标记为 completed（`:586-590`）。

### P1：显式重建可能没有真正重建

`server/services/rag-documents.js:484` 当源文件哈希不变且原文就绪时直接跳过；批量重建也是同一任务入口（`:603-616`）。因此更换 Embedding 模型、切分配置，或用户试图修复旧索引时，可能只排队但未重算。应区分去重同步与显式强制重建，索引版本包含解析器、切分、模型 profile 及参数，任务结果明确展示执行/跳过原因与新旧版本；验证模型切换、失败重试、原子切换和旧索引保留。

### P1：引用编号与 citation key 未做配对验证

`server/services/knowledge-grounding.js:234` 分别验证编号和 key 是否各自存在，但未确认二者属于同一来源。本地构造 A 为引用 1/key a、B 为引用 2/key b，输出“年假五天。[引用 1 | citation:kb:b]”仍 `accepted=true`。应解析每个引用为编号—key—版本—片段绑定，逐句验证引用对，覆盖缺 key、跨文档串配、过期引用和权限撤销。

### P1：多查询复用同一查询向量

`server/services/chat-context-assembler.js:309-312` 将路由阶段向量传给所有不同检索子查询，`server/services/rag-index/index.js:735` 优先直接使用该向量，导致子查询的向量召回仍按原查询而非子查询计算。应只为与向量对应的查询复用向量，其他子查询批量生成各自向量；对关键词、实体、长问题和多条件案例实测 Recall、延迟与成本。

### P1：专题概览和多轮范围仍有明确边界

当前 `server/repositories/knowledge.js` 的概览仅取最多 12 个开头片段，`server/services/chat-knowledge-catalog.js:73` 每段截 1400 字；虽已声明不覆盖全文，仍可能漏掉关键章节或文档。专题继承只查看最近一条用户消息（`:23-40`），且按名称解析，重复名称、名称含空格、重命名或多轮间接追问不能可靠延续。建议持久化当前会话显式资源 ID 与选择来源、限制生效范围及失效条件，按权限重新校验；概览按文档/章节配额生成分层摘要，显示覆盖文档、页数和未处理原因，避免对未读内容作完整性承诺。

## 产品能力差距与方案

1. **权限与协作**：传统知识文档和专题由 `knowledge-access.js` 实施所有者/超级管理员过滤；产品层另有用户、单位、角色级权限（`knowledge-product-access.js`）。应先明确共享产品语义并统一列表、检索、正文、引用、Wiki、图谱、缓存、导出和 Agent 的授权判定；增加角色矩阵、撤权实时性、资源继承、跨用户差分测试和审计。不要在未确认共享策略前直接开放现有权限。Azure 文档级安全过滤与 Bedrock 部分连接器的源端 ACL 可作设计参照，部分 Azure 原生权限功能是预览版，不应直接视为生产成熟基线。
2. **数据接入**：已支持上传、本地目录、HTTP/内部 API、数据库、Markdown Wiki 与定时同步；建议按真实需求选择连接器，增加源端身份与 ACL、增量水位、快照隔离、重命名/删除识别、完整性证明、故障告警、恢复及大规模作业幂等。
3. **解析与来源定位**：已有 PDF/OCR、字符及部分页码/章节定位，但知识索引路径将 PDF 页面合并为字符串。建议结构化保留页码、标题层级、表格行列、图注、OCR 置信与截断信息；将来源引用升级为可回到原文件对应页、章节与高亮的体验。Google Document AI 对结构布局、表格和标题关系的处理可作为对照，而不是要求依赖云服务。
4. **检索与问答**：保留已有关键词、向量、融合、重排、置信门控与追问规划。增加每路召回溯源、单路超时隔离和部分成功结果，避免 `Promise.all` 一路失败使整轮失败；持续验证模型切换、不同语言、法律条文编号、同义词、时间与版本冲突。精确查询、列目录、聚合计数、内容概览与事实问答采用不同策略。
5. **治理**：已有版本、审阅、发布、来源生命周期 outbox、Wiki 来源校验、图谱证据与评测基础。建议用真实业务验证删除、禁用、过期、权限撤销到所有派生缓存/历史引用的生效时延；补充内容所有者、复核周期、失效预警、冲突处理和版本回滚操作体验。
6. **质量与可观测性**：已有 Recall、Precision、MRR、NDCG、引用与拒答指标，但尚无本次对目标环境的实测数据。建立按领域、语言、问题类型、权限角色及版本分层的人工标注集，分别测召回、引用、答案完整性、拒答、长文覆盖、注入攻击及成本延迟；评测覆盖实际聊天链路而不只工作台。建立采集/解析/切分/向量/检索/重排/生成/核验逐阶段耗时与错误率、索引新鲜度、向量覆盖和排队积压看板，记录脱敏及访问控制。
7. **运行与容量**：已有队列、租约、重试、暂存切换与降级状态；需压测多用户并发、文档规模、重建期间读可用性、模型故障、数据源断开、进程崩溃和备份恢复。定义每个部署规模的 P50/P95/P99、吞吐、恢复时间和费用预算，避免凭代码宣称已达到 SLO。
8. **交互体验**：为每份资料展示页数/字符覆盖、处理进度、失败原因、模型 profile 和新鲜度；检索失败区分无权限、未索引、无命中、服务异常和范围错误；批量操作展示可执行、跳过、失败及重试；目录支持分页，原文引用支持打开和定位。普通用户和管理员各跑完整无障碍、移动/桌面及多轮会话测试。

## 实施顺序与验收

| 阶段 | 工作 | 核心验收 |
| --- | --- | --- |
| 1：可信止血 | PDF 全量覆盖、拒答/引用绑定、来源删除安全、强制重建 | 恶意混合拒答及错配引用不得放行；截断扫描不触发归档；长 PDF 页级覆盖可见；切换模型后索引版本发生变化 |
| 2：统一权限与检索 | 统一授权、重算子查询向量、单路故障隔离、会话范围 ID | 跨用户零越权；撤权后结果不可见；多轮范围可解释；多查询比基线不退化 |
| 3：数据与治理 | 增量连接器、结构化解析、可定位引用、版本与派生失效 | 删除/禁用/撤权覆盖各链路；引用可打开正确版本及定位；恢复演练可复现 |
| 4：规模化 | 企业黄金集、灰度发布、压测和运维看板 | 使用业务方标注和部署环境确定目标阈值，持续观察 Recall@K、引用精度、拒答准确率、覆盖率、P95、费用和权限撤销时延 |

以上顺序是建议，不是工期承诺。应先运行基线再设目标，指标与典型业务风险共同决定发布门槛。
