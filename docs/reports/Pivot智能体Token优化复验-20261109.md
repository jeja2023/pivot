# Pivot 智能体 Token 优化复验

日期：2026-11-09。工作区版本v0.7.141。本轮针对此前核心样本比Hermes多19.0%Token继续优化；保留原验收报告和证据包，不覆盖历史数字。

## 变更

真实请求中，工具搜索和完整契约既在工具消息中出现，又进入任务事实摘要，随后每轮重复发送。任务目标同时出现在系统提示、当前用户请求和任务摘要中。

本次只精简模型侧任务摘要：

- 成功的`tools.search`、`tools.describe`准备项显示“仅工具准备，不代表业务执行”，不重复展开全文；原文引用继续保留，完整工具观察、持久状态及审计不变。
- 只有调用方已经携带完全相同的目标时才去重；目标变化或调用方未保证覆盖时仍显示原目标。
- JSON规划、流式规划及语义压缩事实包使用一致规则；业务事实、错误、未知状态、约束、待交付物及来源引用保留。

第一阶段修改集中于`agent-working-state.js`、`agent-runtime/planner.js`、`agent-streaming-runtime.js`和`agent-context-semantic-compression.js`。第二阶段针对真实误判补齐核验参数依据，见下文。没有新增依赖、配置或权限；没有关闭独立核验、缩减业务材料或增加预算。

## 已确认的提示侧收益

旧核心样本294条工作状态消息均能由当时的持久状态和时间顺序逐字重建。替换任务摘要后的本地估算减少294346Token；估算器不等于提供方分词器，这个数字不能作为费用或实际任务收益。

另取四份固定历史请求，各发送原始版和仅替换摘要的版本；模型、端点、工具定义、其余消息和输出参数保持一致。只请求模型，不执行返回的工具调用，属于诊断而非任务通过率。提供方报告的输入用量如下：

| 固定请求 | 原输入Token | 优化后输入Token |
| --- | ---: | ---: |
| EX01第7次请求 | 6353 | 5843 |
| EX03第8次请求 | 4942 | 4480 |
| NX03第13次请求 | 7896 | 7071 |
| NX05第8次请求 | 6476 | 5973 |
| 合计 | 25667 | 23367 |

**同一请求输入减少2300Token，约8.96%。** 不含输出波动，不把该比例直接套用到整项任务或所有模型。

## 完整任务实测

本轮使用相同已配置`gpt-5.6-terra`端点、相同合成资料和工具、独立初始状态。核心上限仍为30次外层请求、200000已报告Token准入上限、480秒及80次业务调用；保留产品风险80和独立核验。Token准入按调用前已报告用量检查，末次请求可能越过阈值，缺失用量不估算。

先在改动前运行EX01、EX03、NX03、NX05，待四项全部结束再应用生产代码改动，随后重新运行：

| 四项合计 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 实际交付通过 | 4/4 | 4/4 |
| 总Token（含独立核验） | 251741 | 246850 |
| 上游请求 | 47 | 49 |

该四项总Token下降**1.94%**，但请求增加两次。EX01出现多余服务试探、数字字符串修正，抵消部分提示节省，说明提示变短不保证每个任务成本下降；原始失败与修复调用均保留。

摘要去重阶段完整16项各两轮业务验收为32/32：27次平台`completed`、4次正确待输入，另1次产物已正确提交但核验服务返回故障，平台保持`needs_input`。共343次请求，已观测1674266Token，**缺失1次用量，因此无法给出完整总Token、下降比例或费用比较**。仅已观测值已高于旧Pivot完整1659555Token，本批没有证明整批19%差距缩小。

缺失响应的HTTP状态是200，但正文为`type:error/upstream_error`及服务器繁忙提示，没有核验结论或usage。产品未把它当作完成。原始响应、平台状态及缺失计数保留，不以业务产物通过掩盖平台核验失败。

与旧Hermes的比较仅沿用原冻结数据，本轮没有重新启动Hermes，因此不能称为当日同时运行的性能实验。

## 减少核验误判造成的往返

第一阶段EX01的一次执行中，任务先写入数字字符串、校验失败，随后修正为数值并成功校验提交。核验只收到输出，没有写入参数，误把旧失败判为当前仍失败，触发重新读取全部来源。该次用量122000Token，保留在32次样本中。

第二阶段在`agent-verification-context.js`加入`inputPreview`，复用现有脱敏、字段裁剪和4000字符整体上限；契约和搜索不额外传参数。`chat-task-verification.js`要求按执行顺序核对历史失败和后续版本，仍保留未解决错误；参数预览不能独立证明工具成功或文件交付。该改动增加少量核验输入，用于减少无依据的修复往返，不把错误直接删掉。

同一历史产物的诊断重放中，旧版和新版核验都通过；不能据此声称随机误判已被完全消除。新版输入增加1089Token，成本真实计入。最终版本四项及额外三项复测结果单列，不与此前32次混成相同版本。

| 原四项合计 | 优化前 | 仅摘要去重 | 最终摘要及核验依据优化 |
| --- | ---: | ---: | ---: |
| 实际业务交付通过 | 4/4 | 4/4 | 4/4 |
| 平台completed | 4/4 | 4/4 | 4/4 |
| 总Token（含核验） | 251741 | 246850 | 218488 |
| 请求 | 47 | 49 | 46 |

最终四项较优化前下降**13.21%**，用量完整。另测EX05、EX06、NX06为3/3，通过包含规则变化修正、真实版本冲突后合并和正确等待账号选择。该三项合计155925Token，保留版本冲突样本92516Token的额外往返，不以最终四项的收益代表所有任务。

**本轮已证明固定输入减少8.96%、最后四项端到端减少13.21%；尚未证明完整核心差距稳定缩小。** 最终六文件版本没有再次重跑全部32次；仅摘要阶段32次出现一次上游故障及缺失用量。模型输出和上游负载有波动，以上专项结果不能直接换算为对Hermes的全局性能比例。

长材料和进程恢复另行验证。16段材料的首段标记、全部读取、计算及实际提交均通过，但该次后续触及原风险预算，平台状态为`completed_with_errors`，不能描述成无告警完成。实际杀进程后的8段恢复任务完成并提交；同Run和新Run续跑路径按记录区分。专项不计入核心32次通过率或成本分母。
