# 0.7.76 在线更新与 0.7.155 安装停滞后续排查

日期：2026-11-13。生产版本更正为 0.7.76，直接安装停滞的包为 0.7.155，界面只显示不动的进度条，没有安装详情。

后续现场反馈：长时间等待后，0.7.155 已安装成功。最新截图显示的是安装完成后的自动更新检查失败：`GET /downloads/latest.yml?noCache=...` 返回 HTTP 404，并把请求头与堆栈重复展示到界面。此项与安装完成状态应区分；安装耗时异常的具体原因仍未确认，先前要求采集“仍卡住”的进程现场已不适用于已完成的这次安装。

## 已确认

从提交 `ef919a5f` 读取 0.7.76 原版更新器，对既有签名修复包执行实际 Windows 签名查询。证书发布者为 `CN=Pivot Local Dev`，系统返回签名状态 1；即使提供正确的内嵌指纹，0.7.76 原代码仍返回“更新安装包 Authenticode 签名无效（状态 1）”。其规则与曾测试通过的 0.7.74 不同。

因此，0.7.76 下载达到 100% 不等于安装包已就绪；服务器上替换安装器、更新描述或新包内的验签代码，均不能改变正在运行的旧客户端校验。维护者需要通过现有集中软件分发或受控覆盖安装先完成一次客户端恢复，普通用户不处理证书。若企业已有旧客户端认可的有效签名发布链，可独立验证其兼容性；当前自签名制品没有通过 0.7.76 的严格校验。

0.7.155 在生产安装数小时不完成的具体阶段尚未确认。开发机当前没有该生产安装器进程，不能从开发机状态推断生产进程已经退出、卡在卸载或文件损坏。既有 CIM 报错与当前无详情的长时间停滞不能合并为一个已经修复的根因。

## 本轮改动

- 原生进程检查排除当前检查器自身，避免安装器或卸载器原位执行时把自己当作客户端阻断；仍拒绝覆盖真正运行中的目标客户端。
- 安装器显示安装详情，并将阶段写入 `%TEMP%\PivotInstaller-<进程号>.log`，不再让无变化的进度条成为唯一状态。
- 页面下载进度达到 100% 时显示“正在校验更新”，只有下载完成事件才提供安装就绪入口。
- 新版签名查询增加 30 秒超时并报告明确错误，避免系统验证服务停滞后无限等待。该改动需要随客户端更新交付，不能远程修改已安装的 0.7.76。
- 提供只读诊断脚本 `scripts/collect_windows_installer_diagnostics.ps1` 和批处理入口，输出安装版本、相关进程、文件状态、更新策略白名单及安装阶段。报告不包含完整配置、隐身通信密钥、业务资料或进程命令行，不修改证书、终止进程或覆盖既有报告。

## 验证与限制

实际 NSIS 测试验证自身排除、目标目录进程阻断、外部同名进程保留、自然退出等待及查询失败阻断。使用独立应用标识和临时安装目录的完整 electron-builder 样本完成首次安装、覆盖安装、同版本重装；原位卸载原来返回 1，修复后返回 0。该样本没有访问真实 Pivot 的安装登记或快捷方式，不代表生产大体积产品安装已经通过。

只读诊断测试验证仅输出更新策略白名单、不泄露配置凭据、不修改配置，也不覆盖已有报告。页面与签名超时有对应回归验证。

28 项定向回归通过，无失败或跳过。另行使用原版 0.7.155 完整载荷和独立应用标识进行验证：首次安装及安装后应用摘要核对约 95 秒完成；一次覆盖安装未在 90 秒时限内完成，后续重建隔离样本也触发构建超时。因此未将完整产品覆盖升级判为通过，不能据此保证生产停滞已经修复。带详情安装器保留为诊断制品，未发布到生产更新目录；源包版本仍为 0.7.155。

隔离完整载荷验证使用的临时安装目录及其独立注册表登记尝试清理时，被自动审批审查拒绝，工具仅返回“blocked by policy”。相关测试痕迹因此保留；未对真实 Pivot 安装登记执行清理，也未终止生产安装器。

0.7.155 原应用载荷的带阶段详情修复安装器单独重建供现场定位，不与 v0.7.156 源码身份混淆，也不能宣称解决了生产停滞。诊断需在卡住的生产机器上执行，结合最后安装阶段和相关进程再决定修复方式。没有终止生产安装、卸载旧客户端、修改生产证书或部署更新源。

## 安装成功后的更新源 404 与错误展示

截图可以确认更新源返回 404，但不能仅从截图区分文件缺失、挂载目录不一致或代理路由。仓库主镜像不包含 `downloads/`，Compose 从宿主机目录挂载到 `/app/downloads`；需在生产核对 `latest.yml`、配套安装器及 blockmap 是否齐全。开发机对截图地址发起的受控读取超时，未直接核验生产目录。

复现了重复提示路径：更新器错误事件发出错误状态，检查 Promise 拒绝后再次发出同一错误，手动检查结果又重复提示。新增共享错误摘要，兼容已安装旧客户端返回的原始文本，统一为短中文原因，不展示请求头、内部地址或堆栈；更新器和页面均对同次错误去重。对应 25 项定向测试通过，包含缺失通道的错误码／文本分类、旧客户端错误事件及手动结果去重，以及更新器错误事件与异常捕获的集成验证。

配套发布目录补齐包位于 `artifacts/windows-update-feed-0.7.155-20261113/`，沿用现有原版 0.7.155 安装器及其版本描述；已核对安装器大小、SHA-512 和 feed 配置，并生成 SHA-256 清单。该包不是新功能版本，未上传生产。操作见[Docker 客户端下载配置](../Docker客户端下载配置.md)。

## 审查复核与 0.7.76 兼容约束

用户要求后续修改不得影响现有 0.7.76 自动更新。本轮不更改生产更新地址、通道、证书或发布文件，不切换安装交互，也没有执行打包发布。

- 确认更新器使用独立 `electron-updater` 会话，原拦截器只绑定业务会话和默认会话。现在将相同的动态隐身签名策略绑定到更新器实际使用的会话；签名仍为既有 v1/v2 格式，只对当前业务同源请求发送密钥派生头。独立更新源和跨源跳转不会自动获得业务密钥，不能直接采纳“匹配任意更新源 Origin 就复用业务密钥”的建议。
- 真实 Electron / ElectronHttpExecutor 受控 HTTP 测试复现无签名请求被断开，绑定后版本描述、安装包及 blockmap 均返回 200。该断开行为与截图 HTTP 404 不同，因此这项修复不能直接作为生产 404 根因已确定的证据。
- 确认切换本地模式且没有独立更新 URL 时，原先会因无法推导同站地址而抛错。现在仅在该配置分支停用有效更新检查；原始更新策略保留，切回远程后恢复。显式独立更新 URL 和远程更新配置保持原行为。
- 使用 `ef919a5f` 的 0.7.76 原配置代码作对照，同站 HTTP、独立更新 URL、退出安装显式启用、关闭更新四组配置结果与当前代码完全一致，v1/v2 签名输出也一致。保留 `installOnQuit` 既有语义和 `quitAndInstall(false, true)`，没有按审查建议切换静默安装。
- 工作区 `downloads/` 与源码版本不同步只是本机交付状态，不能证明生产缺少文件，也不会为凑齐本机目录而改写现有发布源。隐身模式下首次安装经受控渠道分发，继续维持既有服务端门禁。

尚未在真实生产 0.7.76 客户端上完成覆盖更新验收；以上兼容证据覆盖配置、请求协议及受控更新会话，不代表生产问题已全部解决。新增客户端会话修复需要重新构建安装包，已经安装的旧二进制不会因服务端页面更新而获得该修复。

本轮 35 项相关测试通过，包含真实 Electron 网络会话、远程配置恢复、既有配置与签名策略、错误展示及桌面配置入口。ESLint、类型检查、开发规范增量、文本完整性、全局变量、测试位置和差异空白检查通过。核对服务端下载路由、隐身门禁、Windows 签名构建配置、发布通道及包版本均未产生本轮改动；更新元数据和安装文件未发布或替换。
