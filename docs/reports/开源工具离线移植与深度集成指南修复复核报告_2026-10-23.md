## 3. 仍需修复的具体问题

### R01 [P1] Skill 静态校验通过，但工作区工具仍不能按示例执行

指南第 474、486、659 行使用 `workspace.read`。它在能力映射表内存在，因此预览通过；当前实际本机工作区工具经 MCP 目录暴露为 **`mcp.0.workspace.read`**，并且要求设备已连接、工作区已授权。

本次复现结果：

```text
previewSkillSource(新版示例).valid = true
executeBuiltInTool("workspace.read", ...) → 未知工具：workspace.read
示例 Skill 约束 + 实际工具 mcp.0.workspace.read
  → decision: denied
  → reasonCodes: ["skill_tool_not_declared"]
```

目录组装使用 `tool.fullName`，技能策略又按完整 `tool.name` 精确匹配，因此“登记了能力映射”并不等于“拥有同名可执行入口”。只把指令中的名称改成完整名、却不改 `tools` 声明，同样会被拒绝。

**修正与验收**：从当前用户工具目录取得真实全名，同时更新清单和正文；本机连接器场景应使用 `mcp.0.workspace.read`，补充连接器在线及目录授权前提。若目标是读取服务器上传文件，应另用实际存在的受控读取入口，不能以本机连接器代替。验证“发布 Skill → 读取真实文件 → 传入扫描器”的整条路径。

上一轮报告建议使用 `workspace.read` 时只区分了能力名与登记名，没有充分核对执行全名；本次已补足这项验证，需一并纠正。

依据：[目录组装](../../server/services/agent-tool-catalog.js#L86)、[连接器 MCP 名称](../../server/services/mcp-client.js#L170)、[本机服务 ID](../../server/services/local-device-mcp.js#L14)、[技能精确匹配](../../server/services/agent-policy.js#L187)、[内置执行器](../../server/services/agent-tools.js#L906)。

### R02 [P1] 单文件 SKILL.md ZIP 验签成功后，导入链路丢失正文指令

指南第 495—503 行允许根目录只放 `SKILL.md`，并通过 `/api/agents/skills/package` 创建草稿。

当前包读取器只从独立 `INSTRUCTIONS.md` / `instructions.md` 读取指令；对 `SKILL.md` 仅提取 manifest，未将正文写回 `package.instructions`。上传路由随后把这个字段传给 `createSkillVersion()`，最终按空字符串写入 `instructions_md`。

本次用指南中的原样 Skill 制作 ZIP，生成临时 RSA 密钥，在内存中签署包摘要并加入 `SKILL.sig`，要求签名的验证结果为：

```json
{
  "valid": true,
  "signatureValid": true,
  "errors": [],
  "sourceInstructionsLength": 176,
  "routeInstructionsLength": 0
}
```

这是已有实现中尚未修复的真实功能缺口，不能靠文档改写认定已闭环。本次未调用数据库写入接口；空指令的后续落库结论来自上传路由与版本创建代码核对。

**修正与验收**：单文件格式必须用同一次解析保留 manifest 和正文，并明确存在独立指令文件时的优先级或冲突拒绝规则。补充签名 ZIP 导入后 `instructions_md` 与源正文一致的测试，以及发布后指令实际进入任务的验证。

依据：[包指令读取](../../server/services/agent-skill-packages.js#L84)、[只提取 manifest](../../server/services/agent-skill-packages.js#L102)、[上传传参](../../server/routes/agents.js#L205)、[版本写入](../../server/services/agent-releases.js#L155)。

### R03 [P1] 发布流程仍把 preview 当作完整验证，实际会被发布门禁阻断

指南第 503—504 行为“执行 `previewSkillSource` → 个人使用可直接发布”。预览不创建版本验证记录，也不会把版本状态从 `draft` 变为 `validated`。

实际 `publishSkillVersion()` 对个人和共享发布都检查版本状态与最近一次验证结果；未经过 `validateSkillVersion()` 的新草稿会返回 `SKILL_RELEASE_GATE_FAILED`。ZIP 路由只创建草稿，没有自动完成这一验证。

**修正与验收**：明确区分“预览”“创建草稿”“完整验证”“发布”。给出 `POST /api/agents/skills/versions/:id/validate`，确认 `passed: true` 后再调用发布接口。正式发布范围使用 `personal / team / organization`；`shared / global` 是兼容历史值，不宜作为新流程主要术语。说明签名 ZIP 的公钥配置和生成方法，不能把“个人发布可不要求组织签名”理解为“ZIP 导入不验签”。

依据：[完整验证](../../server/services/agent-releases.js#L183)、[发布门禁](../../server/services/agent-releases.js#L278)、[验证/发布路由](../../server/routes/agent-control-plane.js#L462)、[发布范围](../../server/services/agent-skill-scope.js#L14)。

### R04 [P1] 内网微服务对普通用户仍不可用，仅增加 context.user 没有解决授权

指南第 375 行把调用者传给 `safeJsonPost()`，发布记录据此称出站授权已加固。但当前出站检查依旧根据 `isAdmin(user)` 决定是否允许私网目标，工具可见性和审批通过不会改变这一条件。

本次在独立 Node 进程中将示例服务名的 DNS 解析固定到一个私网地址，仅执行安全检查，没有发出网络请求：

```text
http://kroki:8000/mermaid/svg      普通用户：拒绝；管理员：允许
http://hermes-tools:8501/mcp      普通用户：拒绝；管理员：允许
```

MCP 执行器也把实际调用用户继续传给 HTTP 出站守卫。因此“管理员登记服务后，普通用户即可使用统一内网工具”的产品链路尚未成立。示例 Kroki 适配器还没有显式校验任务级网络白名单。

**修正与验收**：设计管理员批准的受管连接授权，将服务可见性、连接权限、固定目标和任务网络策略纳入同一执行判定。不能伪造管理员用户，也不能全局关闭 SSRF。必须测试普通授权用户成功、未授权用户失败、重定向/私网越界失败、DNS 变化失败和任务白名单不匹配失败。

依据：[HTTP 出站权限](../../server/security.js#L367)、[MCP 出站权限](../../server/security.js#L376)、[MCP 调用用户](../../server/services/mcp-client.js#L910)、[任务 HTTP 网络策略实现](../../server/services/agent-http-tool.js)。

### R05 [P1] 新增备份命令路径错误，统一时间戳不构成数据库与文件的原子备份

指南第 789—795 行提供：

```bash
tar -czf cas_backup.tar.gz ./data/cas ./data/uploads
```

当前默认目录实际为：

```text
CAS：DATA_DIR/agent-artifact-objects
上传：项目根目录/uploads
```

主 Compose 对应 `./data:/app/data`、`./uploads:/app/uploads`。本次工作区检查中，命令中的两个目录均不存在，真实默认目录存在。即使现场碰巧有同名目录，这条命令也可能漏掉当前制品。

此外，顺序执行 `pg_dump` 和 `tar`，只使用相同时间戳，不会自动获得数据库与文件之间的一致恢复点；回滚步骤也未明确恢复同一批 CAS/上传文件。

**修正与验收**：按 `PIVOT_ARTIFACT_CAS_DIR`、`DATA_DIR`、`PIVOT_UPLOAD_DIR` / `UPLOAD_DIR` 和容器挂载解析真实宿主机路径。明确暂停写入/维护窗口或经验证的协调快照方案；将数据库、文件、配置和镜像版本绑定到同一恢复清单，并做恢复后的制品读取与摘要核对。避免把普通顺序归档称为“原子备份”。

依据：[CAS 根目录](../../server/services/agent-artifact-cas-store.js#L42)、[上传根目录](../../server/upload.js#L10)、[主容器挂载](../../docker-compose.yml#L44)、[PostgreSQL 逻辑备份说明](https://www.postgresql.org/docs/16/backup-dump.html)。本次没有执行归档、停机或恢复操作。

### R06 [P1] 工具服务仍无鉴权，移除 ports 不等于只能由 Pivot 调用

指南第 529 行仅创建绑定 `0.0.0.0` 的 FastMCP，未配置令牌验证或鉴权代理，第 626 行却称不发布端口可“杜绝绕过 Pivot 治理”。

官方 FastMCP v1.x 仅在配置验证器时包装认证端点。Docker 同一 bridge 上的其他容器可以直接访问服务；宿主机也有网络访问路径。取消宿主机端口发布减少了暴露面，但不能替代身份认证，普通 bridge 也不默认禁止外部出站。

**修正与验收**：补充服务端认证及 Pivot 凭据引用，必要时使用受限专用网络或鉴权代理，明确实际出口控制。测试匿名/错误令牌拒绝和合法连接成功，不能只检查是否存在 `ports`。本次未启动真实 FastMCP，结论针对指南所示配置及 SDK 默认行为。

依据：[SDK 鉴权路由](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v1.x/src/mcp/server/fastmcp/server.py)、[Docker bridge 行为](https://docs.docker.com/engine/network/drivers/bridge/)。

### R07 [P2] 扫描器从占位逻辑改为真实 AST，但仍会漏报并把未覆盖样本标为 CLEAN

本次仅运行提取后的解析/遍历逻辑，没有执行被扫描源码。结果：

| 样本 | 扫描结果 |
| --- | --- |
| `import os; os.system(user_input)` | `HIGH`，检出 |
| `import os as o; o.system(user_input)` | `CLEAN`，未检出 |
| `from os import system; system(user_input)` | `CLEAN`，未检出 |
| `import pickle; pickle.load(untrusted_file)` | `CLEAN`，未检出 |
| `import subprocess; subprocess.run(user_input, shell=True)` | `CLEAN`，未检出 |
| 用户自行定义名为 `eval` 的普通函数并调用 | `HIGH`，误报 |
| 约 1500 项相加形成的合法表达式 | 抛出未处理的 `RecursionError` |

指南第 603—604 行仍将无命中结果称为 `CLEAN` / “扫描通过”。该扫描器目前只能作为有限规则演示，不能作为完整源码安全审计或自动合规门禁。

**修正与验收**：明确 Python 专用、规则覆盖和未覆盖范围；无命中应表示“本次规则未检出”，不要等同于安全。补充名称解析或采用经过评估的静态分析引擎，给出输入字节/节点/深度、超时、并发限制和可控异常。若卡片按列号高亮，还需处理 AST `col_offset` 的 UTF-8 字节偏移，不能直接当中文字符列号。

依据：[指南扫描实现](../design/Pivot开源工具离线移植与深度集成全景指南.md#L531)、[Python AST 规范](https://docs.python.org/3.12/library/ast.html)。
