# 公文写作深入检查与优化建议

检查日期：2026-11-04。范围为当前工作区中的公文写作前端、AI 服务、文档持久化、导出映射和相关测试。

本次只检查、复现并记录问题，没有修改公文写作业务代码。工作区原有的其他修改保留。

## 本轮改造结果

后续已按本报告完成 v0.7.88 改造，逐项实现与验收见[全面改造验收记录](公文写作全面改造验收-20261104.md)。以下内容保留为改造前检查证据。

## 检查结论

现有服务端文档库已经具备用户隔离、保存串行化、重复提交幂等、多窗口版本冲突和删除竞态保护。相关 9 项 Node 测试和 4 项完整应用保存 E2E 均通过。

仍有 11 类问题值得处理，其中编辑器输入、AI 结果归属、建议定位与导出产物归属直接影响正文可靠性。建议先修复这几条链路，再增加新的写作功能。

优先级定义：P1 为应优先修复的内容错误或跨文档污染；P2 为稳定性、输出完整性或状态体验问题。这里的“确认”指代码调用复现或浏览器复现，不代表生产环境的发生频率。

## P1 问题与修复方向

### OW-09：先修复基础编辑器

位置：[输入处理](../../client/chat/apps-workbench-editor.js#L632)、[段落渲染](../../client/chat/apps-workbench-editor.js#L560)、[旧段落边界截断](../../client/chat/apps-workbench-editor.js#L890)、[空撤销实现](../../client/chat/apps-workbench-editor.js#L969)。

输入事件先读取选区，再清空并重建整个编辑区。选区读取使用上一次渲染写入的 `data-text-end`，新增字符超出旧长度后，光标被截回旧位置。完整应用页面逐字输入 `abc`，编辑区为 `acb`；最小夹具确认底层文本值同样错序。这与 `.fill()` 一次填入整段文本的测试不同。

另有三项复现：

- 完整页面输入 `标题\n\n正文`，失焦并保存后成为 `标题\n正文`。空行渲染成没有文本节点的 `div`，再用 `innerText` 反向读取时丢失。
- 完整页面普通键入后按 Ctrl+Z，正文没有恢复。
- 最小 Chromium 夹具通过 CDP 模拟组合输入 `ni → 你 → 提交你`，得到 `ni你你`。这是合成组合输入证据，尚未覆盖目标机器所有 Windows 输入法。

建议：编辑中的 DOM 保持稳定，只同步正文模型；在 `compositionend` 后再格式化；不要在每个 `input` 事件替换整个编辑区。空行应有明确、可往返的表示。为普通输入和 AI/模板操作提供统一撤销事务。暂时继续采用自实现编辑器时，应先解决选区和模型映射，再做样式与性能调整。

验收：逐字输入、中文连续组词、Enter/空行、删除合并段落、粘贴、多段选区、Ctrl+Z/重做均能保持文字与光标一致。

### OW-01：AI 请求必须绑定发起文档和正文版本

位置：[AI 任务](../../client/chat/apps-workbench-ai.js#L170)、[起草结果写入](../../client/chat/apps-workbench-ai.js#L244)、[文档切换](../../client/chat/apps-workbench-editor.js#L278)。

异步请求结束后直接操作全局 `officialWritingState` 和当前编辑框，没有验证发起文档是否仍然活动。A 起草期间切换或创建 B，A 的初稿可以覆盖 B，这一点已在完整应用页面复现；留在 A 继续输入，也会被较早请求的结果覆盖。现有 `pushOfficialWritingUndoSnapshot()` 为空，无法承担恢复保护。

建议：每次任务捕获 `documentId`、正文摘要/修订号、请求 ID 与结果快照。任务结果始终属于发起文档。正文已变化时保留为待采纳结果；切换文档、删除或退出时中止或隔离任务。覆盖正文前保留可恢复版本。所有 AI 模式提供取消入口，目前可见的停止按钮仅覆盖审校。

验收：A 等待时切换 B、删除 A、继续编辑 A、退出再进入，均不得覆盖其他正文。

### OW-02：建议应用不能只信任 start/end

位置：[建议应用](../../client/chat/apps-workbench-ai.js#L309)、[范围替换](../../client/chat/apps-workbench-editor.js#L977)。

复现原文 `甲乙丙丁`，先把 `甲` 改为 `甲甲甲`，再接受原本指向 `丙` 的建议：实际得到 `甲甲新乙丙丁`，预期是 `甲甲甲乙新丁`。建议仍使用旧偏移，也没有检查待替换片段与 `original` 是否一致。

建议：保存文档修订号、原文和前后文锚点；应用时校验。发生前文插删时统一更新锚点，或通过编辑器事务映射位置。找不到或多处同文时标记失效，要求重新定位。审校响应返回时也应匹配请求快照，避免用最新正文猜测旧问题的位置。

### OW-03：区分“问题说明”和“替换正文”

位置：[服务端审校提示与解析](../../server/services/official-writing.js#L61)、[前端结果转换](../../client/chat/apps-workbench-ai.js#L193)。

后端让模型返回 `suggestion（具体修改建议）`，前端直接将其作为 `replacement`。模型合理返回“建议将‘截止目前’改为‘截至目前’”时，点击替换会把整句说明写进正文。若模型返回合法空数组 `[]`，前端又把它当成整体意见卡片，可在正文开头插入 `[]`。没有匹配到原文的建议也会退回 `start=0,end=0`。

建议：审校契约拆为 `explanation`、`original`、`replacement`、`severity`；只有原文锚点有效且提供替换文本时允许直接应用。空数组表示审校完成且没有问题；解析失败、输出截断和没有问题使用不同状态。整体意见只支持查看或转批注。

### OW-04：流式成功需要明确的完成条件

位置：[前端 SSE 消费](../../client/chat/apps-workbench-ai.js#L70)、[服务端流式转发](../../server/routes/apps/index.js#L853)。

前端只提取 `content/delta.content`，忽略 SSE 中的 `error` 和 `finish_reason`；网络读取抛错时，只要已有部分内容仍返回类似成功的对象。服务端上游错误也可能仅结束连接。因此，截断的初稿会沿正常分支写入正文并提示成功。

受控 SSE 复现同时包含半篇正文、超时错误和 `finish_reason=length`，返回值只有正文，错误与截断状态丢失。流式路径直接转发原文，还会保留内联 `<think>…</think>`；非流式路径已做相应清理，两条路径不一致。

建议：统一结果对象包含 `status`、`finishReason`、`partial`、`error`、`content`。明确收到正常完成后才作为可覆盖的完成稿；中断内容保留为可查看草稿。统一流式与非流式的可见正文过滤，并在 `finally` 释放 reader。全文起草可展示实时预览，完成后再由用户采纳。

### OW-05：导出 Artifact 绑定应属于每一篇文档

位置：[全局绑定与解析](../../client/chat/apps-workbench-export.js#L39)、[保存产物](../../client/chat/apps-workbench-export.js#L333)、[状态归一化](../../client/chat/apps-workbench-core.js#L270)。

模块级 `officialWritingExportArtifactId` 的优先级高于当前文档绑定，文档切换时没有清空。绑定 A 为 `101`，切到绑定为 `202` 的 B，解析结果仍为 `101`。服务端收到已有 `artifactId` 会向该产物追加版本，因此不同公文会混入同一产物历史。

同时，状态归一化丢弃 `artifactId/agentArtifactId`，绑定无法随文档可靠保存，刷新后又会生成新的产物。导出期间切换文档时，异步绑定回填同样需要文档归属检查。

建议：在公文记录中显式保存可校验的产物绑定，导出从开始到完成始终使用同一份文档快照。服务端校验产物与该公文之间的归属关系；标题采用用户的公文名称。两个文档轮流导出、刷新后继续导出，产物历史必须分别连续。

## P2 问题与修复方向

### OW-06：导出前让用户看见真实输出要素

位置：[Document IR 映射](../../client/chat/apps-workbench-export.js#L247)。

当前填写的 `cc` 不进入 IR；密级只保留枚举，保密期限遗漏；正文没有成文日期时，把印发日期映射成 `issued_at`；红头机关优先取印发机关。界面字段与导出字段的语义并不一一对应。代码会在导出完成提示中告知部分遗漏，但填写时和导出前缺少预览。

建议：区分发文机关、签发人、落款单位、成文日期、印发机关、印发日期，补全抄送和保密期限的输出模型。提供导出预览和要素缺失提示；不能渲染的内容应在导出前清楚列出。普通 DOCX 与红头 DOCX 当前共用固定红头路径，也可增加明确的版式选择。

本次确认的是映射内容，未对实际 DOCX/PDF 字节、字体和分页进行视觉验收，也未对国家标准符合性作出结论。

### OW-07：保存状态与失败恢复

位置：[加载](../../client/chat/apps-workbench-core.js#L785)、[保存调度](../../client/chat/apps-workbench-core.js#L860)。

加载失败会将当前内存库替换成空库并创建空文档，还返回成功样式的布尔值。保存错误主要通过一次 toast 告知，没有持续的“未保存/保存中/保存失败”状态和可见重试入口。普通输入存在 250ms 分析防抖和 450ms 保存防抖；公文模块未提供关闭页面时的脏状态保护。

建议：文档级保存状态、最后成功保存时间、重试按钮；网络失败保留当前用户的内存草稿。加载应先写入候选结果，成功后再替换。409 冲突提供“另存为副本/比较服务端版本/复制当前稿”，替代只让用户复制后刷新。若增加离线缓存，应沿用账号隔离与登出清理边界。

### OW-10：控制快照体积，并将列表改为摘要加载

位置：[自动草稿](../../client/chat/apps-workbench-editor.js#L1043)、[完整状态列表查询](../../server/services/official-writing-documents.js#L65)、[手动版本](../../client/chat/apps-workbench-proofread.js#L458)。

每份自动草稿同时复制全文正文和完整材料，最多保留 8 份。18 万个汉字的材料约 540,000 字节，经过 8 次正文变化，序列化状态达到 **4,861,338 字节**，已超过单篇 **4,194,304 字节**限制。正文在此复现中只有几个字。手动版本还没有相应数量/字节裁剪。

列表接口一次返回所有文档的完整状态，包括材料、建议与历史；前端的每页 10 篇只是展示分页。文档数量增多后，网络、内存和 JSON 解析成本都会增长。

建议：材料作为独立版本资源引用，快照只存正文差异或材料版本 ID；按时间/关键操作生成快照，并设置可解释的总字节预算。支持清理历史。列表服务端分页，只返回摘要；打开文档时再取详情。

### OW-08：建议状态应限制可执行动作

位置：[建议卡片](../../client/chat/apps-workbench-editor.js#L1254)、[建议应用](../../client/chat/apps-workbench-ai.js#L309)。

已接受或忽略的建议仍渲染替换、插入按钮，操作函数也不校验状态。对同一条插入建议点击两次，正文包含两份插入内容。

建议：完成后的卡片只保留结果和定位信息；应用操作做幂等检查。需要重新采纳时通过显式撤销/重新打开流程完成。

### OW-11：统一内容状态，避免把“有正文”显示成“可导出”

位置：[列表状态](../../client/chat/apps-workbench-editor.js#L4)、[编辑页状态](../../client/chat/apps-workbench-editor.js#L711)。

列表只检查正文和待处理建议。有 `【待补充】` 的正文会标为“可导出”，编辑页同时提示占位和日期风险。基础校对、AI 审校、保存状态与内容状态也没有清晰分离。

建议：共用状态计算器，展示“已起草/待核对/已审校/有未补齐项”等可解释状态；“可下载”与“内容已核对完成”分别表达。基础校对规则应读取已经填写的发文要素，避免用户填了发文字号、签发人仍被正文正则提示缺失。

## 后续体验与结构优化

以下为代码检查发现的能力边界和优化机会，未全部作为缺陷复现：

1. **公文列表检索与筛选**：提供名称搜索、文种筛选、更新时间排序，配合服务端分页。现有页面只有创建、刷新和分页。
2. **材料处理**：当前导入对文件逐个调用 `file.text()`，适合文本文件；可接入现有文档解析/OCR 能力处理 DOCX/PDF，增加文件大小、编码和单文件错误提示。异步导入也应绑定发起文档。
3. **依据追溯**：当前知识库引用主要拼为正文材料字符串；建议保留文档/片段 ID、版本和定位，便于核对来源及识别失效引用。现有文本相似度只能用于提示相近内容，不能作为事实核验结论。
4. **起草与采纳流程**：先展示生成结果和差异，再采纳；减少对已有人工作业的直接覆盖。用户填写的公文名称可作为标题意图显式进入起草请求。
5. **备份恢复闭环**：存在 JSON 备份函数和事件绑定，但当前模板没有对应按钮，也没有恢复入口。可在文档菜单提供“备份/导入为新文档”，同时校验大小、结构与归属。
6. **规范规则可解释**：当前规范选择影响名称提示和少量本地规则。可提供规则版本、适用文种和检查说明，避免将“选择了规范库”等同于已经通过完整格式审查。
7. **模块拆分与渲染**：将文档库、保存状态、编辑器选区、建议、材料分离；编辑器文件目前约 1,400 行。缓存规则分析，隐藏弹窗按需渲染，20 条审校意见批量入库后只渲染一次。避免每次输入或每条意见都重建整个工作区。

## 建议实施顺序

1. **正文可靠性**：OW-09、OW-01、OW-02、OW-03、OW-04，覆盖真实逐字输入和请求竞态。
2. **文档与导出一致性**：OW-05、OW-06，并补充两篇文档交替导出和真实文件内容验收。
3. **保存与规模**：OW-07、OW-10、OW-08、OW-11，补齐可见状态、历史预算和列表摘要。
4. **使用效率**：检索、材料解析、依据定位、预览采纳、备份恢复，再考虑更复杂的审批协作。
