## 4. 已复现问题与修复方案

优先级：P1 为应优先修复的访问控制或结果正确性问题；P2 为明显功能缺口、性能或体验问题。

### 4.1 P1：已删除法规的关联接口仍能读取与写入

证据 A01：普通用户访问已删除法规详情返回 404，但引用图、版本对比、批注读取和新增批注均返回 200；版本对比还返回了已删除法规正文。

原因：详情路由检查删除/归档状态，但对比和引用图服务使用 `includeArchived: true`；批注服务只校验条文 ID 和批注作者，未先检查所属法规的读取权限。

修复方案：建立统一文档/条文读取检查，覆盖列表、详情、图、对比、影响分析、批注、相似条文和 AI 引用。恢复已删除内容应作为 admin 的独立回收站能力，避免通过一般读取接口开放。

验收：同一资源在每个入口的权限结果一致；普通用户不得读写已删除法规；非法、跨文档和不存在的版本 ID 不能静默回退到其它版本。

代码位置：[详情与关联路由](E:/pivot/server/routes/apps/regulations/documents.js:77)、[对比服务](E:/pivot/server/services/regulations/analysis.js:47)、[引用图服务](E:/pivot/server/services/regulations/analysis.js:194)、[批注服务](E:/pivot/server/services/regulations/collaboration.js:14)。

### 4.2 P1：混合检索把更强词法相关度排到后面

证据 A09：两个候选向量得分相同时，词法分数 0.10 的候选排在 0.95 的候选前面。

原因：词法服务按 similarity 得分降序返回，而混合服务沿用“分数越小越好”的旧 BM25 假设，使用 `1 - score / maxScore`。分数为零还会被 `score || 999` 替代。

修复方案：统一检索分数定义。短期修正归一化方向和零值处理；随后采用词法、向量各自召回后的排名融合，避免不同量纲简单加权。算法与产品文案应匹配实际实现。

验收：固定语义得分时，词法相关度更高的条文不能被反向降权；正常命中、零分、缺失分数及降级路径均有行为测试。

代码位置：[词法排序](E:/pivot/server/services/regulations/search.js:53)、[混合分数](E:/pivot/server/services/regulations/search.js:168)。PostgreSQL 的 similarity 返回 0 至 1，越大越相似，见 [pg_trgm 官方文档](https://www.postgresql.org/docs/current/pgtrgm.html)。

### 4.3 P1：无向量的强关键词命中被丢弃，语义召回范围过窄

证据 A10：两个词法候选中，一个强命中没有向量，另一个弱命中有向量；混合检索最终只返回弱命中。

证据 A11：混合服务希望扩大到 300 个候选，但调用的词法函数上限是 50；没有词面重合时，即使成功生成查询向量，结果仍为空。

修复方案：词法与向量独立召回、去重融合；保留无向量候选的词法排序；为不同候选分支设置明确上限；显示实际使用的检索方式和降级原因。法规检索和 AI 取证应使用同一套检索服务。

验收：向量缺失不导致关键词命中消失；同义改写问题能被独立语义分支召回；候选限制与对外返回数量分别控制。

代码位置：[混合候选处理](E:/pivot/server/services/regulations/search.js:152)、[AI 仍直接调用词法检索](E:/pivot/server/services/regulations/analysis.js:257)。

### 4.4 P1：AI 上下文遗漏条文真正命中的内容

证据 A06：条文后半段含“应在三十日内完成”，检索能够命中，但交给模型的上下文只保留开头 240 字，既没有命中词，也没有期限规则。

原因：检索生成固定开头摘要，AI 构建上下文优先使用 excerpt，而不是命中附近的片段或完整条文。对于适用条件、例外和处罚在后半段的条文，容易缺失决定性依据。

修复方案：检索摘要围绕命中位置生成；AI 取证读取完整的逻辑条文，再按模型预算选择片段。保留标题、条号、版本、效力和邻接款项，确保条件与例外不会被割裂；取证不足时明确返回不足状态。

验收：后半段命中、例外款、长条文、同名法规和多轮追问均可回溯到实际送入模型的依据。

代码位置：[检索开头摘要](E:/pivot/server/services/regulations/search.js:82)、[AI 上下文构建](E:/pivot/server/services/regulations/analysis.js:255)。

### 4.5 P1：更新后关联引用继续指向旧版本

证据 A04：目标法规追加新版后，执行“重建跨法引用”仍保留旧条文 ID；AI 关联上下文继续带入旧版内容。

原因：重建只处理 `target_article_id IS NULL` 的悬空引用，已有引用不会重对齐；AI 关联扩展也未要求关联条文来自当前版本。

修复方案：明确两类引用：固定历史版本引用与随当前有效版本变化的引用。新增版本后使后者失效并重建，保留前者的历史解释。每条引用记录来源版本、目标版本、绑定模式、匹配置信度和审核状态。

验收：追加新版、改名、目标删除、条号变化及重建后，引用版本均符合绑定模式；AI 引用按钮、原文定位和导出报告能够打开实际引用版本。

代码位置：[只重建悬空引用](E:/pivot/server/services/regulations/links.js:103)、[关联条文读取](E:/pivot/server/services/regulations/analysis.js:134)、[引用点击未传版本](E:/pivot/client/chat/regulations/events.js:261)。

### 4.6 P2：归档与删除的含义混用

证据 A02：仅设置 `status=archived` 的法规仍出现在普通列表和条文检索，普通用户点击详情却返回 404。

原因：多数检索路径只过滤 `deleted_at`；详情额外过滤 archived。界面将 active 显示为“有效”，但 active 只是管理状态，并无效力日期或审核信息支持。

修复方案：分开管理状态、法律效力和软删除。定义一致的默认查询范围；文档列表与条文检索使用同一可见性条件。将“有效”改为与数据匹配的文案，直到建立真实效力模型。

验收：列表可见的文档必须能按同一权限打开；归档、废止和删除在界面、检索、问答中具有明确且一致的行为。

代码位置：[列表过滤](E:/pivot/server/services/regulations/catalog.js:77)、[详情状态判断](E:/pivot/server/routes/apps/regulations/documents.js:83)、[状态文案](E:/pivot/client/chat/regulations/render-base.js:8)。

### 4.7 P2：筛选发生在截断结果之后，独立分类筛选不工作

证据 A13：仅输入分类、不输入关键词时，前端没有发起检索请求。代码还先取最多 50 个条文候选，再在浏览器筛选分类和适用范围，最后只展示 20 个。

风险：符合条件的法规可能位于候选截断之后，导致结果为空或数量偏少；纯分类保存检索也无法给出预期结果。

修复方案：文档目录筛选与条文检索分别设计；在后端召回之前应用分类、发布机构、适用范围、状态和日期条件；允许纯筛选；提供结果总数与分页。保持列表筛选不被问答弹窗隐式改变。

### 4.10 P2：章节层级与行内条号解析不足

### 4.11 P2：重复条号会使版本对比漏报

证据 A05：同一条号有两个片段，旧新版前片段不同、后片段相同，对比结果报告零处修改。

原因：以 article_label 为唯一 Map 键，后片段覆盖前片段。当前主解析路径常把一条保留为整段，但重复标题、历史分块数据及未来分片都能触发此问题。

修复方案：先按稳定逻辑条文 ID 或章节路径/条号归并完整内容，再做对比；对重新编号建立显式匹配。大条文行级 LCS 为 O(mn)，需要大小上限、替代算法或后台任务。

代码位置：[对比键与 LCS](E:/pivot/server/services/regulations/analysis.js:12)。

### 4.12 P2：引用关系类型在响应中丢失

证据 A03：数据库为 depend，引用图响应却是 cite。SQL 返回 `relation_type AS type`，映射阶段读取 `e.relation_type`。

修复方案：统一输出字段；增加 cite/depend/apply/supersede 的端到端映射测试。自动识别“修订/废止”关系只能作为待审核提示，不能直接当作法律效力事实。

代码位置：[类型映射](E:/pivot/server/services/regulations/analysis.js:215)、[关系关键词判断](E:/pivot/server/services/regulations/links.js:18)。

### 4.13 P2：AI 当前法规范围与功能入口没有完整接通

证据 A13：即使已有活动法规，问答请求也没有 documentId；详情有两个版本时仍没有版本对比入口。

静态确认：预览中的“确认入库”和“合并条文”只显示“待后续完善”；历史条文定位链接只记录文档和条文 ID，不含版本。服务已支持流式问答，但当前前端仍提交普通 JSON 请求。

修复方案：增加“全库/当前法规/选定法规”问答范围；把当前条文及版本作为结构化字段提交；详情增加对比入口；预览编辑后的结果真正进入入库流程；历史链接携带 versionId。流式回答与停止生成可以复用已有模型转发能力。

代码位置：[问答请求](E:/pivot/client/chat/regulations/actions-import.js:158)、[预览占位逻辑](E:/pivot/client/chat/regulations/events.js:377)、[历史定位](E:/pivot/client/chat/regulations/events.js:437)、[服务器问答来源](E:/pivot/server/routes/apps/regulations/ai.js:23)。

### 4.14 P2：详情响应过重，列表存在逐文档统计

证据 A14：只有两个版本、一条当前条文的合成法规，因每版全文 10 万字符，详情 JSON 已达到 901,842 字节。版本列表返回全文，所选版本再重复返回全文，条文向量也被带回。

证据 A15：本页 3 个文档产生 5 次查询，即列表、总数和每个文档的条号统计 N+2；默认 20 条一页时该模式预计为 22 次查询，未计嵌套子查询。

修复方案：版本目录只返回元信息；正文按版本懒加载，条文可分页/按章节加载；向量和服务端源路径不作为常规 UI 数据返回。目录统计用已维护 article_count 或一次分组统计，提供重算校验任务。

代码位置：[版本 SELECT *](E:/pivot/server/services/regulations/catalog.js:48)、[逐文档统计](E:/pivot/server/services/regulations/catalog.js:151)、[详情正文读取](E:/pivot/server/services/regulations/catalog.js:210)。

### 4.15 P2：检索表达式与已有索引不匹配

证据 A16：模式已有 `content gin_trgm_ops` 索引，但查询使用 `LOWER(content) LIKE LOWER(...)`。5,000 条填充数据的默认计划为 Seq Scan；仅为检查索引可用性而禁用顺序扫描时，LOWER 路径仍为 Seq Scan，直接 ILIKE 路径可使用 Bitmap Index Scan。

默认计划中 ILIKE 也选择 Seq Scan，说明不能据此承诺延迟提升或强制索引。修复应保留正确比较语义，再在代表性数据、选择性和并发条件下运行 `EXPLAIN (ANALYZE, BUFFERS)`。

方案：对齐表达式与索引，复用已有 search_content/中文词元底座，减少标题命中后的大量同文档条文重复候选；根据数据量和向量维度决定是否建设向量索引。可变维度 vector 不能简单对所有数据直接建立统一维度索引。

代码位置：[查询表达式](E:/pivot/server/services/regulations/search.js:87)、[模式索引声明](E:/pivot/server/db/schema/pg-schema.snapshot.json)。技术依据：[pg_trgm 索引支持](https://www.postgresql.org/docs/current/pgtrgm.html)、[pgvector 查询与索引](https://github.com/pgvector/pgvector#querying)。

## 6. 优化目标与设计方案

### 6.1 统一数据模型与可见性

保留文档、版本、条文结构，增加逻辑条文与检索片段之间的明确映射。推荐字段：

- 文档：法规层级、文号、来源机构、适用范围、官方来源地址、主题标签、维护负责人。
- 版本：发布日期、生效日期、失效日期、效力状态、审核状态、来源指纹、解析任务/配置版本。
- 条文：稳定键、章/节/条/款/项路径、原页定位、结构审核状态。
- 检索片段：逻辑条文 ID、文本范围、页码范围、向量模型配置指纹与索引状态。
- 引用：来源版本、目标版本、目标条文键、固定/随当前版本模式、关系类型、证据和审核状态。

区分三个维度：管理状态（启用/归档）、法律效力（未生效/现行/失效/废止/待核验）、删除状态（正常/回收站）。先迁移存量为待核验，不从上传时间或文件名自动推断“现行有效”。

### 6.2 完整的导入与索引流程

流程：上传 → 完整性/重复检查 → 文本与逐页 OCR → 结构预览与校正 → 发布版本 → 索引与引用任务 → 可检索状态。

每一步记录状态和错误，任务中心显示逐文件进度。批量导入允许逐文件选择新建文档或追加版本；预览可编辑条号、标题、正文、章节路径并合并相邻片段。确认后采用校正结果，避免重新解析覆盖人工修改。

复用已有 document-processing 与统一任务能力，法规应用只承接元数据、逻辑条文和治理规则。

### 6.3 统一检索与可追溯问答

检索输入同时支持法规名称、条号、关键词、自然语言与元数据条件。后端在召回前统一应用可见性、查询日期、版本及筛选条件。

推荐检索链路：精确名称/条号定位 + 中文词法召回 + 独立向量召回 → 去重与排名融合 → 可选重排 → 合并同条文片段 → 命中周围摘要与来源。

问答复用同一检索链路，并使用用户明确选择的范围。将问答记录、检索版本、上下文快照、模型配置和来源 ID 保存为一次可追溯结果。导出时由服务器根据来源 ID 重建依据；历史报告不随当前法规更新而无提示地改变。

当低命中或证据不足时，显示“未找到足够依据”和可调整的范围/筛选条件；多轮追问必要时补全上一轮主题，避免只用“这个期限呢”作为词面查询。

## 7. 功能扩展路线

以下是建议计划，尚未开始实施。

| 阶段 | 建设内容 | 前置依赖 | 交付与验收 |
| --- | --- | --- | --- |
| 第一阶段：正确性修复 | 统一权限与状态；修复排序、候选丢失、240 字上下文和旧引用；对比入口/类型修正 | 当前实现 | 关键权限矩阵、长条文与版本更新回归；下文高风险用例全部通过 |

| 第三阶段：法规治理 | 生效/失效日期、待核验状态、指定日期查询、回收站、重复合并、元数据字典、维护负责人 | 第二阶段与存量质量审核 | 时间点查询选择正确版本；批量修改可追溯；回收与保留期规则明确 |

| 第五阶段：协作与持续更新 | 更新订阅、人工审核的权威来源导入、影响分析、义务清单、责任人与任务分派、管理看板 | 效力模型与稳定引用 | 更新有审核记录，影响对象能定位，通知仅发送已核实变更，任务有负责人 |

推荐功能的具体价值：

1. **指定日期法规查询**：回答“某事项发生时适用哪个版本”，所选时点与版本一起展示。
2. **原页与完整条文双视图**：从任何命中、批注和报告依据直接定位来源页，并核对上下文。
3. **专题与收藏**：按采购、人事、财务等主题组织法规；可以收藏条文和保存检索，而不改变全库治理结构。
4. **更新订阅与影响分析**：法规新增、修订或废止后，生成变更摘要和受影响引用清单，经审核后通知关注者。
5. **合规义务清单**：从审核过的条文提取主体、触发条件、动作、期限、凭证和责任人；人工确认后转为任务。
6. **质量管理看板**：缺失元数据、重复文档、未索引条文、来源缺页、未解析引用、版本冲突和待审核事项集中显示。
7. **批量治理增强**：跨页选择时明确“本页/全部筛选结果”，使用有上限的服务端任务；预览修改范围，保存逐条修改前后值，支持合理范围内撤销。

权威来源接入应先确定内部允许的来源、获取方式、审核人员和更新规则。不能把第三方页面上的日期或自动识别的引用关系直接当作已核实效力。

## 8. 优先开发包

建议拆成四个可独立评审的开发包，避免把修复和大量新功能放进一个改动。

| 开发包 | 修改重点 | 核心验证 |
| --- | --- | --- |
| A：权限与状态一致性 | 路由共享读取检查、条文到文档可见性、归档/删除语义、非法版本处理 | 普通用户/manager/admin × 正常/归档/删除 × 每个读取/批注入口 |
| B：检索与 AI 依据正确性 | 候选融合、得分方向、无向量保留、后端过滤、全文/片段预算、问答范围 | 固定召回评测集、长条文后半段、同义问法、同名版本、模型异常降级 |
| C：版本与引用一致性 | 引用重绑策略、逻辑条文键、版本对比、历史定位与来源字段 | 追加新版、重新编号、重复条号、源/目标删除、旧报告打开 |

## 9. 验收与评测计划

### 正确性与权限

- 所有入口执行同一可见性规则；普通用户对删除内容的读取/批注请求均被拒绝。
- active、archived、deleted 与法律效力分离，界面不再用管理状态冒充已核实效力。
- 历史版本和跨法来源按钮打开实际引用版本，不默默切到最新版本。
- 长条文后半段、例外款、重复条号和重新编号不会丢失依据。

### 检索质量

- 建立人工标注查询集：名称简称、条号、关键词、同义表达、多条件、历史日期、无答案及多轮追问。
- 记录召回率、排序指标、错误版本率、证据不足识别率；比较词法、向量及融合路径，不能只验证返回数组。
- 按无向量、部分向量、不同模型维度、同维度不同模型和服务不可用分别验收。

### 导入与性能

- 以真实代表文档验证 PDF、DOC/DOCX、网页文本、图片、扫描 PDF 和混合 PDF；检查页数、条数、章节及原页定位。
- 导入超过限制、解析为空和 OCR 不完整有明确状态；失败重试不重复创建文档。
- 数据规模分档测量列表、检索、详情和导入：记录 P50/P95、数据库往返次数、响应体积、内存和并发。先记录基线，再定义适合部署环境的目标。
- 详情版本目录不带 extracted_text/embedding；本页文档统计不随文档数逐项查询。

### 体验与工程

- 批量模式进入/退出、部分失败、关闭弹窗、键盘导航、窄屏和深色主题均有浏览器测试。
- 检索和问答范围清楚，用户可区分“无命中”“过滤后无结果”“向量降级”“证据不足”。
- 自动化测试覆盖完整导入→检索→原文→问答→版本更新→引用定位流程，增加行为测试，减少仅依赖代码正则的契约测试。
- 每个开发包分别执行项目检查、lint 和范围相关回归；模型/OCR 集成测试在真实配置环境中完成。

## 10. 本次建议的决策

可以继续沿用现有架构，优先建设统一检索、统一读取权限、逻辑条文/版本来源及任务状态，不需要重新搭建一套独立法规系统。

第一轮最值得实施的是开发包 A 与 B：它们直接决定资料是否按权限可见、检索排序是否可靠，以及模型是否拿到了回答所需的实际条文。随后补齐版本引用与导入流程，最后推进效力日期、原页追溯和持续更新。
