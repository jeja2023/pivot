# 文档处理底座与 OCR/PDF 工具应用分阶段开发方案

版本：v1.0  
日期：2026-07-05  
适用范围：文档处理底座、文字识别应用、PDF 工具应用、知识库导入、法规查询导入、聊天附件处理

## 1. 结论

建议建设一个“文档处理底座”，并在其上提供两个独立用户应用：

1. 文字识别应用：面向图片、扫描 PDF、无文本层 PDF 的 OCR 识别、校对、导出和入库。
2. PDF 工具应用：面向 PDF 拆分、合并、旋转、重排、文本抽取、图片转换、可搜索 PDF 生成等常用处理。

这两个应用应作为独立工具提供给用户使用，同时把能力沉淀到共享底座，供知识库、法规查询、聊天附件、公文写作材料等业务模块复用。这样可以避免每个业务模块各自实现 OCR、PDF 解析、导出和任务状态管理。

## 2. 与开发规范的绑定关系

本方案必须严格遵守 [开发规范.md](../../开发规范.md)，特别是以下约束：

1. 文档处理能力必须建设为共享底座，具体应用和业务模块复用底座能力。
2. OCR 识别应用、PDF 工具应用、知识库导入、法规导入、聊天附件解析不得各自实现一套解析链路。
3. 所有前端页面必须使用全局统一样式，包括按钮、输入框、下拉框、字体、字号、弹窗、按钮颜色、主题、数据表格、分页控件。
4. 后端路由只负责请求解析、鉴权、参数校验和响应组装，业务逻辑下沉到 `server/services/`。
5. 长耗时能力必须设计为任务接口，不得让普通请求长时间阻塞。
6. 上传文件、生成文件和临时文件必须使用受控路径、受控下载和清理策略。
7. OCR/PDF 相关验收必须覆盖文本型 PDF、扫描 PDF、图片、低置信度、失败重试和导出文件。

## 4. 产品边界

### 4.1 文档处理底座

文档处理底座不是直接面向用户的页面，而是一组后端服务、数据结构、任务接口和共享前端能力，负责：

1. 文件登记、格式识别、页数统计、文本抽取、PDF 渲染、OCR、导出和清理。
2. 统一任务状态，包括 `queued`、`processing`、`succeeded`、`failed`、`needs_review`、`cancelled`。
3. 统一结果结构，包括文件、页面、文字块、坐标、置信度、引擎、语言、处理参数、导出文件。
4. 统一对外接口，供 OCR 应用、PDF 工具应用、知识库、法规查询、聊天附件等模块调用。

### 4.2 文字识别应用

文字识别应用是独立用户工具，目标是让用户上传图片或扫描 PDF 后完成识别、校对、导出和业务分发。核心功能：

1. 上传图片、扫描 PDF、普通 PDF。
2. 自动判断文本型 PDF 还是扫描型 PDF。
3. 展示任务列表、识别进度、失败原因和重试入口。
4. 左侧显示原图或 PDF 页面，右侧显示识别文本。
5. 支持在原图上叠加 OCR 文字框和低置信度标记。
6. 支持人工编辑识别结果并保存修订。
7. 支持导出 TXT、Markdown、JSON、HTML、可搜索 PDF。
8. 支持发送到知识库、法规查询、公文写作材料或聊天附件上下文。

### 4.3 PDF 工具应用

PDF 工具应用是独立用户工具，目标是覆盖高频 PDF 处理场景。核心功能：

1. PDF 拆分、合并、旋转、删除页、重排。
2. PDF 转图片、图片转 PDF。
3. PDF 文本抽取。
4. 扫描 PDF 生成可搜索 PDF。
5. 导出处理结果，并保留原文件不被覆盖。
6. 后续扩展压缩、水印、页码、加密解密、表格提取和版面导出。

## 5. OCR 识别与版式还原策略

### 5.1 OCR 服务策略

1. Pivot 主项目只保留 HTTP OCR 适配器，默认引擎标识统一为 `http`。
2. 具体识别引擎（PP-OCR、PaddleOCR-VL、Tesseract、商业 OCR API 等）只在独立 OCR 服务项目内部配置、升级和切换。
3. 视觉大模型可在独立 OCR 服务内作为复杂版面、低置信度补救或人工复核辅助，不作为 Pivot 主项目的默认批量 OCR 运行时。

业务模块只能调用统一接口，例如：

```js
recognizePage(imagePath, {
  language,
  engine,
  dpi,
  confidenceThreshold,
  timeoutMs
});
```

### 5.2 原版式显示能力

识别出来的文字可以做到接近原图片或原 PDF 显示版式，但要区分三种目标：

1. 原样预览：以原图或 PDF 页面作为背景，叠加 OCR 坐标框。这种方式视觉最接近原件，适合应用内校对。
2. 可搜索 PDF：保留原 PDF 或页面图像外观，加透明文本层。这种方式视觉接近原件，同时支持复制和搜索。
3. 可编辑文档：导出 DOCX、Markdown、HTML 时只能尽量还原阅读顺序、标题、段落、表格和分栏，复杂版面不能承诺像素级一致。

验收时不得把“可搜索 PDF 的视觉一致”误写成“DOCX 像素级还原”。

client/chat/apps-workbench-pdf-tools.js

4. `.form-input`
5. `.workspace-modal`
6. `.workspace-modal-header`
7. `.workspace-modal-body`

### 6.4 数据表建议

建议新增以下表或等价结构：

1. `document_files`：登记上传文件、原始文件名、存储路径、文件类型、大小、页数、来源模块、用户。
2. `document_jobs`：记录处理任务、任务类型、状态、进度、错误信息、配置、创建时间、更新时间。
3. `document_pages`：记录页级渲染结果、页码、宽高、图片路径、文本长度。
4. `document_ocr_blocks`：记录 OCR 块、行、文本、坐标、置信度、语言、引擎。
5. `document_outputs`：记录导出结果、输出类型、文件路径、大小、生成状态。
6. `document_reviews`：记录人工修订、低置信度确认、复核人和复核时间。

## 7. 分阶段开发计划

### 阶段 0：方案固化与范围确认

目标：固化产品边界、技术边界、UI 规范和验收标准。

交付物：

1. 本方案文档。
2. OCR/PDF 能力清单。
3. 数据结构草案。
4. 接口草案。
5. UI 页面结构草案。

开发规范要求：

1. 必须阅读并遵守 [开发规范.md](../../开发规范.md)。
2. UI 方案必须声明复用全局样式。
3. 不进入编码前，不得新增临时页面或临时 OCR 实现。

验收标准：

1. 文档明确底座、文字识别应用、PDF 工具应用、知识库和法规查询的边界。
2. 文档明确 OCR 服务策略和版式还原边界。
3. 文档明确每阶段验收标准。
4. 文档通过 `npm run check:text`。

### 阶段 1：文档处理底座 MVP

目标：建立统一任务、文件、页面和输出管理能力。

主要工作：

1. 新增 `server/services/document-processing/` 服务目录。
2. 新增任务状态模型和基础数据库表。
3. 抽象文件登记、文本抽取、PDF 渲染、输出登记。
4. 复用现有 `extractDocumentText` 和 `renderPdfPages`。
5. 提供统一任务创建、查询、取消、重试接口。
6. 建立临时文件和输出文件清理策略。

接口建议：

1. `POST /api/apps/document-processing/jobs`
2. `GET /api/apps/document-processing/jobs`
3. `GET /api/apps/document-processing/jobs/:id`
4. `POST /api/apps/document-processing/jobs/:id/retry`
5. `POST /api/apps/document-processing/jobs/:id/cancel`
6. `GET /api/apps/document-processing/outputs/:id/download`

验收标准：

1. 文本型 PDF 能通过底座完成文本抽取并生成任务结果。
2. 扫描 PDF 能通过底座完成页面渲染并进入待 OCR 状态。
3. 图片文件能完成文件登记、基础元数据识别和任务创建。
4. 失败任务有错误摘要，不暴露敏感路径和堆栈。
5. 所有生成文件都通过受控下载接口访问。
6. 任务列表支持分页、状态筛选和失败重试。
7. 后端路由没有堆业务逻辑，核心逻辑位于服务层。

### 阶段 2：OCR HTTP 适配层

目标：接入外部 OCR HTTP 服务，但不先做复杂 UI。

主要工作：

1. 定义 OCR 统一接口。
2. 接入 HTTP OCR 适配器。
3. 固化外部服务 `/health` 与 `/ocr` 协议。
4. 支持服务地址、健康检查超时、单页请求大小、语言、页数上限、并发、识别超时和置信度阈值配置。
5. 保存页级 OCR 块、行、坐标、文本、置信度、语言和引擎信息。
6. 兼容旧 `paddle`、`tesseract` 等引擎值，统一归一到 `http`。

验收标准：

1. 单张图片能通过外部 OCR 服务完成识别并返回文本、坐标和置信度。
2. 扫描 PDF 至少能识别前 N 页，N 由全局配置作为硬上限控制。
3. OCR 任务超时后进入失败状态并可重试。
4. 低置信度文本能被标记为 `needs_review`。
5. 外部 OCR 服务不可用时，系统给出清晰错误，不影响文本型 PDF 抽取。
6. 业务模块不直接调用 OCR 引擎命令、SDK 或模型目录，只调用底座适配层。
### 阶段 3：文字识别应用 MVP

目标：提供可用的独立 OCR 工具。

主要工作：

1. 在应用中心增加“文字识别”入口。
2. 新增上传区、任务列表、状态筛选、任务详情。
3. 任务详情采用左侧原图或页面预览、右侧识别文本。
4. 原图预览支持 OCR 坐标框叠加和低置信度高亮。
5. 识别文本支持编辑、保存、恢复原识别结果。
6. 支持导出 TXT、Markdown、JSON。
7. 支持将识别结果发送到知识库和法规查询的导入流程。

UI 硬性要求：

1. 上传按钮使用 `.btn-primary` 或 `.btn-secondary`。
2. 输入框、筛选框、语言选择、引擎选择使用 `.form-input`。
3. 任务列表使用 `.table-container`、`.data-table`、`.compact-table`。
4. 分页使用 `.workspace-pagination`。
5. 详情弹窗使用 `.workspace-modal` 系列样式。
6. 不得硬编码按钮颜色、表格颜色、弹窗颜色和主题色。

验收标准：

1. 用户可以上传图片并获得 OCR 结果。
2. 用户可以上传扫描 PDF 并按页查看 OCR 结果。
3. 用户可以编辑识别文本并保存修订状态。
4. 用户可以导出 TXT、Markdown、JSON。
5. 用户可以看到低置信度标记。
6. 桌面端和移动端无文字溢出、控件重叠和布局跳动。
7. 页面视觉与知识库、法规查询、公文写作等工作区风格一致。

### 阶段 4：PDF 工具应用 MVP

目标：提供可用的独立 PDF 工具。

主要工作：

1. 在应用中心增加“PDF 工具”入口。
2. 支持 PDF 拆分。
3. 支持 PDF 合并。
4. 支持页面旋转、删除和重排。
5. 支持 PDF 文本抽取。
6. 支持 PDF 转图片。
7. 支持图片转 PDF。
8. 支持调用 OCR 底座生成可搜索 PDF。

UI 硬性要求：

1. 工具模式使用统一按钮、表单和分段控制样式。
2. 文件列表和输出列表使用统一数据表格。
3. 处理确认弹窗使用统一工作区弹窗。
4. 进度、失败、空状态使用现有工作区视觉语言。

验收标准：

1. 拆分、合并、旋转、删除页、重排不会覆盖原文件。
2. 每次处理都会生成独立输出文件。
3. 输出文件可通过受控接口下载。
4. 扫描 PDF 可以生成可搜索 PDF。
5. 文本型 PDF 不强制 OCR，优先直接抽取文本。
6. 批量处理有部分失败结果和失败明细。
7. UI 样式完全遵守全局规范。

### 阶段 5：知识库与法规查询集成

目标：让知识库和法规查询正确处理扫描 PDF 和图片材料。

主要工作：

1. 知识库上传时识别文本型文件和扫描型文件。
2. 空文本 PDF、扫描 PDF、图片进入 OCR 流程。
3. OCR 完成后再进入知识库分块和索引。
4. 法规导入支持 OCR 结果预览和确认。
5. 法规文档保留标题、条款层级、页码、来源和 OCR 置信度。
6. 检索结果支持回溯到文件、页码和片段。

验收标准：

1. 文本型 PDF 导入知识库不依赖 OCR。
2. 扫描 PDF 导入知识库时能自动或提示进入 OCR。
3. 图片材料能先 OCR，再由用户确认是否入库。
4. 法规扫描件导入前能预览 OCR 结果。
5. 低置信度内容不会静默入库，必须提示复核或确认。
6. 检索结果能展示来源文件和页码。
7. OCR 失败不会导致整个知识库或法规模块不可用。

### 阶段 6：版式还原与高级导出

目标：增强导出质量和复杂版面处理能力。

主要工作：

1. 生成可搜索 PDF。
2. 导出带坐标的 HTML。
3. 导出尽量保留阅读顺序的 DOCX。
4. 增强表格识别和段落重建。
5. 增强多栏、页眉页脚、水印、印章干扰处理。
6. 支持人工调整阅读顺序。

验收标准：

1. 可搜索 PDF 视觉上接近原文件，文本可搜索、可复制。
2. HTML 导出能保留页面尺寸、文字块位置和基础样式。
3. DOCX 导出清楚标注为“尽量还原”，复杂版面不承诺像素一致。
4. 表格识别结果可以被用户校正。
5. 低置信度或结构不确定区域有明显提示。

### 阶段 7：运维、治理与性能优化

目标：让文档处理能力可管理、可观测、可清理。

主要工作：

1. 增加管理员配置：OCR 服务地址、并发、超时、页数上限、单页请求大小上限。
2. 增加任务监控：队列长度、成功率、失败率、平均耗时。
3. 增加存储清理：临时文件、过期输出、失败残留。
4. 增加审计记录：谁上传、谁识别、谁导出、谁入库。
5. 增加安全限制：文件类型、路径隔离、下载鉴权、敏感日志过滤。
6. 增加性能优化：页面渲染缓存、OCR 分页并发、结果缓存。

验收标准：

1. 管理员可以配置 OCR 和 PDF 处理限制。
2. 大文件和超页数文件会被拦截或提示分批处理。
3. 任务统计能反映成功、失败、耗时和队列积压。
4. 过期临时文件能被清理。
5. 审计记录不包含文件正文、密钥和敏感 Token。
6. 并发处理不会阻塞普通聊天、知识库和法规查询接口。

## 8. 推荐 MVP 范围

第一版建议只做以下范围：

1. 文档处理底座基础任务。
2. HTTP OCR 服务适配器。
3. 图片 OCR。
4. 扫描 PDF OCR。
5. OCR 结果编辑和导出 TXT、Markdown、JSON。
6. PDF 拆分、合并、旋转、删除页、重排。
7. 扫描 PDF 生成可搜索 PDF。
8. OCR 结果进入知识库和法规查询前的确认流程。
9. 全局统一 UI 样式校验。

暂缓到后续版本：

1. 高保真 DOCX 导出。
2. 复杂表格自动还原。
3. 大规模批处理调度。
4. 多引擎自动竞赛。
5. 云端 OCR 服务。
6. 高级 PDF 压缩和加密解密。

## 9. 总体验收标准

### 9.1 功能验收

1. 文本型 PDF 可以直接抽取文本。
2. 扫描 PDF 可以进入 OCR 并输出可编辑文本。
3. 图片可以进入 OCR 并输出可编辑文本。
4. OCR 结果包含页码、文本、坐标、置信度和引擎信息。
5. PDF 工具可以拆分、合并、旋转、删除页、重排和生成输出文件。
6. 可搜索 PDF 可以搜索和复制文本。
7. 知识库和法规查询可以使用 OCR 结果入库，并保留来源。

### 9.2 UI 验收

1. 按钮必须使用 `.btn-primary`、`.btn-secondary`、`.btn-danger` 等全局按钮样式。
2. 输入框、搜索框、下拉框、文本域必须使用 `.form-input` 或同体系全局类。
3. 弹窗必须使用 `.workspace-modal`、`.workspace-modal-header`、`.workspace-modal-body`。
4. 表格必须使用 `.table-container`、`.data-table`、`.compact-table` 或同体系样式。
5. 分页必须使用 `.workspace-pagination` 或已有统一分页渲染函数。
6. 颜色必须使用全局 CSS 变量，不得硬编码主题色。
7. 桌面端和移动端不得出现文本溢出、控件重叠、表格错位和按钮挤压。

### 9.3 安全验收

1. 上传文件有类型、大小、数量和业务场景限制。
2. 文件路径由服务端生成，不信任前端路径。
3. 输出文件通过受控接口下载。
4. 日志不输出密钥、Token、连接串、用户隐私和完整文件正文。
5. 临时文件有清理策略。
6. 任务失败不暴露内部堆栈。

### 9.4 测试验收

必须按改动范围运行或说明以下检查：

1. `npm run check`
2. `npm test`
3. `npm run verify`
4. OCR/PDF 专项样例验证。
5. UI 桌面端和移动端截图或人工验收。

OCR/PDF 专项样例至少包括：

1. 文本型中文 PDF。
2. 扫描中文 PDF。
3. 英文图片。
4. 中英文混排图片。
5. 空白页 PDF。
6. 加密 PDF。
7. 大文件或超页数 PDF。
8. 低清晰度扫描件。

## 10. 主要风险与缓解措施

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| OCR 服务部署复杂 | 用户无法使用 OCR | 通过 HTTP 适配器封装，启动时检测服务状态，缺失时给出明确配置提示 |
| 中文识别质量不稳定 | 入库内容错误 | 独立 OCR 服务优先使用适合中文批量识别的引擎，并在 Pivot 侧保留置信度、低置信度复核和人工编辑 |
| 大 PDF 处理慢 | 队列阻塞 | 页数上限、分页任务、并发限制、进度反馈、后台处理 |
| 版式还原预期过高 | 用户误解能力 | 明确区分原样预览、可搜索 PDF、可编辑文档 |
| 多模块重复实现 | 维护成本高 | 所有模块只能调用文档处理底座 |
| UI 风格割裂 | 产品体验下降 | 每阶段 UI 验收必须检查全局样式类和主题变量 |
| 文件安全风险 | 数据泄露 | 受控路径、受控下载、日志脱敏、临时文件清理 |

## 11. 实施顺序建议

优先顺序：

1. 阶段 1：文档处理底座 MVP。
2. 阶段 2：OCR 引擎适配层。
3. 阶段 3：文字识别应用 MVP。
4. 阶段 4：PDF 工具应用 MVP。
5. 阶段 5：知识库与法规查询集成。
6. 阶段 6：版式还原与高级导出。
7. 阶段 7：运维、治理与性能优化。

原因：

1. 先做底座可以避免两个应用重复开发。
2. 先做 OCR 适配层可以让文字识别应用和可搜索 PDF 共用能力。
3. 先提供独立应用可以让用户直接处理其他文档和 PDF 文件。
4. 再集成知识库和法规查询，可以降低对现有核心流程的冲击。

## 12. 阶段完成定义

每个阶段完成时，必须同时满足：

1. 功能满足本阶段验收标准。
2. 代码遵守 [开发规范.md](../../开发规范.md)。
3. UI 遵守全局统一样式规范。
4. 无临时代码、无调试残留、无乱码。
5. 后端长耗时任务不阻塞普通请求。
6. 文件处理有失败处理和清理策略。
7. 已运行必要测试，或明确说明无法运行原因和剩余风险。

## 13. 后续开发入口建议

后续进入编码时，建议按以下任务拆分：

1. 设计并实现文档处理底座数据表和服务层。
2. 迁移现有 `extractDocumentText`、`renderPdfPages` 到底座调用链。
3. 实现 OCR 适配器接口和 HTTP OCR 服务适配器。
4. 实现文字识别应用前端页面和任务详情。
5. 实现 PDF 工具应用前端页面和基础工具。
6. 将知识库导入接入 OCR 底座。
7. 将法规导入接入 OCR 底座。
8. 补齐专项测试、UI 验收和文档说明。
