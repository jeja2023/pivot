# Pivot 聊天 Agent 任务升级产品级优化方案

> 方案版本：v1.0  
> 制定日期：2026-10-19  
> 状态：产品与架构深化方案；不代表本方案中的后续阶段已完成上线  
> 基线版本：v0.4.6（普通对话默认发送、显式“以 Agent 执行”入口）

## 1. 结论

v0.4.6 已解决“普通消息误入后台 Agent”的问题，但“以 Agent 执行”仍是一次点击后立即创建 Run 的二元交互。它要求用户在提交前自行判断任务是否需要长程执行，且没有在执行前统一呈现目标、交付物、工具范围、风险与预算。

下一阶段应将该入口升级为**任务升级器（Task Promotion）**：

```text
普通消息
  ├─ 直接发送 → 普通对话 / 按需资料检索 / 受控工具候选
  └─ 任务升级 → 任务草案 → 计划审阅 → 用户开始执行 → Agent Run
```

核心原则：**系统可以建议任务化，用户决定是否创建和执行任务；系统可以自动完成低风险步骤，不能自动扩大权限、越过预算或执行外部副作用。**

## 2. 外部产品的可复用设计原则

下表只总结公开文档明确披露的交互与治理能力，不推断任何产品的内部模型路由实现。

| 产品/能力 | 公开设计信号 | 对 Pivot 的可复用结论 |
|---|---|---|
| OpenAI Agents SDK | 将工具、Handoff、Guardrail、人工复核和 Trace 作为编排原语，而不是把 Agent 当作一次普通模型调用。 | Pivot 应把“任务草案、执行、审批、验证、结果”视为同一受控编排，而不是仅给聊天请求附加 `chatMode=agent`。 |
| ChatGPT Work / Cloud Browser | 长任务可在用户离开后继续；遇到登录、用户输入或重要动作时暂停；网站访问许可与重要动作确认分离。 | “可访问某资源”不能等同于“可执行后果性操作”；Pivot 应分开资源许可、工具许可、动作审批与人工接管。 |
| Claude Code | 公开 CLI 支持 Plan 权限模式、允许/禁止工具列表、最大轮次及外部权限提示。 | 任务先计划、工具最小授权、预算上限和可中断性应成为每次任务的显式契约。 |
| GitHub Copilot | 提供 Interactive、Plan、Autopilot 自主等级；Plan 先生成计划，用户审阅后再开始实施。 | Pivot 不应只有“聊天/立即 Agent”两个状态；应引入“协作、先规划、受控后台”三个可理解的执行等级。 |
| Cursor Background Agents | 后台 Agent 是可查看状态、发送追问、随时接管的独立会话，而非聊天消息的隐式副作用。 | Pivot 的后台 Run 应有独立任务卡、运行时间线、接管入口和可恢复结果，而不是只在聊天流中显示状态文字。 |

来源：[OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk)、[OpenAI Guardrails 与人工复核](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)、[ChatGPT Cloud Browser](https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt)、[Claude Code CLI 权限模式](https://docs.anthropic.com/en/docs/claude-code/cli-usage)、[GitHub Copilot Agent Sessions](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions)、[Copilot Plan Mode](https://docs.github.com/en/enterprise-cloud%40latest/copilot/how-tos/chat-with-copilot/chat-in-ide?tool=visualstudio)、[Cursor Background Agents](https://docs.cursor.com/background-agent)。

## 3. 产品目标与非目标

### 3.1 目标

1. 用户不需要在发送前理解“普通模式”和“Agent 模式”的技术差别。
2. 复杂任务在执行前形成可审阅、可编辑、可过期的任务草案。
3. 计划、资源范围、工具范围、审批和预算在创建 Run 前可见。
4. 低风险任务可在一次确认后后台完成；高风险步骤始终按步骤暂停。
5. 用户可追问、暂停、恢复、接管或取消后台任务，并能复核最终交付物。
6. 自动任务化建议必须可度量误报、漏报、转化和完成质量，不能仅凭“点击率”判断成功。

### 3.2 非目标

- 不让普通对话因关键词或消息长度自动创建持久 Agent Run。
- 不在任务草案阶段执行外部写入、发送消息、下载、上传或浏览器写操作。
- 不将“工具候选”视为用户已授权工具执行。
- 不在缺少真实评测、预算和故障演练证据时开放无监督 Autopilot。
- 不重写现有 Agent Runtime、Execution Grant、审批、Task Transaction、恢复或资源租约语义。

## 4. 目标交互模型

### 4.1 三类用户动作

```text
┌─────────────────────────────────────────────────────────────┐
│ 输入任务、问题或材料                                           │
├─────────────────────────────────────────────────────────────┤
│ [发送]                 → Chat：直接回答                       │
│ [任务]                 → Plan：生成可编辑任务草案             │
│ [任务 ▾]               → 协作执行 / 后台执行（符合条件时）    │
└─────────────────────────────────────────────────────────────┘
```

`发送`永远保持普通对话。现有“以 Agent 执行”按钮应演进为`任务`入口：默认动作是**先规划**，不是立即运行。只有用户在草案中确认，或在低风险任务上明确选择“后台执行”，才创建 Agent Run。

### 4.2 非阻塞的任务建议

当本地准入层检测到以下组合时，可展示一次轻量建议卡，但不阻塞发送：

- 明确交付物：报告、表格、文件、邮件、更新结果、可审计清单；
- 两个以上任务动作：查询→汇总→生成、读取→对比→通知；
- 明确外部目标：指定系统、资料范围、人员、网页、文件或时间边界；
- 明确持续性：完成后通知、后台继续、定时、失败重试。

建议卡示例：

```text
检测到可执行任务：查询订单 → 汇总异常 → 生成报告
[查看计划]  [仍按对话回答]  [不再提示此类建议]
```

建议只能来自本地规则、已有受控意图分类或低成本影子评测；它不得调用工具、创建任务或弹出审批。对“写一封邮件”“解释数据库”等创作/概念请求必须保持静默，避免过度任务化。

### 4.3 三种自主等级

| 等级 | 面向用户的名称 | 行为 | 适用范围 |
|---|---|---|---|
| Chat | 直接回答 | 不创建 Run；可按需 RAG 和工具候选 | 问答、创作、解释、单步轻任务 |
| Plan | 先规划 | 创建草案；仅可读分析，不产生副作用 | 不确定范围、复杂任务、首次使用的能力 |
| Run | 协作执行 / 后台执行 | 创建持久 Run；按策略暂停、恢复与验收 | 明确交付物、多步骤、可恢复任务 |

首个发布版本只允许“协作执行”和“受控后台执行”；“完全自动执行”必须等待每种风险类别的独立评测、灰度和 P0/P1 演练完成。

## 5. 任务草案：执行前的产品契约

### 5.1 草案卡必须展示的内容

| 字段 | 要求 |
|---|---|
| 任务目标 | 用户原意的简明重述，可编辑；保留来源消息 ID，不复制保存原文。 |
| 交付物 | 结果类型、保存位置/接收对象、验收条件和失败时交付策略。 |
| 步骤计划 | 有序步骤、并行关系、可跳过条件、每步是否只读/写入。 |
| 资料与工具 | 访问控制过滤后的资料范围、候选工具、用途和最小权限。 |
| 风险 | 外部写入、通知、浏览器、文件、敏感数据、不可逆动作的明确标记。 |
| 资源预算 | 最大轮次、Token、工具调用、时限、并行数；展示档位而非伪精确费用。 |
| 待澄清项 | 无法安全推断的目标、时间范围、收件人、数据源或完成标准。 |

草案生成必须使用结构化 JSON Schema；任一缺失的高风险字段使草案保持 `needs_clarification`，不能显示“开始执行”。

### 5.2 草案状态机

```text
created → planning → needs_clarification ─┐
                    │                     ├→ cancelled / expired
                    └→ ready_for_review → approved → run_created
                                                     │
                                                     └→ rejected
```

- 草案默认 24 小时过期；资料、工具发布版本、权限、预算策略变化时标记 `stale`。
- 用户编辑目标、范围或交付物后创建新 revision；旧 revision 只读可审计。
- `approved` 仅表示允许创建 Run，不替代 Run 内部每个高风险步骤的审批。

## 6. 执行安全与人工参与

### 6.1 四个彼此独立的许可

```text
资源可见  → 可读资料 / 工具目录
工具可用  → 具体 Tool + Release + Scope
动作批准  → 本次副作用参数与影响范围
运行许可  → 预算、并发、网络、Worker、恢复资格
```

任何一层允许都不能隐含放开下一层。该模型延续 Pivot 已有的 Capability、Execution Grant、工具策略、审批和 Worker 隔离边界。

### 6.2 人工检查点

| 事件 | 默认行为 |
|---|---|
| 首次使用新工具/新资料源 | 展示用途与范围，由用户确认。 |
| 登录、密码、验证码、敏感表单 | 暂停并请求人工接管；不读取或记录敏感输入。 |
| 发送、写入、删除、付费、发布、权限变更 | 工具参数冻结后逐步审批。 |
| 连续失败、预算临界、结果不确定 | 暂停，展示已完成步骤、未完成原因和恢复选择。 |
| 最终交付 | 执行 Verifier；结果与验收标准不符时标记部分完成，不伪造成功。 |

## 7. 建议的技术落点

### 7.1 新增受控资源

| 资源 | 责任 | 关键字段 |
|---|---|---|
| `agent_task_drafts` | 草案自身 | `id`、`user_id`、`session_id`、`source_message_id`、`revision`、`status`、`plan_json`、`policy_snapshot`、`expires_at` |
| `agent_task_draft_events` | 审计与协作 | 草案 revision、事件类型、操作者、脱敏差异摘要、时间 |
| `TaskDraftService` | 创建/校验/过期 | Schema、权限、工具 Release、预算和策略快照校验 |
| `TaskPromotionService` | 对话升级 | 本地候选判定、建议节流、草案构建、普通对话回退 |

草案只持有来源消息 ID 和脱敏/哈希化的上下文摘要；聊天消息原文仍遵循既有会话存储与权限规则，不应复制到新的审计表。

### 7.2 建议 API

```text
POST /api/agents/task-drafts
GET  /api/agents/task-drafts/:id
PATCH /api/agents/task-drafts/:id
POST /api/agents/task-drafts/:id/approve
POST /api/agents/task-drafts/:id/start
POST /api/agents/task-drafts/:id/cancel
```

`start` 必须在单一事务中重新验证草案 revision、权限、工具 Release、预算与策略版本，然后创建现有 Agent Run 和 Task Transaction。不得由浏览器提交工具定义、风险等级、预算上限或批准状态。

### 7.3 与现有模块的关系

- `chat-context-assembler` 与语义路由继续负责普通聊天的 RAG/工具候选，不创建草案或后台 Run。
- `agent-runtime` 继续是唯一实际执行引擎；草案批准后只通过既有受控 Run 创建入口进入。
- `agent-task-transaction`、Execution Grant、审批、检查点、Outbox 和 Worker 继续覆盖执行期副作用与恢复。
- `agent-domain-acceptance-evidence` 不把草案通过率视为五分生产证据；真实灰度、SLO 和委员会验收口径不变。

## 8. 评测、指标与灰度

### 8.1 产品指标

| 指标 | 说明 | 初始门槛 |
|---|---|---:|
| 任务建议误报率 | 用户选择“仍按对话回答”或直接关闭的建议占比 | 观察，不设上线承诺 |
| 任务建议漏报率 | 用户后续主动任务化而此前未建议的比例 | 观察，不设上线承诺 |
| 草案批准率 | `approved / ready_for_review` | 按场景分层观察 |
| 计划澄清率 | 草案进入 `needs_clarification` 的比例 | 识别输入契约缺陷 |
| 任务完成率 | Verifier 通过的 Run 占比 | 与直接聊天分开统计 |
| 计划偏离率 | Run 实际工具/风险超出批准草案的比例 | 必须为 0；否则阻断执行 |
| 人工接管恢复率 | 接管后成功恢复并完成的比例 | 分能力与环境统计 |

### 8.2 灰度规则

1. 先只启用“任务建议 + 草案”，不开放自动后台执行。
2. 用脱敏、版本化任务集比较普通聊天、草案和 Agent Run 的完成质量、成本、延迟与安全事件。
3. 草案创建与批准只向内部试点用户开放；默认“先规划”。
4. 对每种副作用工具单独完成审批、故障、恢复、回滚和 P0/P1 演练后，才允许“批准后后台执行”。
5. 任一草案版本、工具 Release、权限或策略漂移时阻止启动，要求重新审阅。

## 9. 分期实施

### Phase A：任务草案与计划审阅

- 实现 `agent_task_drafts`、草案 Schema、revision、过期和来源消息绑定。
- 将“以 Agent 执行”默认动作改为“先规划”。
- 计划阶段只能使用只读资料元数据和工具目录摘要，禁止工具执行。
- 交付草案卡、编辑、澄清、批准/取消以及审计事件。

**通过条件**：普通发送仍不创建 Run；草案不产生工具调用；审批后的 revision 与创建 Run 的策略快照一致。

### Phase B：协作执行与后台接续

- 草案批准后创建现有 Agent Run，显示任务卡、步骤时间线、预算、审批、暂停、恢复和接管。
- 将聊天中的 Agent 状态摘要关联到独立任务详情，而不是在消息流中承载全部控制面。
- 任务完成后提供“复用为计划任务”建议，但不自动创建周期任务。

**通过条件**：断线、刷新、授权暂停、人工接管和 Worker 恢复均保持同一任务 ID 与审计链。

### Phase C：受控自主等级与持续评测

- 仅在有冻结评测、灰度指标和审批演练的工具域提供“批准后后台执行”。
- 引入可配置的协作/计划/后台等级，但不开放无边界 Autopilot。
- 将路由复核、草案放弃、Verifier 失败和人工接管写入评测闭环。

**通过条件**：每个等级都具备独立的安全、质量、成本和恢复指标；不以单一点击率替代验收。

## 10. 当前应优先做的决策

1. 将 v0.4.6 的“以 Agent 执行”按钮默认语义改为“生成任务计划”，还是保留“立即执行”并增加下拉选项。
2. 明确第一批允许批准后后台执行的低风险能力域，例如只读数据汇总、受控报告生成或影子工作区代码检查。
3. 冻结任务草案 JSON Schema、预算档位、风险分类和最终交付物类型。
4. 选取 30–50 条脱敏真实任务，覆盖直接回答、任务建议、草案澄清、审批暂停、恢复和交付验证。

在以上决策完成前，不应把“更智能的 Agent 入口”误实现为更激进的自动执行。
