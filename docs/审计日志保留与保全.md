# 审计日志保留与保全

## 默认保留策略

全局操作审计表 `audit_logs` 默认保留 **365 天**，覆盖登录、权限变更、删除、导出和管理操作等已接入全局审计的事件。维护任务启动时检查一次，之后每 24 小时检查一次；只删除时间戳早于保留期限的记录。365 天属于工程默认值，具体部署仍须确认适用的行业、地区、合同及单位制度要求，不能将 180 天直接等同于六个自然月。

```dotenv
AUDIT_LOG_RETENTION_DAYS=365
AUDIT_LOG_CLEANUP_PAUSED=false
```

`AUDIT_LOG_RETENTION_DAYS` 接受 1～36500 的整数天数；缺失、零、负数、小数和非数字内容回退为 365 天，超过上限取 36500 天。已有合法的自定义值继续生效；升级不会自动覆盖服务器上的旧值，部署时应显式检查。缩短保留期前应先确认保全和归档要求。

## 调查期间暂停删除

发生安全事件、争议或调查时，在服务器部署配置中设置：

```dotenv
AUDIT_LOG_CLEANUP_PAUSED=true
```

重启服务使部署配置生效。Docker 使用 `env_file` 时应重建应用容器，使容器载入新环境变量。该开关暂停整个 `audit_logs` 表的到期删除，启动清理和直接调用清理函数都遵守该开关；日志写入、查询、筛选和导出继续工作。非空且无法识别的开关值按暂停处理，避免配置拼写错误导致证据被删除。

系统监控的“审计清理”显示“保全中 · 暂停清理”，提示中显示保留天数；保全跳过会记录 `lastSkippedAt`，不会更新上次真实成功清理时间或累计删除数。Prometheus 指标 `pivot_audit_log_cleanup_paused` 为 1 表示暂停，`pivot_audit_log_retention_days` 表示当前清理使用的保留天数。

调查结束后，先确认相关记录已按要求导出、归档或不再需要保全，再将开关改回 `false` 并重新载入部署配置。恢复后的首次维护会删除所有已超过配置期限的记录，不提供解除保全后的额外宽限期。延长保留期或开启保全均不能恢复已经删除的日志。

## 范围与归档

该策略和开关仅作用于 `audit_logs`。API 调用日志、智能体执行记录、制度查阅记录、BI 独立安全记录和数据库备份沿用各自生命周期；涉及这些证据时，需同时按对应机制保全，不能认为开启本开关即保全所有业务数据。

尚无必须引入冷热分层的容量依据，因此当前继续在线保留一年。容量需要分层时，应先建立受控、可检索并完成完整性核验的独立归档，再删除在线副本。现有管理页面 CSV 导出最多 10000 条，不能直接当作完整历史归档；数据库滚动备份也不能代替按期限保留的独立审计归档。
