# Pivot Hermes / OpenClaw 类 Agent 体验建设方案

> 文档版本：v1.0
>
> 更新日期：2026-08-24
>
> 适用系统：Pivot 智枢企业智能中枢
>
> 文档性质：产品、架构与工程实施方案

## 1. 执行摘要

Pivot 当前已经具备企业级 Agent Runtime 的核心底座：持久化 Agent Run、工具调用、MCP、工作流、计划任务、审批、预算、检查点、崩溃恢复、事件回放、沙箱、浏览器执行、长期记忆和评测能力。

本方案的目标不是把 Pivot 改造成一个可以无审批修改自身代码的“自我进化模型”，而是在现有底座之上形成接近 Hermes/OpenClaw 的个人 Agent 使用体验：

1. Agent 了解用户，但只使用经过用户确认的长期档案和记忆。
2. Agent 可以持续运行、主动提醒、响应事件和恢复中断任务。
3. Agent 可以使用工具、浏览器、文件、知识库和工作流，但所有副作用仍受策略和审批控制。
4. Agent 可以提出创建 Skill、保存工作流、调整偏好的建议，但必须经过用户确认、版本化、测试和回滚。
5. Agent 从任务结果和用户反馈中改进提示、工具选择和工作流建议，而不是直接改写生产代码。

### 1.1 建设结论

按当前代码基础，底座完成度约为 60%～70%，用户体验完成度约为 35%～45%。建议采用以下目标：

| 目标 | 交付范围 | 估算工期 |
| --- | --- | ---: |
| 内部 MVP | 单用户档案、记忆治理、持续任务、反馈闭环、基础主动提醒 | 4～6 周 |
| 企业 Beta | 多租户治理、事件触发、Skill/工作流审批发布、多端通知、可观测性 | 8～12 周 |
| 企业生产版 | 高可用、灾备、灰度、完整安全评测、多渠道接入、规模化运营 | 3～5 个月 |
| 接近成熟产品体验 | 多端生态、持续目标、复杂主动性、Skill 市场和运营体系 | 6～12 个月 |

以上按 2 名后端/全栈、1 名前端、兼职 QA 和安全工程师估算。若只有 1 名工程师，日历时间大致翻倍。

## 2. 产品定位与边界

### 2.1 产品定位

Pivot 应被定义为：

> 一个具备长期记忆、工具调用、审批、恢复、主动任务和受控能力进化的企业级个人 Agent Runtime。

它不是：

- 无审批的自主代码修改器；
- 绕过企业权限的个人超级账号；
- 只依赖 Prompt 的“看起来会成长”的聊天机器人；
- 把所有用户对话永久保存并自动用于训练的黑盒系统。

### 2.2 允许自主与必须受控

| Agent 可以自主完成 | 必须经过策略或用户确认 |
| --- | --- |
| 拆解目标、排列步骤、选择已授权工具 | 写入业务数据库、发送消息、修改生产文件 |
| 在预算内重试、诊断错误、选择替代工具 | 新增网络域名、扩大文件目录、使用新凭据 |
| 汇总任务结果、提出 Skill/工作流/偏好建议 | 安装 Skill、发布工作流、改变权限和策略 |
| 根据历史反馈调整工具排序和提示建议 | 修改自身代码、修改安全边界、自动提权 |
| 在已批准的持续任务中按规则巡检 | 将临时任务升级为长期后台任务 |

### 2.3 非目标

本阶段不包含训练新的基础模型、模型参数级持续学习、模型直接提交生产代码、未经授权的后台进程、跨用户隐式共享记忆，以及首期同时接入所有 IM、邮件、语音和 IoT 渠道。

## 4. 目标用户体验

### 4.1 首次使用

1. 用户打开 Agent 工作台。
2. 系统引导填写称呼、角色、语言、输出偏好和常见工作类型。
3. 系统展示长期记忆开关、可记忆类别和敏感信息规则。
4. 用户选择工具、目录、网络范围和通知渠道。
5. 系统创建默认个人 Agent 档案版本 `1`。
6. 用户可以直接运行第一个任务，不要求先配置复杂工作流。

### 4.2 日常任务

```text
用户目标
  -> 读取档案、记忆和会话上下文
  -> 规划步骤并选择已授权工具
  -> 低风险动作自动执行 / 高风险动作请求审批
  -> 执行、观察、诊断、重试或恢复
  -> 交付结果并请求反馈
  -> 沉淀反馈信号和可选的进化提议
```

### 4.3 主动任务

```text
Webhook / 时间 / 文件 / 数据变化
  -> 校验租户、用户、签名、频率和输入映射
  -> 创建受策略约束的 Agent Run
  -> 执行、审批、暂停、恢复或失败
  -> Web 收件箱、IM、邮件或 Webhook 回调
```

## 5. 总体架构

继续沿用现有控制面/执行面架构，不新增第二套 Agent Runtime。

```text
┌──────────────────────────────────────────────────────────────┐
│                        Pivot Control Plane                    │
│ Profile │ Memory Governance │ Policy/PDP │ Approval │ Inbox   │
│ Agent Run │ Workflow/Skill │ Feedback │ Evaluation │ Audit    │
└───────────────────────────┬──────────────────────────────────┘
                            │ Run / Event / Approval / Artifact
┌───────────────────────────▼──────────────────────────────────┐
│                        Execution Plane                        │
│ Runtime │ Tool Broker │ Browser Worker │ Code Worker          │
│ Workspace Jail │ Desktop Bridge │ Network Policy │ Checkpoint │
└──────────────────────────────────────────────────────────────┘
```

### 5.1 服务边界

| 服务 | 职责 | 明确不负责 |
| --- | --- | --- |
| `agent-profile` | 档案读写、版本和上下文摘要 | 不直接改变权限 |
| `memory-governance` | 分类、保留期、禁止类别、敏感检测 | 不保存敏感明文 |
| `agent-feedback` | 结果反馈、工具失败、评分和信号 | 不自动修改代码 |
| `agent-evolution` | 提议、审批、应用状态机 | 不绕过版本化发布 |
| `agent-proactive` | 事件、持续目标、提醒、冷却和去重 | 不直接执行未授权工具 |
| `agent-channel` | Web、IM、邮件、Webhook 适配 | 不内置业务权限判断 |
| `agent-evaluation` | 回归集、线上抽样和质量门禁 | 不代替人工审批 |

### 5.2 统一事件

建议事件类型：`profile.updated`、`memory.policy.updated`、`agent.run.completed`、`agent.run.failed`、`agent.approval.requested`、`agent.evolution.proposed`、`agent.evolution.approved`、`agent.evolution.applied`、`tool.reliability.changed`。

事件必须具备用户、租户、Run、版本、时间、幂等键和审计关联，跨进程投递继续使用现有 Event Log/Outbox。

## 6. 分阶段实施计划

### 阶段 0：基线和范围冻结

**周期：第 1 周。**

#### 任务

- 确定首期工具集合和至少两种主动事件源。
- 确定档案、记忆、反馈和进化提议的默认策略。
- 定义成功、部分成功、失败、取消和用户修正的统一口径。
- 建立任务成功率、恢复成功率、审批通过率、工具错误率和平均耗时基线。
- 为每个 P0 功能建立用户故事、接口、数据表、测试和发布条件。

#### 交付物

- 产品范围冻结清单。
- 用户旅程和原型。
- 指标字典和仪表盘字段。
- P0/P1/P2 backlog、负责人和依赖图。

#### 验收

- 不再出现“Agent 自主修改自身代码”这类未定义需求。
- 每项 P0 工作都有可验证的完成标准。

### 阶段 1：个人 Agent 工作台和记忆治理

**周期：第 2～3 周。**

#### 后端

- 完善 `agent_profiles` 的版本、更新来源、审计、导入导出和并发更新。
- 支持档案字段级更新，避免多设备保存互相覆盖。
- 增加记忆策略版本、生效时间和策略变更审计。
- 展示 `fact`、`preference`、`temporary`、`sensitive` 四类记忆。
- 增加保留期、自动归档、全部导出和全部删除能力。
- 确保禁用类别不写入、不检索、不注入模型上下文。

#### 前端

- 把个人档案、记忆治理从“运行环境”折叠面板提升到 Agent 工作台一级入口。
- 增加首次使用向导、档案版本和恢复入口。
- 记忆列表展示来源、保留期、置信度、最近使用和删除状态。
- 说明每条记忆为何被使用，并提供批量禁用和删除。

#### 验收

- 新用户 3 分钟内完成档案配置并运行首个任务。
- 用户可以查看、修改、禁用和删除任意个人记忆。
- 敏感文本不进入长期记忆表、检索结果、反馈摘要或 Agent Prompt。
- 两个设备并发更新档案不会静默覆盖。

### 阶段 2：持续目标和主动式 Agent

**周期：第 3～6 周。**

建议增加 `agent_goals` 统一抽象，或在现有 schedule/workflow 上建立兼容层，字段包括：目标、范围、优先级、状态、事件源、授权范围、预算、冷却时间、失败阈值、下次运行、最近 Run 和版本。

#### 首期事件源

1. 定时：每天、工作日、固定间隔和 Cron。
2. Webhook：签名、重放保护、输入映射、限流和来源白名单。
3. 文件：工作区新文件、文件变更和稳定写入检测。
4. 数据：查询结果变化或业务状态变化。

#### 治理要求

- 每个主动目标都有明确授权范围和过期时间。
- 每次触发创建独立 Agent Run，不复用不可审计的隐式上下文。
- 重复事件不能创建重复 Run。
- 连续失败、超预算和权限拒绝自动熔断。
- 副作用动作继续走 Approval/PDP/PEP。

#### 验收

- 服务重启后已授权目标能继续调度。
- 非幂等副作用不会因重试重复执行。
- 用户可以暂停、恢复、终止和删除持续目标。
- 所有主动运行都出现在统一收件箱。

### 阶段 3：受控能力进化闭环

**周期：第 5～10 周。**

当前已有提议表、审批接口和偏好应用；本阶段把 Skill 和工作流接入验证、发布、灰度和回滚。

#### 提议来源

- Agent 根据任务重复模式提出建议。
- 用户从任务结果保存为 Skill 或工作流。
- 反馈分析发现某类任务反复出现。
- 工具失败分析建议增加校验或更换工具。

#### 提议内容

- 类型：`preference`、`skill`、`workflow`。
- 来源 Run、Trace 或反馈。
- 目标问题和预期收益。
- 结构化变更、工具、权限、网络和文件范围。
- 风险等级、测试计划和回滚说明。

#### 状态机

```text
draft -> pending_review -> sandbox_validate -> versioned_draft -> published
                 |                 |                     |
              rejected       validation_failed        cancelled
```

#### Skill 流程

1. 生成 Manifest、版本、说明、工具和权限草案。
2. 执行 schema、白名单、签名、依赖和供应链校验。
3. 在隔离目录执行静态检查和最小回归用例。
4. 用户审阅 diff、权限、网络范围和测试结果。
5. 批准后创建新版本，不覆盖旧版本。
6. 支持个人启用、团队灰度、管理员发布和自动回滚。

#### 工作流流程

1. 从 Trace 或用户选中的任务生成 DAG 草稿。
2. 审阅节点、依赖、输入输出、审批点和副作用。
3. 使用预览模式运行，禁止直接触发生产副作用。
4. 通过固定评测集后保存为新草稿版本。
5. 用户或管理员审批后发布，支持 diff、灰度和回滚。

#### 验收

- 未批准的 Skill/工作流不会被运行时发现或执行。
- 测试失败的版本不能发布。
- 每次应用都有版本、操作者、来源 Run、测试结果和回滚入口。
- 任何提议都不能修改 PEP、PDP、网络白名单、租户权限或审计规则。

### 阶段 4：结果反馈和能力路由

**周期：第 7～10 周，可与阶段 3 并行。**

#### 反馈采集

- 任务结果：成功、部分成功、失败、取消。
- 用户评分：1～5 分或有帮助/无帮助。
- 用户修正：修正说明和修改后的答案。
- 工具反馈：错误、超时、权限拒绝和返回质量差。
- 工作流反馈：节点失败、输入映射错误和审批等待过长。

#### 初期信号

```text
tool_score = 0.40 * success_rate
           + 0.25 * (1 - timeout_rate)
           + 0.20 * user_helpful_rate
           + 0.15 * schema_valid_rate
```

信号按用户、租户、工具版本和任务类型分层，保留样本数、统计窗口和置信度。

#### 运行时使用

- 只读工具可以按可靠性调整优先级。
- 高失败工具要求额外输入校验或人工确认。
- 工具建议带统计窗口和样本数解释。
- 提示词改进以版本化模板建议存在，不能覆盖管理员模板。
- 工作流改进只能生成草稿，不能修改已发布版本。

#### 验收

- 用户能在任务详情提交反馈，并在反馈页查看汇总。
- 反馈不会污染其他用户的个人记忆。
- 工具推荐变化可回溯到统计窗口和样本。
- 关闭反馈优化后，运行时恢复固定排序。

### 阶段 5：统一收件箱、多渠道和协作

**周期：第 9～14 周。**

#### 收件箱

统一展示运行中任务、待审批任务、失败任务、主动提醒、进化提议、发布结果、预算告警和工具异常。

每条消息至少包含来源 Run、风险、过期时间、操作按钮、已读状态、稍后处理、静音和过滤条件。

#### Channel Adapter

建设顺序建议为：Web/Electron、Webhook、一个企业 IM、邮件，最后再扩展其他渠道和语音。

每个 Channel Adapter 必须实现身份映射、幂等键、附件、审批交互、消息分片、重试、退避和死信；渠道层不得绕过服务器权限。

### 阶段 6：企业生产化

**周期：第 12～20 周。**

- PostgreSQL、连接池、队列、Outbox 和通知的压力与故障测试。
- 租户配额、用户并发、任务预算和工具级限额。
- 重放、断网、审批过期、数据库故障和服务重启演练。
- Skill 签名轮换、依赖锁定、恶意包和路径穿越测试。
- 浏览器隔离、SSRF、敏感字段脱敏和日志审计测试。
- 灰度发布、版本回滚和紧急停用开关。
- 运维手册、故障分级、人工接管和灾备流程。

## 7. 数据模型规划

### 7.1 当前表

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `agent_profiles` | 用户个人 Agent 档案 | `user_id`、`profile_json`、`version` |
| `memories` | 长期记忆 | `type`、`governance_class`、`retention_mode`、`sensitive`、`status` |
| `user_settings` | 记忆策略和用户设置 | `agent_memory_policy` |
| `agent_feedback` | 运行结果和用户反馈 | `run_id`、`outcome`、`rating`、`correction`、`tool_failures` |
| `agent_evolution_proposals` | 受控进化提议 | `kind`、`proposed_change`、`status`、`version` |
| `agent_runs` | 任务运行 | 状态、目标、预算、策略和 metadata |
| `agent_tool_calls` | 工具调用审计 | 工具、策略决定、错误、耗时和输入摘要 |

### 7.2 建议新增

#### `agent_goals`

用于统一持续目标、主动任务和用户授权。建议字段：`id`、`user_id`、`tenant_id`、`title`、`goal`、`status`、`trigger_spec`、`authorization_spec`、`budget_spec`、`cooldown_seconds`、`max_failures`、`next_run_at`、`last_run_id`、`version`、`created_at`、`updated_at`。

#### `agent_channel_bindings`

保存 Webhook、IM、邮件等渠道和用户/租户之间的受控映射。密钥只存引用，不存明文。

#### `agent_evolution_validations`

保存提议的静态检查、沙箱测试、评测结果、风险评估和发布门禁。

#### `agent_tool_reliability`

保存工具版本、任务类型、时间窗口、样本数、成功率、超时率和置信度。

## 8. API 规划

### 8.1 当前第一版接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET/PUT | `/api/agents/profile` | 读取或更新个人档案 |
| GET/PUT | `/api/memories/policy` | 读取或更新记忆策略 |

### 8.3 通用要求

- 所有接口经过用户和租户范围校验。
- 写接口支持幂等键或明确的状态条件。
- 所有审批、应用、发布、回滚写审计日志。
- JSON 字段限制深度、长度和数组数量。
- 不向浏览器返回凭据明文、私钥、内部令牌或完整敏感输入。
- 错误响应包含稳定 `code`，前端不依赖中文错误文本做逻辑判断。

## 9. 安全与治理

### 9.1 记忆治理

| 类别 | 默认行为 | 内容 |
| --- | --- | --- |
| `fact` | 可保存、可检索 | 项目、系统、任务事实 |
| `preference` | 可保存、可检索 | 用户输出和工作偏好 |
| `temporary` | 短期或带过期时间 | 当前任务临时上下文 |
| `sensitive` | 永不持久化 | 密码、Token、银行卡、证件和私钥 |

用户关闭某类记忆后，系统必须不再写入、不再检索、不再注入，并提供清理旧记录的入口；策略变化本身需要审计，但不记录敏感原文。

### 9.2 进化治理

- 提议和应用分离。
- 批准和发布分离。
- 草稿和已发布版本分离。
- 验证失败不能发布。
- 高风险权限增加必须重新审批。
- 不能修改 PEP、PDP、网络策略、租户权限和审计规则。
- 发布后必须可以回滚。
- 所有变化可追溯到来源 Run 和反馈信号。

### 9.3 数据隔离

个人档案、个人记忆和个人反馈默认只属于本人；共享 Skill、共享工作流和组织级反馈必须显式标记作用域；跨用户可靠性信号必须脱敏、聚合并设置最小样本阈值。

## 10. 指标、测试与验收

### 10.1 产品指标

| 指标 | MVP 目标 | 生产目标 |
| --- | ---: | ---: |
| 首次任务完成率 | ≥ 60% | ≥ 80% |
| 任务成功率 | ≥ 75% | ≥ 90% |
| 用户有帮助率 | ≥ 70% | ≥ 85% |
| 主动任务按时率 | ≥ 95% | ≥ 99% |
| 审批响应中位数 | ≤ 30 分钟 | ≤ 10 分钟 |
| 可恢复任务恢复成功率 | ≥ 90% | ≥ 98% |

### 10.2 安全指标

未授权工具调用、审批哈希不匹配继续执行、敏感信息进入长期记忆、未批准能力被运行、重复副作用和 Webhook 重放重复 Run 都必须为零。

### 10.3 测试层级

- 单元：档案规范化、记忆分类、反馈统计、提议状态机、版本 diff 和回滚。
- 集成：Run 加载档案、终态自动反馈、记忆禁用、提议验证和发布门禁。
- 安全：越权、Prompt 注入、Skill 包、Webhook 重放、SSRF、凭据和路径泄露。
- 故障：服务重启、数据库短暂不可用、工具超时、审批过期、Outbox 重复投递和主动任务熔断。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 主动任务过多 | 通知疲劳 | 默认低频、聚合、可解释、可暂停 |
| 记忆错误或过时 | 错误个性化 | 来源、置信度、保留期、编辑和解释 |
| 进化提议扩大权限 | 安全事故 | 权限 diff、签名、沙箱、审批和发布门禁 |
| 反馈样本太少 | 错误推荐 | 最小样本数、置信区间、静态回退 |
| 多渠道身份错误 | 越权操作 | 显式绑定、二次确认、租户和用户双校验 |
| 持续失败 | 资源浪费 | 预算、冷却、熔断和人工接管 |
| 数据库或事件故障 | 重复副作用 | 幂等键、Outbox、Checkpoint 和演练 |
| 范围不断扩大 | 项目延期 | P0/P1/P2 冻结，每两周重新排序 |

## 15. 最终验收场景

1. 用户设置“中文、先给结论、输出简洁”，连续任务中 Agent 正确应用档案。
2. 用户禁止保存偏好后，新偏好不入库，旧偏好不再检索。
3. 用户授权每天检查资料目录，发现新文件后创建任务并通知。
4. 任务需要发送外部消息时暂停审批，拒绝后不执行副作用。
5. 服务在非幂等工具执行后重启，恢复时重新审批而不是重复执行。
6. Agent 提议创建 Skill，用户拒绝后 Skill 不可见、不可执行。
7. Skill 草案沙箱测试失败时不能发布，并显示失败原因。
8. 工作流新版本错误率升高时可以回滚上一版本。
9. 用户低评分并修改答案后，反馈进入个人闭环但不污染其他用户。
10. 工具连续失败后给出替代建议，并可回到固定工具排序。
11. Webhook 重复投递只产生一个 Agent Run。
12. 删除用户后个人档案、记忆、反馈和提议按保留策略处理并可审计。

## 16. 下一步执行建议

立即启动以下五项 P0 工作：

1. 将个人档案、记忆治理、结果反馈和进化提议从“运行环境”折叠面板提升到 Agent 工作台一级入口。
2. 建立统一 Agent Inbox，先整合现有通知、审批和运行失败。
3. 在现有计划任务和触发器之上抽象 `agent_goals`，先交付定时和 Webhook。
4. 为 Skill/工作流提议增加沙箱验证、评测门禁、发布和回滚状态。
5. 建立工具可靠性统计和 P0 安全回归集。

完成这五项后，Pivot 将从“可扩展 Agent 平台”进入“可长期使用的企业个人 Agent Beta”阶段；后续再扩展多渠道和生态能力，不需要重写当前 Runtime。
