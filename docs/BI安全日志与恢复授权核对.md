# BI 安全日志与恢复授权核对

本手册对应建设方案第 22.4 节。独立安全日志、持久 outbox 和恢复后默认关闭已经接入；数据库与全部共享文件的物理共同恢复点、生产故障域与 100 GiB 演练仍须分别验收。本机 Windows 验证只记录文件 fsync，不能替代 Linux 文件及目录 fsync、独立身份和存储故障域认证。

## 部署与首次启用

配置 `DATA_ANALYSIS_SECURITY_JOURNAL_DIR` 为受保护的独立目录，`DATA_ANALYSIS_SECURITY_KEY_FILE` 为单独保管的密钥文件。日志和密钥均不得位于 `data`、`uploads`、分析存储或其他配置的 Artifact/CAS 等主数据目录中；密钥也不能放在日志目录内。生产环境使用独立服务身份与不同主机/主存储的故障域，操作系统控制日志写入和密钥读取，备份另行保管密钥。路径分开不等于已经通过故障域验收。

密钥内容为 32 字节或更长随机值的十六进制表示。Linux 日志目录权限为 0700，密钥和记录文件为 0600。示例密钥只能由负责密钥保管的人员在指定环境创建，不能复制开发环境中的值。

迁移 `202611070009` 先扩展表、索引与捕获触发器，不在 DDL 事务中扫描历史数据。回填按固定表白名单、主键游标和短事务推进，保留扫描/捕获计数；每批最多 500 行，锁等待上限两秒、单语句上限五秒。默认每次后台轮询有有限的批次和时间预算。历史行与并行变更用相同资源锁串行化，已存在的当前事件不再生成旧基线。

运维身份执行并检查输出：

```sh
node scripts/bi_security_recovery.js --flush --full
node scripts/bi_security_recovery.js
```

需要重复执行时沿持久游标续跑，不删除进度或 outbox。只有全部历史清单完成、待确认事件为空且日志可验证，初始化状态才转为 `ready`。日志确认按事件 ID 幂等，独立追加后主库 ACK 前崩溃不会产生第二次提交。首次启用的强制标记保存在数据库中，后续关闭重型执行开关、重启旧客户端或移除环境变量均不能绕过独立确认。

## 正常运行与故障

主体、来源、模型、字段政策，以及分析视图、仪表盘和旧指标的共享/删除变更在主事务内生成 outbox。BI 审计也进入独立日志。每条记录包含稳定事件 ID、资源修订、请求/主体标识、实际数据库登录身份、前后摘要和删除墓碑；密码、密钥、原始 SQL、查询结果和字段原值不写入安全记录。审计详细内容在独立记录中保留摘要与动作/结果，恢复时明确标注原明细摘要，不伪造已经丢失的原始明细。

对外完成必须等待独立加密文件、文件 fsync、Linux 目录 fsync和主库确认。文件以不可覆盖的原子链接发布，并用 AES-256-GCM、用途 AAD、连续位置和前项摘要保护。实时读取检查已确认锚点；后台至少每分钟复核完整链，完整性复核超过九十秒不能继续借用旧缓存。缺口、错误密钥、头部退回或未知数据库事件均拒绝读取。

副本中断时主库撤权已经生效，不把已提交的收紧操作回滚。接口返回 `ANALYSIS_SECURITY_COMMITTED_PENDING`、`applied: true` 与 `securityConfirmationPending: true`，界面显示“权限变更已在主库生效，权限已收紧，安全记录待持久确认”。维护者修复日志或密钥后继续确认同一事件。批量操作也可能超过单次同步确认期限，不能据此重复执行原业务变更。

运营接口展示安全模式、待确认数量与年龄、独立副本可用性和回填进度；复用原告警路由报告日志不可验证与恢复未签认。维护监测和安全日志管理通过系统运维入口执行，不能由普通业务账号关闭栅栏。

## 恢复后重放

在隔离恢复实例、尚未开放业务网络时执行：

```sh
node scripts/bi_security_recovery.js --replay --reason '填写恢复点、事故编号和负责人核对原因'
```

命令先持久关闭读取，再验证独立日志、重放当前撤权和删除墓碑。历史账号、模型、数据集和共享资产不能因恢复较旧数据库而重新获得旧权限；已删除字段不恢复为公开政策。缺失的身份只按不可登录、停用状态补齐依赖，不能从安全日志重建密码。较新定义缺失的模型保持归档，须恢复对应不可变定义后重新核查。

旧 Token、Refresh Token、API Key 和分析执行租约失效。仍满足业务截止和当前权限的工作可以重新领取，过期/取消工作保持终态；自动刷新与业务告警先暂停，外部通知不盲目重放。此过程不代表已经恢复全部业务数据，更不能在物理文件尚未核验时开放服务。

即使旧数据库和现存独立日志的头部一致，也不能据此证明故障前没有尚未确认的撤权。恢复流程始终保持关闭，要求当前身份源和业务授权核对。生产工具必须在恢复后、开放网络前完成此步骤；手工恢复数据库也不能省略。

## 当前身份与授权签认

恢复负责人可以导出待核对草稿：

```sh
node scripts/bi_security_recovery.js --prepare-authority --output /srv/recovery/authority-draft.json
```

草稿来自恢复实例，只是核对清单，不是当前授权证明。当前身份源负责人和业务授权负责人必须根据独立保留的当前记录逐项核对账号状态、凭据指纹、归属、字段与共享范围，明确保留或删除全部历史主体和资产。不能把旧数据库导出文件直接签为最新状态。无法确认最新状态时继续关闭。

签认结构的 `resources` 使用固定表名和稳定目标标识，`payload_json` 仅包含安全政策字段。活跃账号的 `credentialDigest` 是当前密码验证器的 SHA-256 指纹；恢复库验证器与当前身份源不一致时，先按现有受控流程恢复/重置验证器，不能仅将账号改为活跃来跳过核对。指纹不能用于重建密码。清单不包含密码验证器、密码或密钥原值。

核对完成后填写 `authority`、`approvedBy`、`reason`、`approvedAt` 和 `expiresAt`，并把 `requiresCurrentAuthorityReview` 明确改为 `false`。签认时间不得早于本次恢复关闭时间，有效期不超过一小时。由独立保管的 Ed25519 私钥签署；应用仅持有配置 `DATA_ANALYSIS_SECURITY_AUTHORITY_PUBLIC_KEY_FILE` 指定的公钥：

```sh
node scripts/bi_security_recovery.js --sign-authority /srv/recovery/authority-reviewed.json --signing-key /srv/authority-keys/private.pem --output /srv/recovery/authority-signed.json
node scripts/bi_security_recovery.js --reconcile /srv/recovery/authority-signed.json
```

签认绑定实例标识和独立日志高水位，修改内容、缺项、错误凭据指纹、过期签名或其他实例的证明均拒绝。权威变更、核对摘要和审计先事务提交，再等待独立确认；中途失败仍保持关闭。若已应用但确认未完成，可在证明有效期内重跑同一签认文件，按已保存摘要继续确认，不能重复提升 Token 代次或生成多个核对提交。

安全模式转为 `ready` 后，仍须完成共同恢复点全部文件校验、固定查询/导出与当前拒绝验证、执行器预检、生产开关和恢复责任签认。安全日志完成不等于 G0—G7 放行。私钥、密码恢复材料和签认文件都不能贴入普通日志、工单正文或业务聊天。
