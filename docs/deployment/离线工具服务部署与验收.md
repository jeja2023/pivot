# 离线工具服务部署与验收

适用主程序：v0.7.32 起；独立工具镜像：`pivot-offline-tools:1.0.0`；Kroki/Mermaid：`0.28.0`。版本职责与升级范围见 [v0.7.32 发布记录](../releases/v0.7.32-离线工具受控接入与产物交付.md)。

本手册覆盖本仓库交付的 Python 有限规则审查与 Kroki 图形工具，以及 Skill、连接治理和产物下载链路。统一 TTS 引擎、DOCX 修订保真和复杂 OA 清洗仍应按具体现场选型；本次不以通用接入底座代替这些引擎的业务验收。

## 1. 联网准备

环境要求：目标相同的 Linux CPU 架构、Docker Engine/Compose、Node 22；主业务 PostgreSQL 沿用独立运维。测试 Python 基线为 3.12，MCP 固定 `1.26.0`。构建服务：

```bash
docker build -f docker/offline-tools/Dockerfile -t pivot-offline-tools:1.0.0 .
docker pull yuzutech/kroki:0.28.0
docker pull yuzutech/kroki-mermaid:0.28.0
node scripts/offline_tools_release.js --export /secure-delivery/tools-1.0.0
node scripts/offline_tools_release.js --verify /secure-delivery/tools-1.0.0
```

输出目录必须全新。BOM 记录三个镜像的本地 ID、架构、仓库摘要和每份归档摘要。保留依赖锁中的所有分发摘要，Linux 构建自动跳过 Windows 专属包；基础镜像使用 Dockerfile 固定摘要。不要在生产机在线 pip install。

如需导出已验证的其他本地工具镜像标签，可在导出命令后追加 `--tools-image=pivot-offline-tools:标签`。导出的 Compose 会使用该标签，BOM 和镜像归档也记录同一镜像；仍需确认三个镜像与目标机器的系统和架构匹配。测试镜像不自动成为正式发布物。

离线包包含仅使用 Python 3.12 标准库的 `verify_bundle.py`；内网无 Node 源码环境时运行 `python3.12 verify_bundle.py .` 即可先校验全部交付文件，然后再执行 `docker load`。BOM 和校验脚本的来源也必须可信。

新导出的离线包还包含 `install_bundle.py` 一键安装脚本。已有六文件旧包也可使用可信来源的同版 [安装脚本](../../docker/offline-tools/install_bundle.py)，不必改写旧包的 BOM。

镜像导出包不包含业务数据、生产配置或服务密钥。物料完整性与可信来源是两个不同要求，需要来源认证时应另行签名清单并通过可信通道交付。

## 2. 内网安装

### 一键安装

适用于 Linux 上已有 Pivot 和 `ai-bridge` Docker 网络、Docker Compose 2.30 以上及 Python 3.12 的环境。在生产机执行（路径按实际情况修改）：

```bash
sudo python3.12 /secure-delivery/tools-1.0.0/install_bundle.py /secure-delivery/tools-1.0.0 /data/pivot
```

脚本校验物料摘要和 Docker 系统架构、检查已有同名镜像及 Compose 配置、创建或复用密钥、导入镜像、启动服务并验证匿名拒绝及认证后的工具目录。它不显示密钥，不覆盖不同内容的同名镜像或 Compose 文件；现有密钥必须满足容器 UID/GID 1000 的读取和权限要求。失败时已导入的镜像和已创建的密钥会保留，排查后可重新执行。包和 BOM 仍需事先经过可信来源与生产交付审核。

旧包未包含安装脚本时，把可信来源的 `docker/offline-tools/install_bundle.py` 单独传至生产机，并把命令中的脚本路径替换为该文件的实际路径。脚本只安装和检查服务；仍需由 Pivot 最高管理员在下一节登记连接，并通过受控渠道录入密钥。此步骤不会自动更改 Pivot 权限或任务网络策略。

### 手动安装

在内网先运行 `--verify`，再分别 `docker load -i image-1.tar`、`image-2.tar`、`image-3.tar`；比对导入后镜像 ID 与 BOM，确认 OS 和架构匹配。将 `docker-compose.tools.yml` 放到 Pivot 部署目录；确认外部网络 `ai-bridge` 存在，或由管理员首次创建。

```bash
node scripts/offline_tools_release.js --secret
docker compose -f docker-compose.tools.yml config --quiet
docker compose -f docker-compose.tools.yml up -d --no-build --pull never
docker compose -f docker-compose.tools.yml ps
```

密钥命令只创建不存在的 `data/secrets/offline-tools-token`。Linux 上由部署管理员设置目录访问和文件权限，确保容器 UID 1000 可读，其他用户不可读；例如按实际运维账号配置属组，文件模式 `0440`。不要将目录设为全员可读写。密钥经受控渠道录入 Pivot 凭据字段，不通过聊天或普通日志传递。

工具入口非 root、只读根目录、临时 tmpfs、CPU/内存/PID 限制。工具入口虽不发布宿主机端口，仍必须校验 Bearer 密钥；同网络容器及宿主机不是可信身份的证明。Kroki 和 Mermaid 只在 `renderer` 内部网络，不能自行访问公网；工具入口共享网络的公网出口应由现场防火墙管理。

启动时工具服务等待 Mermaid 的实际渲染健康检查通过；冷启动 Chromium 可能需要数十秒。若持续未就绪，检查 Mermaid 容器日志、可用内存和 CPU，以及 `renderer` 网络；不要通过跳过健康检查把启动状态误认为绘图能力已就绪。

轮换时同时更新 secret 文件与 Pivot 连接凭据，重建工具容器，验证新密钥成功、旧密钥和匿名请求拒绝。不要用关闭 SSRF 或模拟管理员角色来绕过接入失败。

## 3. Pivot 服务登记

1. 内置超级管理员创建全局工具连接，地址 `http://offline-tools:8501/mcp`，协议 `standard`，鉴权 `bearer`，录入部署密钥。
2. 通过配置的 `protocolVersion` 固定兼容版本 `2025-11-25`，保存并刷新工具目录，取得真实数字服务 ID。
3. 核对 `run_ast_audit`、`render_diagram` 的 Schema，配置治理与审批，禁止关闭调用日志或权限判定。
4. 普通用户只有在服务端数据库核验该活动全局连接可见后才获得固定端点的私网访问。个人自行创建的连接仍受原出站约束；`ALLOW_PRIVATE_MCP_URLS=false` 会关闭该委托。
5. 任务策略显式允许 Origin `http://offline-tools:8501` 与端口 8501；登记全局连接不能覆盖任务网络白名单。敏感地址、重定向和解析到敏感地址的 DNS 结果仍应拒绝。

全局连接对可访问用户开放。需要更细部门/人员边界时必须在工具/能力治理层实施并验证，不能把普通个人共享连接当作已批准的全局网络连接。

## 4. 原生报告与图形交付

Python 工具采用明确的结构化返回：

```json
{"pivotArtifact":{"kind":"audit","data":{"status":"completed","issues":[]}}}
```

图形使用 `kind: diagram` 与 SVG 文本。Agent 执行器在工具输出契约通过后调用 `tool-result-artifacts`，仅接受登记的类型与有限体积。服务器生成身份和调用标识，调用原有 `artifact.render`，完成 Artifact → IR → CAS → Rendition。输出带产物/渲染 ID、摘要与下载提示，复用原有预览/下载面板，不新增一套页面。

审查报告保存行/列、规则命中和原始 JSON，输出 HTML。SVG 在服务器解析后拒绝脚本、事件处理器、外部资源、异常样式及过深结构；导出 SVG/PNG 使用同一渲染器注册表，PNG 转换有像素上限。下载凭证短期、一次性且绑定用户/租户，不能直接暴露容器目录。

手动工具 Schema 测试显示原始执行结果，不自动创建 Agent 产物。需要交付文件时应在 Agent 运行中调用，保留真实 `stepId`。

## 5. Skill 与签名发布

本机读取用真实工具全名 `mcp.0.workspace.read`；要求桌面连接器在线且代码目录已授权。外部服务 ID 从目录复制，例如 `mcp.42.run_ast_audit`。清单和正文都必须使用相同的真实名称；静态能力登记不证明设备或工具可执行。

ZIP 根目录只保留一个清单。`SKILL.md` 的正文是执行指令，独立指令文件只能与其一致；冲突时拒绝。`SKILL.sig` 为 RSA-SHA256 分离签名，载荷是 `agent-skill-packages.packageDigest(entries)` 计算的十六进制包摘要字符串，不是 ZIP 文件本身的字节。验证使用受信公钥；组织发布私钥只由现有服务端签名机制管理。

流程：签名包导入 `/api/agents/skills/package` → 草稿 → 预览 → `/api/agents/skills/versions/:id/validate` 通过 → `/publish`。个人版本也不能跳过完整验证。范围为 `personal/team/organization`，团队/组织共享还需管理员批准和组织签名。版本回退通过 `/api/agents/skills/releases/:id/rollback`。

## 6. 备份与恢复

`node scripts/offline_backup.js --plan` 显示配置解析后的实际路径，包括 CAS、上传、文档处理、数据分析、Agent 大对象、运行包和技能目录。可配置的目录以实际环境变量为准；容器内路径需按真实挂载定位到宿主机。

先停止所有应用写入、后台任务及外部写入者，再在维护环境执行：

```bash
node scripts/offline_backup.js --output /secure-backups/pivot-20261023 --maintenance-confirmed
node scripts/offline_backup.js --verify /secure-backups/pivot-20261023
```

脚本生成数据库 custom dump、各受控数据目录和逐文件摘要清单，拒绝已有目录、符号链接、重叠来源和嵌套输出。文档处理与分析目录的 `tmp` 不纳入备份；不存在的默认可选目录在清单中标记为 `absent`，显式配置但不存在的目录会报错。失败留下 `incomplete` 标记。配置、外部数据库和加密密钥另行保管，恢复后需同一加密密钥才能解密原凭据。

新版清单包含各来源状态；旧版清单仍可校验，但只覆盖其当时记录的数据库、CAS 和上传目录，不能据此认定文档处理、分析或其他 Agent 文件已备份。按清单将每个来源恢复到部署中对应的实际目录，并检查 `absent` 项是否确实没有数据。

恢复演练先还原到独立数据库和新文件卷，以对应镜像/配置启动隔离应用，核对产物读取、摘要、用户权限和核心业务；验收后才安排切换，保留旧数据。统一时间戳不等于跨数据库/文件原子快照。

## 7. 验收矩阵

| 类别 | 必须验证 |
| --- | --- |
| 鉴权 | 匿名/错误令牌 401，正确令牌成功，轮换后旧令牌失效 |
| 连接 | 普通授权用户成功、个人私网连接拒绝、撤销后拒绝、任务白名单不匹配拒绝 |
| 网络 | loopback/link-local/元数据拒绝、DNS 复核、重定向拒绝、断网冷启动 |
| 扫描 | 正常、直接调用、导入别名、遮蔽、语法错误、空源码、超限、中文行列 |
| 绘图 | Mermaid/Graphviz 实际输出，损坏 SVG 拒绝，外部资源/脚本拒绝，图片大小限制 |
| 产物 | 数据库记录、CAS 可读、摘要一致、跨用户拒绝、下载凭证不可重复兑换 |
| 运维 | 服务重启、取消/超时后进程回收、物料校验、完整备份校验和隔离恢复 |

测试执行应保存各阶段结果。纯契约测试、真实 SDK、Docker 引擎、目标设备性能和恢复演练分别记录，跳过项不计为通过。
