# 完整 PPT 制作引擎部署与验收

v0.7.135起生产优先使用[PPT Master独立服务部署与更新](PPTMaster独立服务部署与更新.md)：服务独立启动，Pivot只配置一次地址和密钥；兼容服务协议的升级只替换服务镜像。本文保留原直接Docker执行路径及详细引擎验收说明。

日期：2026-11-08。引擎基线：PPT Master 6.8.0，提交 `769547394107870a0c7b5ad8d1c0c75035123aef`。Pivot 仍提供现有原生文稿编辑和导出；完整引擎是独立的受限执行路径。

独立镜像统一命名为 `ppt-master:6.8.0`，可由其他项目按其 JSON 协议接入。本文的 `PIVOT_*` 变量属于 Pivot 宿主配置，不限定镜像名称或使用方。

v0.7.133起生产优先使用[一键离线发布与更新](PPT引擎一键离线更新.md)：构建自动导出`ppt-master.tar`、登记完整镜像ID并签名，生产首次登记公钥后用单命令更新、检查和回退。下面的仓库摘要与手工签名配置保留为高级部署方式；不能把本机验收的临时签名直接用于正式发布。

## 1. 运行结构

- 后端驱动当前账号可用模型，按所选上游流程读取完整发行包的 SKILL、流程和参考文档，再通过固定 JSON 协议操作任务目录。
- 文本、图片、音视频、字体和原有 PPTX 从当前授权素材复制成输入快照，输入不可由模型覆盖。执行单元无网络，不接收用户密钥或任意 Shell。
- 固定上游工具提供 SVG 校验、原生导出、原稿往返和模板校验；最终 PPTX 必须来自最近成功的上游导出且源稿指纹未改变。
- 任务状态、步骤、模型用量、确认问题和检查点持久保存；跨实例使用条件租约和心跳。取消、期限、权限和父任务状态在继续动作及交付前复核。
- 输出为原生 PPTX 与项目源包；Brand/Style 等不要求 PPTX 的模板工作区可单独交付源包。复杂原生对象保留在 PowerPoint/上游项目，不自动声称已转换成 Pivot 画布元素。

## 2. 准备完整发行包

```powershell
python scripts/prepare_ppt_master.py --checkout <固定提交的本地上游仓库>
python scripts/build_ppt_master.py --checkout <固定提交的本地上游仓库> --tag ppt-master:6.8.0
```

准备器通过 `git archive` 读取固定提交，不采用可能已经修改的工作区文件；核对 Git 树和完整内容摘要，保留全部上游技能资源与归属门禁。输出目录非空时拒绝覆盖，应使用新的空版本目录。构建器使用最小 tar 上下文，避免把开发目录、凭据或缓存带进镜像。

发行包固定信息在 `config/ppt-master-engine.json`；依赖精确版本在 `docker/ppt-master/requirements.lock`，Python 底座按镜像摘要固定。源码库不携带完整上游二进制/示例或安装环境，运行包在构建期准备并进入镜像。

本路径不安装 PyMuPDF，文档文本提取继续复用 Pivot；完整上游文件保持原样，PDF 来源转换后端在运行状态中明确标为 Pivot。需要上游 PDF 后端时应先完成依赖许可处理。镜像中字体、FFmpeg、Python 包和上游各自的第三方许可仍需随正式制品治理。

## 3. 签名、镜像与开关

1. 获取已构建并预置到执行节点的 `image@sha256:...`，登记到既有 Capability Worker 信任清单，允许固定入口 `python,/runner/runner.py`。
2. 使用既有正式发布密钥对清单规范化内容签名，配置可信公钥和签名清单路径。生产继续强制校验，不以标签或本地“已验证”声明替代。
3. 配置下列变量并重启服务：

```dotenv
PIVOT_CAPABILITY_WORKER_ENABLED=true
PIVOT_PPT_MASTER_ENABLED=true
PIVOT_PPT_MASTER_IMAGE=registry.example/ppt-master@sha256:<已验证摘要>
PIVOT_CAPABILITY_WORKER_TRUSTED_MANIFEST=<签名清单路径>
PIVOT_CAPABILITY_WORKER_SIGNING_PUBLIC_KEY=<可信发布公钥>
```

实际开关、摘要或签名缺失时，工作台显示不可用。服务端还须能访问既有 Docker 执行服务和对应任务挂载目录；不要为此将任意用户输入变成 Docker 参数或授予用户直接访问 Docker 服务的能力。

默认限制：单用户一个活动制作任务、全局两个，等待确认也占用名额；每次工具执行 1 CPU、1GiB 内存、120 秒、非特权 UID、只读根文件系统、无网络。每个任务默认最多 80 个模型轮次、40 万令牌，最大分别为 160、50 万；用户可在上限内增加预算继续，不重置累计消耗。完整快速流程的首轮输入约 3.4 万令牌，默认预算需覆盖多轮规划、确认及生成；它是累计上限，不代表实际用量或固定费用。

## 4. 使用入口

v0.7.131起主入口默认为“AI自由设计”，单位模板、原稿保留及统一模板库按需进入。模板库中的PPT Master Style按固定目录复制到任务工作区后校验并应用；单位PPTX模板使用当前账号可见的固定源版本，按原稿保留路径处理。内置用途模板的新配色单独升级版本，不覆盖历史文稿快照。

应用 → PPT 制作 → “完整制作引擎”；已有文稿的 AI 面板也可进入。选择模型、工作方式、页数、累计预算和执行轮次上限，填写制作要求和事实材料，按需上传原稿或图片/音视频。达到预算或轮次上限时，可在允许范围内提高对应数值后继续。

- 默认制作按上游合同确认设计；快速制作只有明确选择时才启用；美化和图片重建要求相应源文件。
- 图片重建需要所选模型支持图片输入；请求时按既有图片限制读取和压缩输入快照，最多携带全局图片限制数量的前几张图片，源图优先。检查点只保存快照路径，不保存图片编码。其他素材仍可通过任务路径使用。
- 生成过程中显示实际阶段、步骤与累计用量。真实确认问题会暂停，用户填写答复后继续。未完成、取消和失败不能显示为交付完成。
- 失效租约或可恢复失败可从检查点继续；先核对现有文件，不能盲目重放上一轮动作。已取消任务不自动恢复。
- 完成后下载原生 PPTX 和完整项目源包；重新打开入口可查询最近任务。文件沿用一次性下载令牌与当前账号鉴权，不直接暴露任务工作区路径。

聊天任务可使用 `presentation.master` 的 start/status/respond/resume/cancel 操作。工具登记成功不代表文件已完成，respond 只能传递用户对当前问题的实际答复。

## 5. 验收

```powershell
node scripts/verify_ppt_master.js --image ppt-master:6.8.0
node scripts/test_ppt_master_browser.js <上一步输出的证据目录>
```

容器验收使用临时测试签名密钥，只验证签名合同，不代表正式发布签名或生产认证。它实际执行完整发行包预检、上游项目初始化、SVG 校验和原生导出、公式/形状对象回读、未修改原稿页面字节保留、模板工作区校验，以及越界、脚本和危险导出拒绝。浏览器验收使用确定的测试模型操作序列，最终文件仍由真实上游容器生成；不能将测试模型流程通过表述为真实模型设计质量通过。

真实模型与业务材料还应核对：论证与事实完整性、设计质量、模板/原稿保真、长稿成本和时延、实际语音/图像服务可用性，以及目标 PowerPoint/WPS/LibreOffice 矩阵。原生文件包检查与独立 Office 实际渲染分开报告。

## 6. 当前配置与能力边界

运行包完整保留上游能力，但宿主开放的执行动作仍按固定白名单和实际配置决定。当前运行单元不联网：可使用已上传照片、图形、音视频及字体；在线图片生成、联网搜索、实时语音服务和 Windows PowerPoint 视频导出需要后续经过现有权限/网络或桌面执行面适配。不能为获得这些能力绕过隔离边界，也不能把没有配音的视频或静态图片登记为旁白/动画完成。

完整引擎产物不经过当前Pivot文稿模型重新导出，避免复杂对象被重建丢失。v0.7.128新增源包权威的原稿编辑及页面视频路径，见[离线部署与支持范围](PPT原稿编辑与视频离线部署.md)；按对象类型开放明确字段，不宣称所有原生内容均可编辑。现有工作台文稿与历史版本不因此迁移或覆盖。
